Modifications to crimson_pro_regular.ttf
========================================

The SIL Open Font License permits modification and does not require this notice,
but it is recorded for the same reason `special-elite/MODIFICATIONS.txt` in this
repository is: a binary font file carries no diff, so without a written record a
future re-download of the upstream release would silently undo the fix.

The bundled copies of this font (mobile/src/main/res/font/crimson_pro_regular.ttf
and wear/src/main/res/font/crimson_pro_regular.ttf) have been modified from the
upstream release at https://github.com/google/fonts/tree/main/ofl/crimsonpro. Only
the vertical metrics were changed; no glyph outline, character mapping, name table
or Reserved Font Name was touched.

  hhea.ascent           918  ->   862
  hhea.descent         -220  ->  -276
  hhea.lineGap            0  ->     0   (unchanged)
  OS/2.sTypoAscender    918  ->   862
  OS/2.sTypoDescender  -220  ->  -276
  OS/2.sTypoLineGap       0  ->     0   (unchanged)
  OS/2.usWinAscent     1006  ->   984
  OS/2.usWinDescent     295  ->   286

Why
---

Every renderer centres a line of text by its line box. This font's box centre sat
0.055 em above its own capital letters, which reads as text sitting high in a
centred pill or chip. Upstream's own realistic descenders (g, j, p, q, y, accented
Latin letters) already came within 0.011 em of the old descent line, so the
correction had to be checked carefully against clipping them - see below.

The correction centres the box on the font's flat capital letters - E, F, H, I, L,
which are perfectly uniform in this font. Its digits agree closely (0.053 em
offset measured the same way), so the flat-cap target is not fighting the digits.

ascent + |descent| is unchanged (1138 units in this font's 1024-unit em), so line
height, spacing, wrapping and every reserved height are the same as upstream; only
where the ink sits inside that box moves. The flat-cap band now lands within
0.0001 em of the box centre, and every ordinary descender clears the new descent
line by 0.044 em - a wider margin than it had before the fix (0.011 em), because
lowering the ascent to correct the top freed up room at the bottom for the same
total span.

usWinAscent/usWinDescent were nudged to the font's real ink extents
(head.yMax/yMin).

Pinned by BundledFontMetricsTest, so a re-download from upstream fails the build
rather than silently reverting the fix.
