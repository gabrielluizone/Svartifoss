Modifications to zilla_slab_regular.ttf
=======================================

The SIL Open Font License permits modification and does not require this notice,
but it is recorded for the same reason `special-elite/MODIFICATIONS.txt` in this
repository is: a binary font file carries no diff, so without a written record a
future re-download of the upstream release would silently undo the fix.

The bundled copies of this font (mobile/src/main/res/font/zilla_slab_regular.ttf
and wear/src/main/res/font/zilla_slab_regular.ttf) have been modified from the
upstream release at https://github.com/google/fonts/tree/main/ofl/zillaslab.
Only the vertical metrics were changed; no glyph outline, character mapping, name
table or Reserved Font Name was touched.

  hhea.ascent           944  ->   925
  hhea.descent         -256  ->  -275
  hhea.lineGap            0  ->     0   (unchanged)
  OS/2.sTypoAscender    787  ->   925
  OS/2.sTypoDescender  -213  ->  -275
  OS/2.sTypoLineGap     200  ->     0
  OS/2.usWinAscent      944  ->   883
  OS/2.usWinDescent     256  ->   231

Why
---

Every renderer centres a line of text by its line box, so where a font's ink sits
inside that box is the font's decision, not the app's. This font's box centre sat
0.019 em above its own capital letters - the smallest offset of the six faces
corrected in this pass, but nonzero and the same underlying cause, so it is
normalized here for consistency rather than left as the one exception with a
different rule.

The correction centres the box on the font's flat capital letters - E, F, H, I, L -
rather than on the raw digit ink, because this font's numerals are old-style (text)
figures: 3, 4, 5, 7 and 9 dip below the baseline by design, while 0, 1, 2, 6, 8 do
not. Averaging over all ten digits would pull the box down to fit the five that are
meant to hang low; centring on the flat caps leaves the old-style figures to extend
below the box exactly as designed, the same way ordinary descenders do in any face.

Upstream carried two different totals for hhea (944+256=1200) and for
typo+lineGap (787+213+200=1200): the same total line advance, reached two
different ways. That split is collapsed here - typo now equals hhea exactly, with
lineGap zero on both - so a renderer honouring either table places the line
identically, which upstream's own numbers already intended but expressed
inconsistently. The total is unchanged (1200 units in this font's 1000-unit em);
only where the ink sits inside the box moves. The flat-cap band now lands within
0.0001 em of the box centre.

usWinAscent/usWinDescent were narrowed to the font's real ink extents
(head.yMax/yMin), which upstream's values exceeded.

Pinned by BundledFontMetricsTest, so a re-download from upstream fails the build
rather than silently reverting the fix.
