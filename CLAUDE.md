# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Svartifoss — an Android app that lets a paired Wear OS watch control music playback on the phone (and on the watch itself), with customizable physical buttons / digital crown / gestures. **Sideload-only**: the phone and watch APKs are installed manually from GitHub releases (watch install via Wear Installer). A self-hosted F-Droid repo used to be served from GitHub Pages under `docs/fdroid/`; it was retired in 3.1-beta2 having fallen three versions behind, and GitHub releases are now the single distribution channel — don't reintroduce it without being asked. `fastlane/` at the repo root still holds store-listing metadata (descriptions, screenshots) in the Fastlane layout, now only of use to a future store attempt. It is *not* on the Play Store — a split free-phone-app / paid-watch-app listing was drafted (see `docs/play-console-*.md`) but the author shelved it, not a store enforcement action. A future Play Store attempt is more likely to be a single listing with in-app premium unlocks (Play Billing) than the old split-app model. Both APKs must still share the same `applicationId` and signing key (see "Package naming gotchas" below).

## Module layout

This is a multi-module Gradle (Groovy DSL) Android project, configured in `settings.gradle` / `build.gradle` / `libs.toml` (version catalog):

- `mobile/` — the phone app. Reads the currently playing media session, executes actions (play/pause/skip/volume/Tasker tasks/open other apps), and syncs config/state to the watch over the Wearable Data Layer API. Uses **Dagger 2** (`di/AppComponent.kt`, manual `dagger-android` injection) for DI.
- `wear/` — the watch app. Renders the on-watch UI (now-playing screen, action menu, volume bar), receives button/crown/gesture input, and talks to the phone. Uses **Hilt** for DI (different DI framework than `mobile/` — don't assume Dagger conventions carry over).
- `common/` — shared code linked into both `mobile` and `wear`: communication path constants (`CommPaths.kt`), action/button-config models, protobuf schemas (`src/main/proto/*.proto` — actions, music, watch, notifications, custom lists), shared views/drawables.
- `wearutils/` — a **git submodule** (https://github.com/gabrielluizone/WearUtils, this repo's fork of matejdro/WearUtils) with its own `libs.toml`. If this directory is empty, run `git submodule update --init` before building — Android Studio/Gradle sync will fail otherwise.

Root directories that are *not* part of the build: `icons/` (tracked; raw Material Symbols SVG downloads used as source material when adding drawables), `archived/` (parked scraps), `licenses/` (tracked; per-font license texts for the bundled typefaces), `wearmediatemplate/` (Google's Wear OS media-controls design guidance — screenshots plus `media-expressive.md` — kept as reference material for face styling), and the gitignored local reference folders `retromusic/`, `echo/` (a full local checkout of the Echo Music source — one of the three players `docs/player-integration-notes.md` documents from source, so read it there rather than guessing) and `redesign/`. Several stray build outputs / scratch files also sit at the repo root and are **not** build inputs (`full.apk`, `part.apk`, `mobile-debug.apk`, a bundled `com.google.android.wearable.media.sessions_*.apk`, `svartifoss_config.json`, `run.md`, `promp.txt`, `CHANGELOG.pdf`, `RELEASE_3.md` (a drafted GitHub release announcement, not shipping docs), assorted screenshot `*.png` scratch files, the gitignored `.playwright-mcp/` capture dir) — ignore them.

Three root paths are *not* Gradle inputs but **are** shipping infrastructure, so don't mistake them for scraps: `firestore.rules` + `firebase.json` (the deployed Firestore security boundary) and `firebase/` (its emulator-backed Node test suite, `node_modules` gitignored), plus `.github/community-theme-publisher/` (the trusted publisher run by the one workflow) — all three belong to *Community themes* below. `mobile/google-services.json` is **gitignored and required**: the `com.google.gms.google-services` plugin is applied in `mobile/build.gradle`, so a fresh clone will not build until that file is supplied. `AGENTS.md` at the root is a short repository guide for other agent tools that defers to this file; if you change module layout or the test/build story here, keep its summary from contradicting this one.

### Phone ⟷ watch communication

All communication goes through the Google Play Services **Wearable Data Layer API** (`MessageClient`/`DataClient`), with paths centralized in `common/.../CommPaths.kt`. Key entry points:
- Phone side: `WatchListenerService` (`WearableListenerService`) receives messages and forwards to `MusicService`; `WatchInfoProvider`/`ButtonConfigTransmitter`/`ActionListTransmitter` push config to the watch.
- Watch side: `PhoneConnection`, `WatchMusicService`, `PreferencesReceiver`, `IdleMessageListener` handle the corresponding receiving/sending logic.
- Communication is bidirectional. The watch reports *back* to the phone with `WatchInfoSender` (`watch/communication/WatchInfoSender.kt`), which sends the watch's own button hardware capabilities as a `WatchInfo` (from `watch.proto`) so the phone knows which physical buttons exist. (Note the phone-side `WatchInfoProvider` is a different thing — it *pushes* config to the watch.)
- Payloads for structured data (action lists, button configs, watch info) are serialized with **protobuf** using the schemas in `common/src/main/proto/`.
- Watch-facing settings are declared in `common/.../MiscPreferences.kt`, edited in the phone's settings UI, and synced phone → watch (received by `PreferencesReceiver`). Add new watch-behavior toggles there, not in watch-local prefs. Phone→watch delivery is owned process-wide by `mobile/.../WatchPreferenceSyncCoordinator.kt` (started in `WearMusicCenter.onCreate`): it listens for default-SharedPreferences changes, coalesces them in a bounded 120 ms window, pushes through independent conflated message/DataItem workers with exponential-backoff retry for durable writes, and re-publishes once per process start to repair a stale watch — don't add per-screen push listeners (fragment-lifecycle listeners stranding edits is exactly the bug it replaced). It only syncs keys in `MiscPreferences.EXPORTABLE` (plus the `WEAR_DEV_*` diagnostics keys), so a new watch-facing preference must be added to `EXPORTABLE` to reach the watch at all. Delivery is **two transports for one payload**, not a choice between them: the `/Settings` DataItem stays the durable source of truth (survives watch reboot/process death, and owns key *removals* via its inventory logic), while the same snapshot also goes out over `MessageClient` (`CommPaths.MESSAGE_APPLY_PREFERENCES`, encoded by `common/.../WatchPreferenceMessage.kt`, received by `wear/.../PreferenceMessageReceiver.kt`) because DataItems are eventually-consistent and under doze don't land until the watch next wakes — that lag was the "setting only applies after I tap the watch" bug. Both transports carry the same persisted phone sequence (`WatchPreferenceSyncProtocol.SEQUENCE_KEY`, also in the v1 message values); one watch-side `WatchPreferenceReceiver`/`PreferenceSnapshotReconciler` orders them together so a delayed older DataItem or message cannot clobber a newer snapshot, and applies *additively* (never deletes), so a dropped message can't remove a preference. Two rules keep that pair honest, and both were learned from the same failure — a watch frozen on the last values it managed to receive, showing an old theme in an old language while the phone's settings screen looked entirely correct. **One snapshot feeds both transports, and both filter on `shouldSyncWatchPreference`.** `PreferencePusher` takes a `SharedPreferences` and reads `all` from it, so the DataItem used to carry the phone's *entire* default preference file — the saved streaming shortcuts, the search history and the track history all live there as JSON blobs, as does every phone-only setting — none of which the watch reads, all of it spending the same 100 KB per-item budget the watch-facing keys need. `SnapshotPreferences` (a read-only view inside the coordinator) hands the pusher exactly the filtered map the message already used. **The message and DataItem run independently, each serial with only the latest pending snapshot.** The message used to run after a successful put, so one rejected put took the whole channel down: the retry re-sends the identical payload, which means a snapshot the Data Layer refuses fails forever while the message that would still have worked was never reached. **And what travels is one appearance scope, not twenty-two.** Face scoping multiplies each of the ~179 scoped keys by twenty-one built-in faces plus `custom_active` — about 310 KB fully materialized, roughly three times the transport's own cap — while the watch reads *exactly one* of those scopes: every watch-side read (player, AOD, panels, tile, queue, menu, picker) resolves through `ThemeAppearance.resolve(prefs)`, and nothing on that side ever constructs a scoped key for another face. Sending all of them therefore spent the budget on values the wrist has no way to reach, and it did so at the expense of the ones it does: a library with four or five customized faces sat at the guard, which surfaced as a *community theme* refusing to install (`WatchSyncTooLarge` → "your watch settings are too large") and as an instruction to delete your own work. `selectWatchPreferenceSnapshot` (pure, JVM-tested, in the coordinator) now splits the map in two. The unscoped behaviour keys and the **active** scope are mandatory and never measured against a budget — whatever is on the wrist is always transmitted whole, however large the library has grown, which is what makes the install ceiling unreachable rather than merely further away. Every other scope is a *cache*, useful only in the moment between picking a different face on the wrist and the phone publishing that face's scope back, so those are packed in a fixed order (`ALLOWED_BASE_FACES`, then unrecognised scopes, then a *stale* `custom_active` last — once a theme is inactive its snapshot is the one group nothing can read) while `WATCH_SNAPSHOT_SCOPE_BUDGET_BYTES` lasts, and skipped after. A skipped scope costs a fraction of a second of default styling on a face changed from the watch and repairs itself, because `MESSAGE_SET_SCREEN_FACE` makes the phone write that face and re-publish, at which point it *is* the mandatory scope. Two consequences to keep straight. `WatchThemeRepository.fitsWatchSyncSnapshot` must project through this selector with `CUSTOM_SCOPE` as the active scope — measuring the raw preference file is what made one theme refusable on behalf of twenty faces, and asking about the *current* scope would measure the face the install is about to switch away from. And `estimateWatchPreferenceSnapshotBytes` counts `Set<String>` members: the auto-start blacklist is the one set in `EXPORTABLE` and grows with the packages a user picks, so counting it as zero understated precisely the entry a heavy user is most likely to have made large. The former "Apply this look to all faces" shortcut made the growth immediate by writing every key onto all twenty faces and was removed along with that destructive bulk action. `warnIfSnapshotIsOversized` still logs once as the payload approaches the limit — reaching it now means the mandatory half alone is near the cap — and `reportDroppedScopes` logs which inactive scopes were left behind, because the only visible symptom would otherwise have nothing anywhere naming a cause.
- **Synchronization ordering:** the shared preference receiver commits changed values, sequence and ownership inventory atomically and posts `PreferencesBus` only when values change. A message remains additive, but records ownership of introduced keys; its matching DataItem must still reconcile removals even at the same sequence. Once a marked snapshot arrives, legacy snapshots cannot overwrite it. Startup and Developer “Sync watch settings” use the same coordinator, selector and transports; do not call `PreferencePusher` directly from UI. `ConfigSyncQueue` similarly owns commits, icon refreshes and startup repairs for each action/button config, coalescing requests without losing pending disk saves. Never cancel an already-submitted Data Layer put and then start its replacement: cancellation of `await()` does not retract that Task. Music snapshots reuse one sequence across the immediate message and both durable artwork phases; obsolete preparation can be cancelled, while submitted puts finish under a mutex. Watch asset publication rechecks the music sequence after suspension, and `MusicAssetOrder` prevents a delayed interim phase from cancelling the completed phase of that same revision. Config decoders cancel obsolete jobs and keep existing assignments until a complete replacement is ready. See `docs/communication-latency.md` for evidence, tests and device validation limits.
- **Watch command dispatch:** `WatchCommandDelivery` joins the manifest listener and the running music service through a process-owned `WatchCommandInbox`. The manifest listener preserves the first command while starting the service; the inbox drains only after the service reaches STARTED and its media-session observer is active. A running service consumes immediately without another foreground-service start. Duplicate deliveries are identified by source node and MessageEvent request ID, never payload: repeated skips/toggles remain separate actions. Failed/aborted startup clears pending commands rather than replaying them on a later launch.
- Structured notifications reach the watch via `notifications.proto`, `CommPaths.DATA_NOTIFICATION` (`/Notification`), decoded into `watch/model/Notification.kt`.
- **Media notification actions:** the phone mirrors the active media notification's action buttons to the watch as `MediaAction` entries inside `music.proto`'s `MusicState` (label + rasterized PNG icon + a locale-independent `semantic` hint). `PendingIntent`s can't cross the Data Layer, so `mobile/.../notifications/MediaNotificationActions.kt` is a process-local registry: it keeps the `PendingIntent` on the phone, sends an opaque id to the watch, and resolves the id back when the watch taps the action (the `semantic` field is presentation-only, never an execution token). `MediaActionIdentity.kt` classifies action semantics. The same listener also feeds `mobile/.../notifications/AppGlyphStore.kt`, a **persistent** package→PNG cache of each media app's notification small icon. It has to be persistent rather than read live out of `MediaNotificationActions`: that registry holds what is posted *now*, while the rows that want a glyph are launcher rows ("Play YouTube Music"), and the whole reason to tap one is that the app is not playing — so the notification is exactly what does not exist at that moment. Reading live would have shown the glyph only for apps the user did not need to launch. `AppPlayAction`/`PlayPlaylistShortcutAction`'s app-icon fallback prefer it over `getApplicationIcon`, and `MusicService`'s source icon falls back to it before the launcher icon (a cold start would otherwise show a full-colour icon on Split's seam for the first track and the glyph from the second on). A caller that takes the glyph **must** also report `iconTintable = true` — the bytes are a flat-white template on transparency, so untinted on a light surface it is an invisible white shape; that is why `PlayPlaylistShortcutAction` carries image and tintability together in one `AppMark` rather than deciding them in two independent getters. **Action icons are rasterized at transmit time**, so learning a glyph does not by itself update anything already on the watch — the store therefore keeps a persisted generation counter and `MusicService` re-sends the action list and both button configs (`ActionList.retransmit`/`ButtonConfig.retransmit`, which push without a disk write, since a notification arriving in the background has no business rewriting the user's config file). Both halves are needed: the live listener covers a glyph learned while the service is up, and `needsRetransmit` at startup covers the ordinary case where it was learned while the service was stopped — without it the bytes are already on disk next launch, `remember` takes its "nothing changed" branch, and the launcher icon stays on the watch permanently. These feed the watch's quick-actions panel; MediaSession custom actions are the fallback when no notification actions exist.
- **Service lifetime / the persistent notification:** `MusicService` is a foreground service, and `promoteToForeground()` must answer **every** `startForegroundService()` aimed at it (see its own comment) — so it runs at the top of `onStartCommand` before any branch, including the ones that immediately stop. Its notification carries "Stop" (`ACTION_STOP_SELF`) and "Force stop" (`ACTION_FORCE_STOP`); the latter unbinds the notification listener and then kills the process outright. Because that is deliberately *not* an orderly shutdown, two things cannot be left implicit: the notification is taken down explicitly (`removeServiceNotifications()`, also called from `onDestroy` for the ordinary path) rather than relying on service teardown, which may never run before the kill and left "Music control active" stranded in the shade; and the listener unbind calls `NotificationService.requestUnbindNow()` — which reaches the connected listener instance directly, since it is in this same process — falling back to the `ACTION_UNBIND_SERVICE` `startService` message only when none is connected, because the process may die before it can deliver anything to itself. If the unbind is missed the system rebinds the listener, revives the process, and `onListenerConnected` starts `MusicService` again, posting the notification right back. Note what `requestUnbindNow` deliberately does **not** use: `NotificationListenerService.requestUnbind(ComponentName)`, the static overload, exists only from **API 35** while the instance method has been there since 24 — it is present in `compileSdk 36`'s `android.jar`, so calling it compiles cleanly and then throws `NoSuchMethodError` at runtime on every older device. That trap is general here: `compileSdk` is 36 against `minSdk` 23, and with `lint` unusable as a gate (see *Build & test commands*) nothing catches a too-new API but the device itself — so check the actual `@since` of any framework method that isn't obviously ancient, rather than trusting that it resolved. Both actions also notify the **watch** (`CommPaths.MESSAGE_STOP_WATCH_APP` / `MESSAGE_FORCE_STOP_WATCH_APP`, handled by `IdleMessageListener` → `watch/communication/WatchAppShutdown.kt`), since the watch is a separate app on a separate device that nothing else would ever tell — it used to keep its ongoing-activity chip and `WatchMediaSession` proxy pointed at a service that no longer existed. Two constraints there. The send must **not** run on `lifecycleScope`: both callers `stopSelf()` immediately after, and that scope is cancelled at `onDestroy` milliseconds later, which cancelled the very send — hence the process-scoped `SHUTDOWN_SCOPE`. And Force stop waits for the send to complete before killing, with an unconditional `FORCE_STOP_KILL_MAX_DELAY_MS` backstop, because a fixed short delay regularly lost the Bluetooth hand-off while an unbounded wait would make Force stop do nothing when no watch is reachable. On the watch side `WatchAppShutdown` is a plain listener list, deliberately not a `LiveData`: a singleton `LiveData` replays its last value and would close the app again on next open, and `SingleLiveEvent` only trades that for holding the event until an observer is STARTED — i.e. closing the app in the user's face when they next bring it up. `removeServiceNotifications` deliberately spares `NOTIFICATION_ID_SERVICE_ERROR` — that one is not a status readout but the standing prompt to grant notification access, and this service stopping is the normal *consequence* of not having it, so clearing it would delete the only route back to the setting.
- **Logging / diagnostics:** the phone runs **Timber + Firebase Crashlytics** (`mobile/.../logging/TimberCrashlytics.kt`, `CrashlyticsExceptionWearHandler.kt`); the watch forwards its own logs on request via `MusicCenterLogRequestReceiver` (extends `WearLogRequestReceiver` from `wearutils`) over `CommPaths.MESSAGE_SEND_LOGS` (`/SendLogs`) + `CHANNEL_LOGS` (`/Channel/Logs`), so a watch-side crash surfaces in the phone's Crashlytics. Firebase Crashlytics and (since 2.2.1) Firebase Analytics are both active — keep the Data Safety / privacy docs consistent with that. Crash reporting is user-optional: `mobile/.../logging/CrashReporting.kt` centralizes the opt-out (Settings → Data & support → Privacy) — Crashlytics auto-upload stays disabled and finalized reports are sent manually only after the current privacy choice has been read; opting out also deletes queued unsent reports.
- **Developer announcements** also ride Firebase, but as push rather than diagnostics: `mobile/.../notifications/AnnouncementNotifications.kt` mirrors `CrashReporting`'s single-gate shape, subscribing/unsubscribing the device to one fixed FCM topic (`"announcements"`) as `MiscPreferences.ANNOUNCEMENTS_ENABLED` (Settings → Data & support → Privacy, on by default) changes — there is no backend, so a Firebase Console campaign targeting that topic is the entire delivery mechanism, and the app never holds a token/user list itself. `AnnouncementMessagingService` (manifest-registered `FirebaseMessagingService`) renders the received message as a notification.

### Watch-side data flow

`PhoneConnection` (Hilt `@Singleton`) listens to `DataClient` updates and exposes `LiveData` properties (`musicState`, `rawPlaybackConfig`, `rawStoppedConfig`, `customList`, etc.). The two separate configs — playing vs. stopped — let users assign different button actions depending on whether music is currently playing.

`MusicViewModel` (`@HiltViewModel`) consumes `PhoneConnection` LiveData and drives `MainActivity`. It owns `WatchActionConfigProvider` (one for each config) which decodes protobuf action configs from the phone into `ButtonAction` objects keyed by `ButtonInfo`.

`WatchMusicService` is a foreground `LifecycleService` that keeps `PhoneConnection` active. Why it is staying alive is decided by the pure `resolveServiceHold(uiOpen, musicPlaying, hasTrack)` (top of the same file, tested by `ServiceHoldTest`), which has **three** states, not two: `ACTIVE` (UI open or music playing), `PAUSED_TRACK`, and `IDLE`. The middle one exists because the app is only reachable from the watch face while this service is up — it carries the ongoing-activity chip and the proxy `WatchMediaSession` — so tearing it down on the short idle timer meant an ordinary pause evicted the app and getting back to a paused track cost a trip through the launcher. How long a paused track holds is a user choice decoded by `common/.../PausedHoldPolicy.kt` (`MiscPreferences.WEAR_PAUSED_HOLD`, default 30 minutes; `"always"`/negative → `FOREVER`, `0` → no hold, anything unparseable → the default rather than `NO_HOLD`, so a corrupt value can't silently restore the bug). Every full-screen watch activity (now-playing, queue, menu) binds a `UiOpenServiceConnection` to hold the service while it's in the foreground — the Compose windows are opaque, so `MainActivity` underneath them gets stopped and can't be the one keeping the service alive.

`WatchMediaSession` (`watch/communication/WatchMediaSession.kt`) is a `MediaSessionCompat` proxy: it mirrors phone playback state (metadata, playback state, album art, volume) received from `PhoneConnection`, and forwards transport controls (play/pause toggle, skip, seek, volume) back to the phone over the Data Layer. It is owned and lifecycle-managed by `WatchMusicService`. This is the architectural keystone that enables Wear OS system media surfaces, Tiles, and Complications to see and control the phone's music.

**On-watch face picker** (`wear/.../view/facepicker/`): long-pressing the centre of the player opens `FacePickerActivity`, so a face can be changed from the wrist. Three things about it are deliberate. It is **its own Activity**, not an overlay in `MainActivity` — that is what makes the right-swipe close the *picker* back to the player (via `SwipeToDismissBox`, as the queue and menu do) instead of exiting the app. It is a **vertical** list rather than a horizontal gallery like the system's watch-face picker, because a left-to-right drag *is* the Wear OS dismiss gesture and a horizontal pager would have to fight it for every swipe. And the choice is **written locally *and* sent to the phone** (`CommPaths.MESSAGE_SET_SCREEN_FACE` → `MusicService.applyScreenFaceFromWatch`): the local write is what applies it instantly, but preferences are phone-owned and `WatchPreferenceSyncCoordinator` re-publishes the whole snapshot once per process start, so a watch-only write would be silently reverted. The local write must also `PreferencesBus.postValue(prefs)` — `MainActivity` re-reads its appearance only when that bus emits and does *not* reload in `onStart`, so without it the player keeps rendering the old face. The picker lists the user's **saved custom themes** alongside the built-in faces, so the payload has two forms: a bare face key, or `custom:<themeId>`. `WatchThemeRepository` publishes the library to the watch as a JSON id/name/baseFace array in `MiscPreferences.WEAR_AVAILABLE_CUSTOM_THEMES` (a synced pref, not a DataItem — the profile *contents* stay phone-local), which `WatchFaceCatalog.optionsFor(currentFace, customThemesJson)` merges with `ALLOWED_BASE_FACES` minus `ArchivedFaces.KEYS`; so a repository change that doesn't rewrite that key leaves the wrist picker showing a stale list. `applyScreenFaceFromWatch` routes the two forms differently, and must: a `custom:` id goes through `WatchThemeRepository.applyProfile`, which materializes the whole snapshot, while a bare face key is written directly and **clears** any active custom theme, for the reason `ConfigBackup.import` does the same — a custom theme owns its own base layout, so a bare `wear_screen_face` write landing underneath one rewrites a saved profile rather than switching away from it. The local-write half therefore cannot apply a theme at all: `normalizeBaseFace` rejects a `custom:`-prefixed value, so writing the payload straight into `wear_screen_face` resolved to `classic` and picking your own theme visibly switched the watch to the wrong face. `FacePickerActivity.applyFace` writes the option's **base face** locally instead (the one part of a theme the watch can honestly render alone) and lets the phone deliver the snapshot; picking a *built-in* face additionally clears `WEAR_ACTIVE_CUSTOM_THEME_ID`/`_COMPLETE` locally, mirroring `applyScreenFaceFromWatch`, because otherwise `resolve()` keeps returning the active `Custom` context and the pick appears to do nothing. `WEAR_AVAILABLE_CUSTOM_THEMES` is also republished once per process start from `WearMusicCenter` (`WatchThemeRepository.publishAvailableThemes`): only `saveState` wrote it, so a library built before the key existed never reached the watch at all — the same class of staleness the preference snapshot re-publish exists for. Ordering is by recency first, then registry order: `watch/.../view/facepicker/FaceRecency.kt` (pure over a plain map, JVM-tested) records last-used timestamps **watch-locally** — never in `MiscPreferences.EXPORTABLE`, both because which faces this wrist uses is not a property of the theme and because the preference sync only deletes keys a previous phone snapshot declared phone-owned, so a key the phone has never heard of survives every sync; adding them would put a Bluetooth write on every face change for no benefit. Saved custom themes sort ahead of built-ins. Rows carry the shared palette glyph, deliberately: a per-face Canvas miniature was tried and removed — at row size the sketches read as approximations of faces rather than as the faces, which is worse than an honest generic icon. Which gesture does what is `common/.../CenterLongPressAction.kt` (faces/queue/none, pinned by `CenterLongPressActionTest`); anything unset resolves to **faces**. It deliberately does *not* consult the legacy `WEAR_CENTER_LONG_PRESS_QUEUE` boolean — it briefly did, on the reasoning that an install which opted into long-press-for-queue should keep it, but that boolean is off by default so for almost everyone it only kept the gesture inert, and for the few who had set it the result was the queue opening where they were reaching for the picker. The queue has other routes; an on-watch face change had none. `WearMusicCenter.repairCenterLongPressPreference` is the one-shot that undoes the short-lived migration which had written `"queue"` through, narrowed to exactly that state so a later deliberate choice is never reverted.

### Playback position on the watch

The watch is told the position only when something *else* changes — `MusicService` deliberately suppresses position-only retransmissions (`equalsIgnoringTime`), which is right (constant Bluetooth traffic to say nothing) but means that for most of a track the watch is not reading a position, it is **predicting** one. The progress ring, the track time and the synced-lyrics screen all ride on that prediction, and the lyrics screen is what turns a one-second error from invisible into obvious.

**Never subtract one device's clock from the other's.** This is the rule the whole subsystem exists to enforce. The original design sent the sample time as a phone epoch timestamp and had the watch subtract it from its own `System.currentTimeMillis()` — correct only if the two wall clocks agree, and Wear OS syncs a watch's clock from its phone with tolerance, not exactly. Whatever they differed by became a fixed offset on every predicted position for a whole track, which produced two symptoms that look unrelated: lyrics consistently ahead of or behind the song, and a visible step on every pause/resume (a paused state predicts nothing, so only the playing one carried the skew). The fix is `MusicState.positionAgeMs` (and the same field on `PlaybackSync`) — a **duration**, how stale the sample already was when the phone built the payload, measured entirely with the phone's own clock; the watch adds however long it has held the payload, measured entirely with its own `elapsedRealtime`. `positionUpdateTime` is still sent for old watch builds, and `-1` on `positionAgeMs` makes a new watch fall back to the old subtraction for old phone builds. `common/.../PlaybackPositionEstimate.kt` owns the arithmetic (JVM-tested; never returns negative — the legacy path could, which ran the lyric backwards past the start of the track).

Four pieces sit on top of that:

- **One anchor, not three** — `wear/.../communication/PlaybackClock.kt`. The position used to be derived independently in the player ViewModel, the lyrics ViewModel and the media-session proxy, each re-extrapolating from `PhoneConnection.musicStateArrivalRealtimeMs` and none of them ever corrected. That is why the lyrics screen appeared to sync when opened and never again — the open *was* the resync, because a fresh observer replayed the last state and re-anchored on it. `PlaybackClock` holds the single anchor, updated from a `MusicState`, from a local event (seek, optimistic play/pause, predicted advance — position known *now*, zero staleness), or from a sync reply. Deliberately not thread-safe: everything touching it is on the main thread, and synchronizing would only hide a caller that wandered off.
- **Correction over a round trip** — `CommPaths.MESSAGE_REQUEST_PLAYBACK_SYNC` / `MESSAGE_PLAYBACK_SYNC` (`PlaybackSync` in `music.proto`). `positionAgeMs` measures staleness at the *sender*, so the one leg it cannot describe is the flight between devices. The watch stamps a request with its own monotonic clock, the phone echoes that token back untouched (so no clock is ever compared across devices), and the watch halves the measured round trip. `common/.../PlaybackSyncPolicy.kt` (pure, JVM-tested) holds the three rules: throw the sample away when the round trip is too long for the symmetry assumption; below `IGNORE_THRESHOLD_MS` do nothing, between there and `STEP_THRESHOLD_MS` apply a fraction so successive checks converge invisibly, past it snap (a visibly wrong line should not be eased into place); and back off the interval each time a check finds nothing, dropping to the floor the moment one does.
- **Two transports for the state itself** — `CommPaths.MESSAGE_MUSIC_STATE` sends the same `MusicState` as `DATA_MUSIC_STATE` over `MessageClient`, the shape `MESSAGE_APPLY_PREFERENCES` already uses beside `/Settings`. The DataItem stays the durable source of truth and carries the album-art/source-icon **assets**; the message carries none (a message cannot hold them) and exists because the replication layer's latency was not merely cosmetic — it put a lasting offset on the predicted position. Whichever arrives first is applied and the other is discarded by content.
- **Predicting the track boundary** — `wear/.../view/PredictedTrackAdvance.kt` (pure, JVM-tested). When the watch already holds the queue and the current track has run its full duration, the next entry is knowable before the phone says so, which removes the worst-felt latency in the app (players routinely drop out of the playing state at a boundary, so `onMetadataChanged` is late, and the cover then travels as the slowest Data Layer asset). It is **a prediction, never a second source of truth** — a real state is applied verbatim the moment it arrives, agreeing or not (`MusicViewModel.resolvePrediction`) — so every rule in it refuses to predict rather than guessing (shuffle, repeat-one, an implausible duration): a refused prediction costs only today's latency, a wrong one shows a track that is not playing.

### Watch input handling

`MainActivity` handles seven input categories:

1. **Screen gestures** — `FourWayTouchLayout` (from `common/`) divides the screen into quadrants; taps in each quadrant are reported as a `ScreenQuadrant` gesture mapped through button config.
2. **Full-screen swipes** — up/down/left swipes on the now-playing screen are pseudo-buttons (`SwipeGesture` in `common/`, buttonCodes chosen outside the quadrant range) flowing through the same `ButtonInfo`/config pipeline as quadrant taps. Right swipe is deliberately never intercepted — it's the system-wide Wear OS dismiss gesture. UI above `FourWayTouchLayout` needs a dispatch boundary: `ClaimedGestureHost` surrounds both the Compose face and the shared Android mini buttons, observes only streams a child actually claimed, and mirrors them into `MainActivity`'s detector without consuming them; a rejected DOWN still falls through to `FourWayTouchLayout`. Do not replace this with an `OnTouchListener` on the outer `ComposeView` — its internal `AndroidComposeView` receives a `pointerInput`/`clickable` stream before that listener and silently creates dead swipe regions over face content. Swipe recognition intentionally has no drawn finger-path/trail; feedback comes from the configured action and haptics.
3. **Physical stem buttons** — `StemButtonsManager` (`wear/.../view/StemButtonsManager.kt`) translates raw `KeyEvent` sequences into single-tap, double-tap, or long-press gestures per configured button. Includes an ambient-mode phantom-click workaround.
4. **Rotary encoder / digital crown** — handled via `RotaryEncoderHelper` directly in `MainActivity`. On devices with discrete rotary input, crown turns are simulated as button presses (`SpecialButtonCodes.TURN_ROTARY_CW/CCW`) through `StemButtonsManager`, so they're user-configurable like any button. Otherwise, continuous scroll deltas do whatever `common/.../RotaryAction.kt` resolves — volume / seek / **off** (`MiscPreferences.WEAR_ROTARY_ACTION`, falling back to the legacy `ROTARY_SEEK` boolean when the three-way key was never written) — subject to a configurable deadzone and sensitivity. `OFF` exists and is *swallowed* rather than passed on because rotary input is not only the crown: every non-Classic Galaxy Watch reports a finger circling the **touch bezel** as rotary scroll, which is physically the same gesture as an edge-seek drag on the progress ring. For the same reason `MainActivity` drops rotary events outright while `binding.seekBar.isSeekDragging` — otherwise an edge-seek drag popped the volume overlay open and the seek never happened.
5. **On-screen mini buttons** — up to three *visible* configurable buttons (`ScreenButtons` in `common/`, codes 7–9, tap + long-press) rendered as a fixed overlay near the bottom of the now-playing screen (except on a face that hosts them inside its own composition — see `MiniButtonPlacement.isHostedByFace` and Chat below); ordered after `center_tap_zone` in the layout so they win touch dispatch over the center play/pause zone and `FourWayTouchLayout`. Where the row rests is decided by the watch and is not a preference: it sits at the lowest margin that keeps the whole row inside a round display and lifts only as far as it must to clear the track text. `MiscPreferences.WEAR_SCREEN_BUTTONS_OFFSET` is **retired** - nothing reads it and it has no settings row - but it must not be deleted, because published community themes already carry the key and `parsePublishedSettings` rejects a whole profile on a key it does not recognise; see its own note in `MiscPreferences`. Where and how the row sits is `common/.../MiniButtonPlacement.kt`, decoded from `screen_buttons_curve_style`: what began as a pure bezel-curve amount (flat → curved/curved_extreme) gained a second, orthogonal axis whose values relocate the row entirely — `spread` (bottom row, pushed to the screen edges) or a rail down `side_left`/`side_right`/`side_split` (split rail: first configured button left, the rest right) — rather than only bending it, because to a user "how are the mini buttons arranged" is one question, not two pickers. Consumed identically by wear `MainActivity` and `WatchPreviewView`, the usual shared-resolver pattern so the preview can't show a bottom row while the wrist shows a side rail. Their *colour* is the sibling resolver `common/.../MiniButtonSurfaces.kt` — `resolve(style, palette)` is the pure, JVM-tested decision table for `screen_buttons_bg_style` and `paletteFor` derives the expressive/glow tones every caller must agree on. It has three consumers now (the View row's `styleScreenButton`, the Chat face's Compose circles, `WatchPreviewView`), and the two that predated it had already drifted: the preview stroked `glow_exp` with the un-lifted tone and chose its icon colour on a naive luminance split where the watch used the WCAG crossover. `FOLLOW_FACE` (`"glass"`, the default) is the one value that resolves to *no* colour — `followsFaceNeutral`, meaning the drawing surface supplies its own neutral skin, which is what lets Chat keep its accent circle until a style is picked.
6. **Quick actions panel** — an overlay opened by double-tapping the center of the now-playing screen (rendered in `MainActivity`): three round configurable slots plus a full-width row (`QuickPanelButtons` in `common/`, codes 10–13, continuing the pseudo-button range). Unconfigured slots now default to mirroring the current media notification's *real* actions (labels + icons, executed on the phone via `MediaNotificationActions` — see the communication section), with MediaSession custom actions as fallback and the older Like / Shuffle / Repeat + "Up Next" queue-preview row behind that; a `NullAction` assignment hides a slot. The phone writes quick-panel assignments into *both* the playing and stopped configs so the panel behaves the same regardless of playback state.
7. **One-handed hand gesture** — Wear OS's semantic *primary action*, which is a double pinch on the Pixel Watches that currently support it (`DoublePinchGesture` in `common/`, code 15, continuing the pseudo-button range; `wear/.../input/DoublePinchGestureController.kt` owns the subscription). It is the one input here that a watch can simply not have: the wear-sdk `GestureInputManager` arrived in API **36.1**, the hardware has to report `ACTION_PRIMARY` as supported, and the user has to have the gesture switched on in the watch's own settings — so the phone keeps its row last on the Controls screen rather than among the inputs every watch has. Two things about the subscription. It is registered only while the *active* config has an assignment, and against `binding.root`'s **window** — which is why registration waits for that view to be attached: `setEnabled` is driven by a config `LiveData` observer bound to the Activity, so it first runs at `onStart`, and an Activity's decor view only joins the WindowManager after `onResume`. And every failure path logs, because all of them look identical from the wrist (nothing happens) and the watch forwards its log to the phone. That silence is also why the watch *reports* what it can do rather than leaving the phone to offer the row on faith: `DoublePinchGestureController.availability(context)` resolves a `common/.../HandGestureAvailability.kt` (`UNSUPPORTED`/`DISABLED`/`READY`, plus `UNKNOWN` for a probe that threw), `WatchInfoSender` sends it as `WatchInfo.handGesture`, and `ButtonConfigFragment` renders it both as the section's own summary and as the note above the action picker — which is the *only* place the gesture is explained at all, since its name says neither how it is performed nor when it counts. Keep the four cases and "no watch info yet" distinct: a watch that has not been heard from and a watch that has answered "this hardware cannot" are opposite advice, and an absent field (an older watch build) is neither. The wire form is an explicit `code`, not the ordinal, because the two apps update independently. The other half of that is `addEnabledActionsChangeListener`: the fix the phone recommends is a switch in the watch's own Settings, nothing else tells this app it was flipped, and without the watch the subscription would sit there emitting nothing until the player was closed and reopened — so a change re-runs registration and re-publishes `WatchInfo` through `MainActivity.republishWatchCapabilities`.

Resolved actions don't always round-trip to the phone: `MusicViewModel.executeActionOnWatch` intercepts actions that make sense locally (opening the menu/queue, opening search input, volume UI) and only sends the rest to the phone for execution.

### Phone app UI

The phone UI is a single activity (`mobile/.../view/mainactivity/MainActivity.kt`) that swaps fragments via a bottom navigation bar: `WatchFaceFragment` (Watch face — see below), `ControlsFragment` (a ViewPager2 with swipeable "Music playing" / "No playback" tabs, each page a `ButtonConfigFragment` — the two configs are presented as states of one feature, not separate nav destinations), `ActionListFragment`, and `SettingsHomeFragment` (a ViewPager2 of `MiscSettingsFragment` sections: General, Behavior/watch, Automation, Apps, Data & support — `MiscSettingsFragment.SECTION_*` args select a page, and which preference categories from `settings.xml` that page shows is looked up in `view/settings/SettingsCatalog.kt` (see below); service-specific integrations live under Apps — playlist shortcuts (`PlaylistShortcutsActivity`) match a link's source service via `music/StreamingShortcutLinks.kt`'s pure link-detection helper (YouTube Music, Spotify, Deezer, Tidal, Apple Music, Amazon Music, SoundCloud, Qobuz, Bandcamp, Audiomack, Mixcloud, Pandora, or a generic fallback), shared with `MusicService`'s launch-intent resolution — these are link shortcuts, not account/API integrations, so the target streaming app still decides whether playback actually starts — see *Actions system* below for how shortcut launches and the autoplay nudge actually work). The usage guide (`TutorialFragment`) is not a tab: it opens in `HelpActivity` from the toolbar's help button. A left navigation drawer holds only app/about info (version, author), not navigation. The activity also owns cross-fragment chrome: the toolbar (plus the `toolbar_main` options menu), a mini player (driven by a `MediaController` bound to the active media session, with queue and detail dialogs), and a shared FAB whose click is dispatched to the current fragment via the `FabFragment` interface. Missing notification access — without which the app cannot see what is playing at all — interrupts with a dialog **once** (`showNotificationServiceWarning`, gated by the persisted `NOTIFICATION_ACCESS_PROMPTED_PREF`), then persists as a tappable banner row under the toolbar that opens the same dialog (`refreshNotificationAccessBanner`, driven from `onResume` so it clears itself the moment the grant is made). The dialog is dismissible while the condition stays true, so re-showing it every resume — the previous behavior — taxed precisely the user who had read it and chosen to grant it later.

The **Watch tab** (`mobile/.../view/watchface/`) is the visual customization surface for the watch's now-playing screen: `WatchPreviewView` (a Canvas miniature of the watch honoring the same preference keys the watch reads — face, screen theme, album art style/dim, accent color modes, mini-button appearance — with a miniature per face) docked above a nested `WatchFacePrefsFragment` (`res/xml/watch_face_settings.xml`). The preview is **contextual**: `WatchPreviewView` has a `PreviewSurface` enum (player, AOD, volume, seek, quick panel, queue, mini buttons) and `surfaceForPreference()` maps the preference key being edited to the watch surface it affects, so touching e.g. `wear_volume_style` temporarily previews the volume overlay instead of the player. Five of the seven pages are the deliberate exception to the normal one-row-per-Preference presentation — Text, Color, Panel, Player and Background each render one contextual surface (`TypographyEditorPreference`, `ColorEditorPreference`, `PanelEditorPreference`, `PlayerEditorPreference`, `BackgroundEditorPreference`) while their ordinary rows stay inflated and hidden, still owning storage, validation, dialogs and search metadata. Background is the odd one of the five: the other four present a fixed set of controls, one per key, and it presents a *list the user builds* — so its layer rows are inflated by the fragment rather than declared in the layout, and their values live in one encoded preference (see the background stack above) instead of one key each. Six of its legacy rows (`dim_album_art`, the three shading ones, the two accent-floor ones) describe *one particular* layer, so `BackgroundEditorModel.controlFor` resolves all of them to the list and `WatchSearchTargetResolver` deliberately carries **no** prerequisite for them: both gates they used to have now point at rows that are themselves read through that list, and redirecting a user to a control that is no longer on screen is worse than landing them where the setting actually is. The Text page's own exception is the older and more detailed one: `TypographyEditorPreference` renders one Word-like contextual surface, while the seven legacy `cat_wf_typography_*` categories and all 56 of their Preference objects stay inflated but hidden. They remain the authority for scoped storage, validation, font/list dialogs and `SettingsSearchIndex`; `TypographyEditorModel` maps every legacy key to an editor target/control so a search result selects and pulses the corresponding contextual control. Two of its rows share one control — a colour *mode* and the hex behind it — so the model types the hex as `TypographyValueSpec.Hex` and the editor asks for one or the other by kind (`settingKeyFor`/`customColorKeyFor`) rather than taking whichever came first. It used to take the first, which was always the mode: picking **Custom** set a mode whose colour could never be named, since the hex row is hidden here and the mode's `ListPreference` dialog only reports an actual *change*, so re-picking Custom to reach a swatch did nothing either. The swatch is now a second button revealed by that mode, the pairing the Colors page always had. Its other half is that those six hex rows were the only picked colours in the app with no `showLyraColorPickerDialog` wired to them at all — `initAccentColorTarget` covers the nine colour *targets* and these arrived later with the effects — which `CustomColorRowReachabilityTest` now pins for every `HexColorDotPreference` in `watch_face_settings.xml`. Do not delete those hidden XML rows or write around `FaceScopedPreferenceDataStore` from the editor. The miniature shows the phone's *actual* current track when one is playing — `WatchFaceFragment` observes `MainActivity.activeMediaSession()` and feeds art/title/artist into `WatchPreviewView.setNowPlaying()` (Palette-extracts the accent from the real art), a 500ms ticker drives `setPlayback()` so the progress ring/track-time/play-pause state animate live, and `MiniButtonIconLoader` reads the *playing* button-config file off disk (`action_config_playing`, mirroring `DiskButtonConfigStorage`'s format) so the preview's bottom row shows only the mini buttons the user actually configured, with their real icons — all falling back to a built-in sample otherwise. `WatchPreviewView` sizes text to the wear faces' sp values against a 192dp reference watch; keep those (and the cookie/ring geometry) in sync when changing the wear faces. Those appearance preferences were *moved* out of `settings.xml` — the Settings tab keeps behavior-only options — so a watch-appearance preference belongs in `watch_face_settings.xml`, and any new key must also be reflected in `WatchPreviewView.refresh()`/drawing if it changes the screen's look. Shared Lyra preference chrome (HSV color picker dialog, runtime-accent dialog tinting) lives in `view/settings/LyraPreferenceUi.kt`, used by both preference screens. `ResettableNumericEditTextPreference`'s "Reset to default" **applies and dismisses** rather than filling the field in: it must go through `callChangeListener` (plain `setText` persists in silence, so the contextual preview and the dependency wiring are never told), and it cannot reach the field through `getView()` — that is always null on a `PreferenceDialogFragmentCompat`, whose content view belongs to the AlertDialog. Getting either wrong is what made Reset write the default away invisibly and then have OK overwrite it with the stale box contents. A per-face preference that only one layout reads gets an `isVisible` line in `updatePlayerCapabilityVisibility` (`wear_expressive_seek_mode`, `wear_carousel_card_shape`) — a picker offered beside a face that ignores it reads as broken, not as inapplicable. Album-accent → surface-color math (tonal containers, the legacy blur-radius downscale) lives in `common/.../PaletteTransforms.kt` so `WatchPreviewView` and the wear faces/overlays consume the identical functions instead of copies that can drift (same rationale for `common/.../BitmapBlur.kt`, the shared artwork blur — repeated bilinear down/up sampling rather than `RenderEffect`, which is API 31+ and needs a `RenderNode`, so it works on every supported watch and in the phone preview alike); Face geometry is no longer duplicated either: `common/.../FaceGeometry.kt` holds the fractions, proportions and counts a face and its miniature both need (Carousel's rail, Chat's bubbles and waveform, Split's seam and panel, Note's disc, Verse's band, Expressive's cookie/ring, Metadata's row budget), and both sides read it. Only the *drawing* is duplicated, because Compose and `Canvas` genuinely cannot be shared.

**Settings search** (`view/settings/SettingsSearchActivity.kt`, opened from a toolbar action visible only on the Settings/Watch tabs) makes the ~190 preferences across both tabs findable by name instead of by remembering which of the twelve pages holds one. `SettingsCatalog.kt` is the piece that makes this possible without a second source of truth: it holds the section↔category maps for *both* `settings.xml` and `watch_face_settings.xml` (`SETTINGS_SECTIONS`/`SETTINGS_CATEGORIES`, `WATCH_SECTIONS`/`WATCH_CATEGORIES`), read by three consumers — `MiscSettingsFragment`/`WatchFacePrefsFragment` (to hide the categories the current page doesn't want) and `SettingsSearchIndex` (to know which page a result lives on). `SettingsSearchIndex.build()` derives the searchable rows by parsing the preference XML directly rather than from a hand-maintained list, so a new preference is searchable with no second registration to forget, and titles/summaries come out already localized. Matching (`SettingsSearchIndex.rank`, pinned by `SettingsSearchRankingTest`) is a pure function scored by where a term hits (title > category > summary) after accent/case normalization. Picking a result flows back through `MainActivity`: `SettingsSearchActivity` returns (tab, section, preference key) as an activity result, `MainActivity.openSearchResult` stashes it as `pendingSearchTarget` and drives the bottom nav to the right tab, and the bottom-nav listener's `consumeSearchTarget` hands it to `SettingsHomeFragment.newInstance`/`WatchFaceFragment.newInstance` (section) which forward the key one level down to `MiscSettingsFragment`/`WatchFacePrefsFragment`, which scroll the list to it once laid out. The stash-and-consume indirection exists because switching to a tab that's already selected fires no bottom-nav callback, so the direct fragment-swap path and the tab-switch path both have to end up going through the same consumer.

**A result whose row is currently gated by another preference is redirected, not opened.** Conditional rows deliberately stay *in* the index — dropping them would make a feature undiscoverable precisely when the user is searching for how to turn it on — so something has to stand between the index and the page, or search lands on a row that is hidden or greyed out and the search looks broken. That is `view/watchface/WatchSearchTargetResolver.kt` (Watch tab, section + key) and its sibling `view/settings/SettingsSearchTargetResolver.kt` (Settings tab, key only): pure policies whose reads are injected as `readString`/`readBoolean` lambdas, so they stay free of Android *and* of face-scoped storage while each caller still supplies the correct persisted scope. They map a requested key to the prerequisite that gates it — a title/artist typography row to `wear_show_track_title`/`_artist`, a Flex axis row to whichever font key would have to select Flex first, a face-specific row (`wear_split_panel`, `wear_metadata_*`, the mini-button curve on a hosting face) to `wear_screen_face`, `notification_timeout` to `enable_notification_popup` — and set `redirected`, which `WatchFaceFragment`/`SettingsHomeFragment` surface as a `settings_search_prerequisite` toast. Neither ever writes: it points at the switch and lets the user decide. The trap is that these allow-lists **duplicate `WatchFacePrefsFragment`'s own visibility logic** (`updateAodDetailVisibility`, `updatePlayerCapabilityVisibility`) in a second place, and they say so at the site — the two move together or search starts redirecting away from rows that are in fact visible. The AOD list is an explicit allow-list rather than a negation for the same reason `PausedHoldPolicy` has a default: a removed or unknown persisted style (legacy `"minimal"`) then falls on the safe Classic path instead of being treated as a visual face. `SettingsSearchRoutingTest` guards the other half — every row in both XMLs must be reachable from search, with `EXTERNAL_CATEGORIES`/`EXTERNAL_TOP_LEVEL_ROWS`/`NON_SEARCH_ROWS` the narrow, named escape hatches (`typography_editor_surface` is one: a container, not a preference).

Watch-tab **appearance preferences are scoped per face**: `common/.../FaceScopedPreferences.kt` stores each appearance key in its `SCOPED_KEYS` set as `"<baseKey>@<face>"` and resolves reads as explicit per-face value → per-face default → legacy global value → definition default (one carve-out: a *non-default* legacy `wear_album_art_style` value beats the per-face default, because `default_config.json` seeds `cover` on every install so key presence alone isn't user intent). The per-face defaults give album-accent faces "tonal" quick-panel/queue/volume and "expressive" seek surfaces, give each face its matching background via `PlayerBackgroundStyle.defaultForFace()` (`common/.../PlayerBackgroundStyle.kt` — the artwork/background treatment enum, selectable independently of the structural face and rendered on the watch by `watch/view/PlayerBackgroundDrawable.kt`), and deliberately *beat* a pre-scoping global value (that value was never chosen for the face). The Watch-tab preference screens write through `mobile/.../view/settings/FaceScopedPreferenceDataStore.kt` (scoping by the resolved `AppearanceContext`, so edits land in `custom_active` while a theme is active and in `key@<face>` otherwise; its `getBoolean` must consult `perFaceDefault` in *both* branches, the same trap `FaceScopedPreferences.getBoolean` has fallen into twice), the flat SharedPreferences phone→watch sync carries the scoped entries unchanged, and the watch resolves through the same common object — so the settings UI, the preview, and the watch can't disagree. A new watch-appearance preference that should be per-face must be added to `SCOPED_KEYS`; behavior prefs and the face selector itself stay global, and `wear_quick_panel_source` is deliberately unscoped (it drives a phone-side binding with no per-face notion). The `Boolean` read overload must walk the *same* four-step order as the `String` one — it used to skip `perFaceDefault` entirely, which went unnoticed only because no boolean had a per-face default yet, and then silently ignored Carousel's "edge ring and edge seek off".

Scoping arrived in 3.0, so an in-place upgrade from 2.x carries one pre-scoping global value that keeps bleeding into whichever per-face defaults it happens to match — `mobile/.../view/watchface/FaceResetMigrationPrompt.kt` (called once from phone `MainActivity.onCreate`) recommends "Reset all faces to default" exactly once per device. It cannot detect the upgrade from its own preference key (new in the same build that reads it, so a fresh install and an upgrade look identical on the run that matters); it compares `PackageInfo.firstInstallTime` vs `lastUpdateTime` instead. Its reset path is `WatchFacePrefsFragment.resetAllFaces(context, prefs)` — shared with the Watch tab's button, so keep them one function.

**Custom watch themes** layer on top of face scoping: `common/.../ThemeAppearance.kt` decides which appearance context is active — `AppearanceContext.BuiltIn` (the per-face resolution above) or `AppearanceContext.Custom`. The phone keeps a library of up to 24 named profiles in `mobile/.../view/watchface/theme/WatchThemeRepository.kt` (managed in `WatchThemesActivity`, opened from the Watch tab), stored as JSON in a *separate* named SharedPreferences file — deliberately, since the default prefs file is mirrored wholesale to the watch. Applying a profile materializes exactly one complete snapshot into the fixed `custom_active` scope (`"<key>@custom_active"`) plus metadata prefs (`wear_active_custom_theme_id` / `_schema` / `_complete` / `_revision`) in a single default-prefs transaction. Both the watch and the preview resolve through `ThemeAppearance.resolve()`; a Custom context reads *only* the snapshot (never legacy globals or `key@<face>` values) and falls back to the built-in base face whenever the snapshot is incomplete or its schema mismatches — so a partially synced theme can never activate. The snapshot's key set derives from `FaceScopedPreferences.SCOPED_DEFINITIONS` (= `EXPORTABLE` ∩ `SCOPED_KEYS`), so a new scoped appearance preference must be in both registries or profile capture/import will silently drop it.

The redesigned phone theme is internally named **Lyra** (resource names like `dialog_bg_lyra`, `lyra_*` selectors). The accent color can be static, user-picked, or dynamically extracted from album art; `view/LyraAccent.kt` is the single source of truth for resolving the currently displayed accent outside `MainActivity` (standalone dialog activities use it to match what's on screen). AppCompat dialogs inherit their static shell from `LyraAlertDialogTheme`; `view/LyraDialogStyling.kt` supplies the runtime-accent buttons and stock single-choice marks after show, so non-preference dialogs that should match a `ListPreference` reuse that helper rather than inventing another row or Material-dialog treatment. It also walks the decor view for `CompoundButton`s and `EditText`s, because a `setView()` dialog carries controls the AppCompat shell knows nothing about and every one of them draws its selected state from the theme's static `colorControlActivated` — which is how the report-a-theme reasons and the account-deletion choice kept showing sage-green radio marks under a pink accent while their buttons were correctly tinted. The walk is safe precisely because the shell contains neither type (its own choice rows are `CheckedTextView`s, handled separately). The same trap catches any *activity* control inflated from the static theme: `CommunityThemeDetailActivity.applyCommunityAccent` has to name each one, and the report row — a stock `TextButton`, so its label came from `colorPrimary` — was missed for exactly that reason.

### Community themes (the online gallery)

Shipped in 4.0, layered on top of the local theme library above: a user can publish a saved profile and install someone else's. The governing decision — recorded in `docs/online-themes-plan.md` — is that **reading and writing are split**, because they have opposite requirements and merging them is what would make this expensive for a solo developer to run.

- **An author's name is a control, on the card and on the detail screen.** Tapping it narrows the gallery to everything that author published — `OnlineThemeDiscoveryRequest.author`, an **exact** match on the normalized pseudonym rather than a search term, because `discover`'s searchable text also carries every theme *name* and a query for an author called Verse would return the whole Verse catalogue beside their work. It clears the query when it applies, since arriving here is always a tap on a name and a leftover search would silently intersect with it. The detail screen does not open a second gallery: it returns the name as `EXTRA_AUTHOR_FILTER` and finishes, because the gallery *is* the list of an author's work and stacking another copy would make Back land on an unfiltered duplicate of the screen you just left. The chip is labelled with the author's own name — it is the one filter reached by tapping something else, so a fixed word could not say which name it landed on.
- **Browsing needs no account and no live backend.** The approved catalogue is static JSON committed to *this repo* and served from GitHub Pages: `docs/themes/index.json` plus one `docs/themes/<uuid>.json` per theme. `mobile/.../view/watchface/theme/OnlineThemesRepository.kt` is the read-only client — ETag-conditional fetches with a disk cache under `cacheDir`, where a malformed response never replaces a valid cached copy, so an offline phone keeps browsing what it already has. URLs *inside* the catalogue are never trusted; a profile is fetched from the path derived from its id. Search, base-face chips and newest/most-liked ordering are `OnlineThemeDiscovery.kt` — a pure function over the already-downloaded list, JVM-tested — so no keystroke, chip or sort costs a network read, and the whole gallery stays one cached request.
- **Writing goes through Firebase, and the client is never trusted — but only *submitting* costs an identity.** `CommunityThemeGoogleAuthentication.kt` (Credential Manager → Google) is reached from `CommunityThemeSubmissionRepository.kt` alone, and only after someone taps **Sign in and submit**; never hoist it to screen entry. Liking (`CommunityThemeLikeRepository.kt`) deliberately needs **no account**: it provisions an anonymous Firebase UID silently on the first heart tap, so liking, unliking and the private **Liked** filter never prompt. Two things follow that are easy to get wrong. The anonymous UID lives only in local Firebase state, so clearing app data yields a new one and lets the same person vote again — accepted on purpose (a popularity signal, not a ballot), and stated as such in the privacy policy. And signing in to submit **links** Google onto that anonymous account rather than replacing it, so reactions left beforehand survive; the rules therefore accept a linked `google.com` identity *as well as* a non-anonymous `sign_in_provider`, because that claim keeps reporting `"anonymous"` after a link until the account signs in afresh. Anonymous authentication has to be enabled in the Firebase console or every like fails at sign-in rather than at the rules. `firestore.rules` is the actual boundary: an intake document is immutable from every client, an author can read only their own **pending** submission (so a reviewer's UID is never exposed), an allowlisted moderator can make exactly one pending→approved/rejected decision and can never publish, and a create is atomically tied to a private per-user quota document capping **ten submissions per 24-hour period**. That quota is schema **3**: a fixed window (`windowStartedAt` + `windowSubmissionCount`) replacing v2's rolling history, because proving a *rolling* limit needs the timestamp of every submission in it — each extra one costing a stored field and a branch of the progression rule inside the very batch whose expression budget is the trap below. A fixed window costs the same at any allowance and gives up only the boundary, where a burst can straddle two windows. Migration from v2 opens the new window at the oldest submission v2 still remembered, carrying its count, so migrating is never a way to reset the limit. Everything under `themeIntake`/`communityThemeSubmissionQuota` requires `identifiedUser()` and only the like rules accept a bare `signedIn()` — a quota counted in free, disposable anonymous accounts would measure nothing. Likes are one private doc per voter (`communityThemeLikes/<theme>/voters/<uid>`) — no client ever reads a voter list or writes a public counter, which is why displayed totals only move when the publisher next rewrites the catalogue. That is deliberately **not** every run: counts are re-read every time and ride along free whenever a theme is published or withdrawn, but a run where *nothing else* changed defers the rewrite until `LIKE_REFRESH_INTERVAL_MS` (twelve hours) has elapsed, measured from the catalogue's own `generatedAt` so there is no second clock to keep in step. The interval is deliberately **shorter than the gap between cron runs**, so a moved count is published by the next run at the latest; it shipped at a week and at a week it defeated itself — every daily run logged `Like counts moved but are not due for publication` and the public figures stood still for days, which from the app is indistinguishable from likes not being recorded at all, while Firestore was recording every one of them. What the interval still buys is that a second run the same day (a manual dispatch, a tightened cron) cannot commit twice to move the same number. Two carve-outs matter: an entry with **no** `likes` field is a missing count rather than a stale one (the app reads it as zero), so it is never deferred — that is the state a catalogue published before like aggregation is in — and `--refresh-likes` (exposed as the workflow's `refresh_likes` input) forces a rewrite on demand. `installs` rides that same deferral rather than getting a clock of its own, for the reason two clocks would produce: the two numbers on one card would each have been last correct at a different moment.
- **Downloads and reports are two more per-account ledgers of the same shape, and each departs from the like in exactly one way.** `communityThemeInstalls/<theme>/installers/<uid>` (`CommunityThemeInstallRepository`) is what the public `installs` figure counts, because a statically hosted catalogue never observes a download — a Pages request measures a phone refreshing its cached copy of the *whole list*, and the profile fetched on the way to a detail screen is a preview. The only countable event is an install succeeding on a phone, so that is what is written, and it is **create-only**: removing a theme from My themes does not un-download it, and a client-side delete would make a number that is only republished weekly walk backwards. It must also never fail the install — the theme is already applied when it runs, so every path swallows and logs — and it is written on a **process-scoped** scope (`recordInstallDetached`), since the screen finishes in the same gesture and a `lifecycleScope` launch would be cancelled precisely on the successful path. `communityThemeReports/<theme>/themeReporters/<uid>` (`CommunityThemeReport.kt`) is the moderation gap Play's UGC policy requires closing. It is the one write made *about somebody else*, so: no count is ever aggregated into the catalogue (a public tally is a brigading tool), the reported author can never read it, and it cannot be withdrawn — a delete would let a group probe which reports a moderator had acted on. Both accept an anonymous account for the reason a like does. Three things are easy to get wrong here. The subcollection is `themeReporters`, **not** `reporters`: the moderator queue is a collection-group query, which a rule bound to a concrete parent path does not authorise, so `firestore.rules` carries a `match /{path=**}/themeReporters/{uid}` granting `list` to moderators alone — and a wildcard rule silently applies to every same-named subcollection in the database, which is why the name has to be one nothing else will claim. The reason vocabulary and the 300-character `details` cap are written twice, in Kotlin and in Rules, with `CommunityThemeReportContractTest` pinning them (the same silent `PERMISSION_DENIED` the base-face registry produced). And every teardown path has to reach all three ledgers: `applyWithdrawals` and `applyAccountErasure` in `publisher.mjs` delete installs and reports alongside votes, reports going with the listing because once it is gone the only thing they still record is who complained about what.

- **Approval is a git commit.** `.github/workflows/publish-community-themes.yml` (daily cron plus manual dispatch, pinned to the default branch) runs `.github/community-theme-publisher/publisher.mjs` with the Firebase Admin SDK: it re-parses and re-digests every approved candidate, aggregates like counts, commits `docs/themes/`, then finalizes the intake documents. Nothing an APK sent is trusted as publication data. `docs/admin/` is the restricted moderator page (static, Firebase Web SDK; `firebase-config.js` holds the *public* web config — never a service account, whose only home is the `FIREBASE_SERVICE_ACCOUNT` repo secret).
- **The reviewer's identity is not on the submission, and that is load-bearing.** `reviewedBy` lives in `themeIntakeReview/{themeId}` (moderator-only), never on `themeIntake`. Firestore grants read access **per document, never per field**, so while the verdict and its author shared one record the author-read rule had to be pinned to `status == "pending"` — which is exactly why submitting was write-only. Splitting them is what lets `allow get, list` accept `resource.data.ownerUid == request.auth.uid` in every status and back the app's *My submissions* screen (`CommunityThemeSubmissions.kt`). Putting a reviewer field back on the intake would silently leak it to every author. Every moderator action is one atomic batch verified with `getAfter` (`reviewRecordMatches`), so a decision can never exist without an author; the publisher's `migrateLegacyReviewers` carries already-decided documents across and is self-terminating.
- **An author may withdraw their own theme, and the rule order that allows it is load-bearing.** `validAuthorWithdrawal` accepts an owner setting *only* `status` to `withdrawn` from any state, with no `reviewedAt` and no review record, because no review happened. It is tested **first** in the `themeIntake` update rule: the moderator branch reaches `reviewRecordMatches`, whose `getAfter` on a review document this write never made is an *evaluation error* rather than a clean false, so putting it first would stop an author who is also a moderator from taking down their own theme. It is the same publisher machinery as a moderator withdrawal, and it exists because account deletion already lets someone remove every theme they published — refusing the smaller request would only push them toward the larger one. The app surfaces it in *My submissions* (`CommunityThemeSubmissionsActivity`), reachable from the account screen and the gallery toolbar, where the public like count comes from the already-downloaded catalogue (`OnlineThemesRepository.publishedLikeCounts`) rather than from any per-theme Firebase read; a record the catalogue does not list gets `null`, never `0`, since a submission in review has nothing to be liked yet.
- **A moderator has four transitions, and the self-moderation ban applies to only two of them.** `validModeratorUpdate` allows decide (pending→approved/rejected), reopen (approved/rejected→pending), withdraw (any→withdrawn) and a name/author correction. Nobody may decide or reopen their own submission — that is what stops a moderator publishing themselves into the gallery — but withdrawal and correction are deliberately *not* covered by that ban: a listing nobody can take down is worse than one its own author could also remove. Withdrawal only sets a status; `collectWithdrawnThemes`/`applyWithdrawals` in the publisher remove the file, index row, marker, votes and records, in the same commit-then-Firestore order an erasure uses. The correction is refused once a theme is `published`, because the file is already committed to Git under the old text and rewriting the record alone would leave the two disagreeing with nothing to notice it.
- **Duplicate submissions are refused on the phone from a field the catalogue now publishes.** `buildIndexEntry` writes `settingsDigest` into each index entry (recomputed from the published profile, never carried from a client), `OnlineThemesRepository.publishedSettingsDigests()` reads it back, and `preflightAgainstPublished` feeds it into `CommunityThemeSubmissionRules.publishedSettingsDigests` — the parameter that had existed since the policy was written and that nothing supplied. It **fails open** (no catalogue → no comparison), because the publisher's `duplicate-published-settings` rejection is the real boundary and a network outage must not block a legitimate submission. Like `likes`, a missing `settingsDigest` is a *missing* field rather than a stale one, so it is backfilled immediately instead of waiting out `LIKE_REFRESH_INTERVAL_MS`.
- **Deleting an account is the publisher's job too, and the one decision the app must collect.** `CommunityThemeAccountDeletionRepository` writes one create-only `communityThemeAccountDeletion/<uid>` document carrying `themeDisposition` (`keep`/`delete`); `applyAccountErasure` in `publisher.mjs` carries it out. The split is forced: an APK can delete its own Firebase identity but cannot touch the catalogue in Git, so an in-app deletion would destroy the account and leave its published themes standing. Which is why the *publish* phase withdraws the profile files and index rows (and refuses to publish a theme whose owner is erasing in the same run — it would commit a file the same run takes back out) and *finalization* does every Firestore write plus `auth.deleteUser`. Three rules that are easy to get wrong: "keep" leaves a published theme in place with its `ownerUid` replaced by the `ERASED_OWNER_UID` sentinel (safe because the author-read rule also requires `status == "pending"`, so an erased-but-public row can never be read back), while a submission that is *not* public is deleted under **both** dispositions; the request is deliberately not editable or withdrawable by a client, because a change landing between the Git commit and the Firestore writes is the one state this pipeline cannot reconcile; and an anonymous like-only account may erase itself but is never asked the question, with `choiceWithoutPrompt()` returning `keep` so an account that unexpectedly owns something public has it left alone. The screen's own rules are the pure `CommunityThemeAccountActions` (JVM-tested). `CommunityThemeAccountRepository.refresh()` is how a completed erasure becomes visible: a cached `FirebaseUser` outlives the identity behind it, so only `reload()` failing with `FirebaseAuthInvalidUserException` drops the local session.

**A theme is data, never code** — enumerated preference keys with typed values, no URL, file path or intent — which is what makes hosting user-generated content tractable here at all; the worst a hostile submission can do is look bad. The public parse boundary is `WatchThemeRepository.parsePublishedProfile`, deliberately kept separate from the tolerant `parseProfile` that still serves old local backups: it accepts only current `FaceScopedPreferences.SCOPED_KEYS` with the exact JSON type per key, rejects unknown/archived faces and oversized text, fills any omitted setting from the **shipped base-face default** rather than the recipient's own preferences, and refuses a candidate that would push the phone→watch preference payload past its transport budget. Installing is additive (`installAndApplyPublishedProfile` records a `PublishedThemeSource` id+revision, so a later gallery revision is detectable and the repository never overwrites edits in an already-installed local copy), but the detail screen does not present that installed copy as addable again: it resolves installation from `PublishedThemeSource.id` and switches its primary action to **Remove theme**. Removal must apply the profile's built-in base first when that local copy is active, then delete it; deleting first leaves `WEAR_ACTIVE_CUSTOM_THEME_ID` pointing at an orphaned snapshot. A profile installed *from* the gallery can never be re-submitted as a new public theme, while `duplicate()` deliberately clears its provenance so the user's fork is neither removed with nor mistaken for the downloaded original.

**Two settings deliberately break "a theme is data", and are unpublishable because of it — both now *archived*.** They shipped, did not work in practice, and were hidden behind the developer "Show archived options" switch rather than removed, the disposition `liquid_glass` and `typewriter` already have: `archivedAlbumArtSources` in `WatchFacePrefsFragment` filters `wear_album_art_source`, and the imported font's picker row is injected by `importedFontChoice`, which gates on the same switch (it has no `archived*` entry because it has no `wear_font_values` entry either). Both keep the "currently in use stays listed" rule, and the font's row additionally stays visible while a file is held, because removing one is only reachable from it. `CommunityThemeVocabularyParityTest.theDeviceLocalAppearanceOptionsStayArchived` pins the decision. Everything below still applies — archiving hides the pickers, it does not change what the values mean. `common/.../DeviceLocalAppearance.kt` is the registry: `wear_album_art_source` may name `custom_image`/`custom_folder` (a picture or a folder of pictures the user picked from their own storage, see `AlbumArtSource.isDeviceLocal`), and all six font controls may name `user_font` (a `.ttf`/`.otf` imported through `mobile/.../view/settings/UserFontStore.kt`). Both name a file this phone has and nobody else does; the bytes are not in the profile and could not be, since a profile is a small JSON document that has to fit the phone→watch budget while a font is megabytes. A published copy would therefore install cleanly and render in a typeface, or over a photograph, the recipient has never had — worse than a refusal, because nothing about it looks wrong. The constraints asset already refuses every one of these values and *that* is the real boundary (re-applied by `firestore.rules` and the publisher, neither of which can execute Kotlin); this registry exists so the app can tell the two *reasons* apart. An unsupported value is usually one that should have reached the contract and did not — the fifty-one fonts were exactly that — so `UnsupportedSetting` says "change this setting and submit again", which is right there and actively wrong here; `CommunityThemeSubmissionDraftResult.DeviceLocalSetting` is checked **first** in `CommunityThemeSubmissionDraftFactory.build` and reported by `SubmitCommunityThemeActivity` before any sign-in. It is also the third category `CommunityThemeVocabularyParityTest`'s two sweeps cannot express — offered, current, and permanently outside the vocabulary, which is neither "accepted" nor "archived" — so the exemption is derived from this object and `everyDeviceLocalValueIsRefusedByThePublicVocabulary` pins the other direction. Three consequences to keep straight. `AlbumArtSource.needsLookup` had to become an enumeration rather than "anything but `LOCAL`", or the two custom sources would be gated behind `ONLINE_ARTWORK_ENABLED` — a network switch refusing a file that never touches the network. The keys holding the picked URIs (`CUSTOM_ALBUM_ART_IMAGE`/`_FOLDER`) are **global and not in `EXPORTABLE`**: a URI is a persistable grant that does not survive uninstall, so restoring one would report a chosen picture that cannot be opened, and they are named in `BackgroundEditorModel.globalKeys` because the Background page is otherwise entirely face-scoped. And the font's *display name* (`USER_FONT_NAME`) **is** exportable, because `ConfigBackup`'s `filesDir` sweep already carries the file itself and this is what stops it arriving nameless.

**The imported font is the one user-supplied file the watch has to render with, so it travels as an asset, not a preference.** `CommPaths.DATA_USER_FONT` + `ASSET_USER_FONT`, published by `UserFontStore.publishToWatch` on import, on clear, and once per phone process start (`WearMusicCenter`) — the same staleness repair `publishAvailableThemes` exists for, and free when nothing changed because the item's *payload* is `UserFontContract.fingerprint`, so an unchanged font produces a byte-identical item the Data Layer never re-delivers. Received by the manifest-registered `wear/.../communication/UserFontListenerService`, which is its own listener rather than another path on `ConfigListenerService`: that one posts frozen DataItems into `PhoneConnection`'s LiveData on the callback thread, while this has to open an asset channel and read up to 2 MB, on a process-scoped scope because `WearableListenerService` is torn down the moment `onDataChanged` returns. An item with **no** asset means the user cleared their font and is a real instruction, distinct from the item never existing. `wear/.../theme/UserFont.kt` holds it: a process-scoped holder seeded in `WearMusicCenter.onCreate`, because `watchFontFamily(key)` takes no `Context` and threading one through its ~30 call sites to serve one catalog entry would be a large change to the wrong places. Both `watchFontFamily` and `watchFontTypeface` get a `user_font` branch falling back exactly as an unknown key does, and `WatchFontCatalog` gets the phone-side twin so the preview and the picker render in the imported face. Validation is by **parse**, not by name — extension and MIME are advisory and providers disagree — and it happens on the phone at import, where there is still a screen to explain the refusal; a `.woff` would import, transmit and render as nothing on both devices, which is why the extension list excludes it. `UserFontStore.clear` deliberately does **not** rewrite the font preferences that name the removed file, so re-importing restores every face that was using one.

Four cross-boundary invariants, each of which fails quietly:

- **`firestore.rules` carries its own copy of the base-face registry, and it is the fifth.** `validNewThemeIntake` pins `data.baseFace` to a literal list mirroring `ThemeAppearance.ALLOWED_BASE_FACES` minus `ArchivedFaces.KEYS`, because Rules cannot execute Kotlin. A face added everywhere else but not there passes every local gate — the draft factory builds it, the constraints asset accepts it, the preview renders it — and is then denied at the write, which the app can only report as `community_theme_submit_error` ("check your connection"). Ribbon and Frame shipped exactly that way. The emulator suite's per-face sweep now derives the expectation from the shipped constraints asset rather than retyping it, so the next face fails there instead; every other rules test submits `poster`, which is why the gap was invisible.
- **Firestore evaluates at most 1000 expressions per request, and a submission is one batch of four documents.** Intake, quota, account and name reservation are written atomically, so all four rules — plus every `getAfter` cross-check between them — spend one shared budget. Exceeding it is reported as `PERMISSION_DENIED`, indistinguishable from a real rejection, so the symptom is a valid theme that will not submit while the rules look correct. Two habits caused it and both are now avoided deliberately: `keys().hasOnly(L) && keys().hasAll(L)` over the identical list costs twice what `hasOnly(L) && keys().size() == N` does, and a rule must not re-derive the full shape of a *different* document that has its own rule in the same batch. The account/name pair and the quota therefore each fully validate themselves and cross-check only the pairing fields (owner, key, `lastSubmissionId`, and a `request.time` timestamp proving the write belongs to this request) — the reciprocal `getAfter` guarantees are unchanged, since every one of those documents is write-once with no client update or delete rule. Adding a field or a validation to this path means re-running `npm test --prefix firebase`: the limit is only ever hit by the *second* submission from an account, so a suite that submits once will not notice.

- **The scoped-appearance schema is written in four places, in three languages.** (The constraints asset is at schema **2** since the background layer stack; a new *rule kind* additionally needs the parse in `CommunityThemeConstraints`, its mirror in `schema.mjs`, and — if it can exceed 128 characters — an entry in `maxPublicTextLengthFor`/`maxSettingTextLength`.) Kotlin's `FaceScopedPreferences.SCOPED_DEFINITIONS`, the shipped asset `common/src/main/assets/community-theme-constraints.json` (loaded by `CommunityThemeConstraints.kt`), the publisher's `schema.mjs`, and the moderator page's `docs/admin/theme-profile-schema.mjs`. Neither JS copy can execute Kotlin, so both fail closed on a key they don't know. `common/src/test/resources/community-theme-defaults.properties` is the shared fixture that keeps them aligned — read by **both** `CommunityThemeDefaultsParityTest.kt` (JVM) and `defaults-parity.test.mjs` (Node). So adding a scoped appearance preference is no longer just `SCOPED_KEYS` + `EXPORTABLE`: the fixture and both JS tables move in the same change, or submissions start failing closed.
- **Numeric settings have the same trap, and it went unchecked for longer.** `CommunityThemeVocabularyParityTest` sweeps *pickers*, so nothing covered the fifty `int` settings - all of which are free-typing `ResettableNumericEditTextPreference` rows. The contract declared a range, the watch clamped what it read, and the field in between accepted anything, so an out-of-range number rendered exactly as intended and only surfaced at submission as `community_theme_submit_unsupported_setting`. `common/.../AppearanceNumericRanges.kt` is the authority now: the preference clamps on `setText` (every persist path goes through it) and states the range in its dialog, `WatchThemeRepository.normalizeProfile` clamps a profile saved before the bound existed - which is what makes an already-broken theme submittable without changing how it looks, since the watch was clamping it anyway - and `AppearanceNumericRangeParityTest` pins the registry against the asset, against every numeric row, and against the Text page's slider bounds. Its `UNBOUNDED_BY_DESIGN` set is the escape hatch, and it holds only behaviour settings that have no bound anywhere in the app: inventing a ceiling is not the same as relocating one.

**The constraints asset is a *vocabulary*, not only a key list, and the pickers can outgrow it.** `community-theme-constraints.json` pins the exact set of values each scoped key may hold, and `prepareCommunityThemeSubmission` validates the whole snapshot against it — so one setting holding a value the asset has never heard of makes that entire theme unsubmittable, reported as `community_theme_submit_invalid` ("this saved theme cannot be submitted"), which names neither the setting nor the value. Adding a *key* is the documented trap above; adding a *value* to an existing picker is the quieter one, and it has already happened: fifty-one fonts and both new AOD styles reached `wear_font_values`/`wear_aod_style_values` without reaching the asset. Because these keys are face-scoped it presented as certain *faces* being unsubmittable, which sent the investigation to the base-face registries instead. `mobile/src/test/.../res/CommunityThemeVocabularyParityTest` now sweeps every picker against the asset in both directions, reading the archived-option sets and their key pairings out of `WatchFacePrefsFragment` rather than retyping them — an archived value is deliberately outside the public vocabulary (`publisher.test.mjs` pins `typewriter`), and one archived for one key is often live for another (`solid_theme` is a retired mini-button background and a current seek style), so the exemption has to be per key. `mobile/build.gradle` declares the asset as a test input for the same reason it declares the wear face directory: it lives in `common`, so without that the task stays `UP-TO-DATE` and the sweep never re-runs.
- **`settingsDigest` must be byte-identical in Kotlin and Node.** `common/.../CommunityThemeSubmissionPolicy.kt` owns the canonical encoding (a version header, then the base face and its sorted typed values) and the publisher recomputes it from scratch. It backs both duplicate detection and the originality count, so a drift between the two implementations doesn't error — it silently makes every submission look original and unique.
- **The local gate is user feedback, not a security boundary.** `COMMUNITY_THEME_MINIMUM_CHANGED_SETTINGS` (12 applicable visual changes) and the client-side rolling-window check exist so a person learns the answer *before* being asked to sign in; the rules and the publisher re-apply the same or stricter policy. `isRollingSubmissionLimitReached` deliberately returns false for legacy/malformed quota documents so they fall through to the fail-closed rules path instead of being mislabelled as a rate limit.
- **The emulator suite hides a trap in how account kinds are built.** `authenticatedContext(uid)` already yields a token whose `firebase.sign_in_provider` is `"custom"`, which satisfies `identifiedUser()`; an anonymous caller must override that claim explicitly. Get it backwards and the test still passes, against the wrong account kind. Worth knowing while debugging it: a rule that reads `request.auth.token.*` when `request.auth` is null reports an opaque *evaluation error*, not `false`, so a token the emulator rejected looks exactly like a broken claim expression.
- **Previews are synthetic, and that is a published privacy claim — with exactly one deliberate exception.** `CommunityThemeDetailActivity` renders each surface locally through the same `WatchPreviewView` the Watch tab uses, on fixed sample media, and the moderation preview attached to a submission is a WebP of that synthetic render. The phone's real album cover may appear only from local memory, never paired with live title/artist/playback data and never uploaded. **The app still never captures anything from the watch**, and that half of the claim is absolute. The exception is an *author-supplied* photograph: one image per submission, of the Player only, picked from the system photo picker and re-encoded on the phone (which is what strips EXIF), stored in `themeIntakeShots`, reviewed beside the synthetic render, and committed to `docs/themes/shots/<uuid>-player.webp`. The detail screen prefers it on the Player, labels which of the two is on screen, and `community_theme_show_screenshots` (phone-local, default on, deliberately outside `EXPORTABLE`) gates the *download* rather than the display. The whole contract is `common/.../CommunityThemeScreenshots.kt`, mirrored in `firestore.rules` and `publisher.mjs` and pinned across all three by `CommunityThemeScreenshotContractTest` — which needs its two root files declared as test inputs in `mobile/build.gradle`, or it reports `UP-TO-DATE` and passes on a broken bound. `docs/privacy-policy.md` (and its hand-transcribed `.html` twin) says all of this in the *Community themes* section — so a change here is a privacy-doc change too. Design record: `docs/theme-screenshots-plan.md`.

### Actions system (mobile)

Button presses/gestures map to `PhoneAction` subtypes (`mobile/.../actions/`), each with a corresponding `ActionHandler<T>` implementation (playback, volume, app-launch, Tasker, open menu/playlist, etc.). New actions typically need: an action class, a handler, a binding in `di/ActionHandlersModule.kt`, and an entry in the relevant action list (`RootActionList`, `PlaybackActionList`, `VolumeActionList`).

The saved streaming-shortcuts library doubles as an action-picker category (`StreamingShortcutActionList`): each saved link becomes an assignable `PlayPlaylistShortcutAction`. **Streaming-shortcut launches are watch-initiated:** modern Android blocks a background phone service from starting activities, so an action can carry an optional `remoteUri` (`actions.proto`, present on both button-config and action-menu entries; format `targetPackage|uri` or a bare URI, produced by `PlayPlaylistShortcutAction.remoteUri`). When the watch resolves such an action it registers the URI with `wear/.../communication/PhoneUriOpener.kt` and round-trips the action so `MusicService.playDeepLink` runs on the phone; the phone answers over `CommPaths.MESSAGE_DEEP_LINK_VERDICT` (`/IdleMessages/DeepLinkVerdict`, empty payload = played, otherwise the `targetPackage|uri` to open) and **only that verdict opens anything**. It used to fire the open *in parallel* with sending the action, which defeated the entire ladder below: the target app was brought to the foreground while the silent routes were still being tried, so a pocketed phone lit up and switched apps even when the MediaBrowser route went on to work — and with SoundCloud, where nothing plays, opening the app was the whole visible outcome. `PhoneUriOpener` is process-scoped because every caller (the menu, a button, the Tile trampoline via `ShortcutLaunchActivity`) closes itself in the same gesture, and it is now the single implementation of the open — `MainActivity` and `ShortcutLaunchActivity` each carried a copy of the scheme-validation plus `RemoteActivityHelper.startRemoteActivity` dance. A verdict arriving with nothing outstanding is ignored, since `playDeepLink` also runs for shortcuts started from the phone's own UI. Its `VERDICT_BACKSTOP_MS` (30 s) is a safety net for a lost message or a phone that died mid-ladder, deliberately far beyond the ladder's ~16 s worst case so it can never race a merely slow verdict; a verdict is sent at **every** terminal path, success included, precisely so that timer is not the normal mechanism.

`playDeepLink` (mobile) is the actual playback engine and tries progressively stronger contracts because merely *opening* a link only navigates, it doesn't play: (1) if the target app already has any active session (found across **all** active sessions via `ActiveMediaSessionProvider.controllerForPackage`, not just the tracked "current" one), issue `playFromUri` — and then **verify it**, sampling `playbackIdentity` before and re-checking after `DEEP_LINK_VERIFY_MS`, because "accepted" is not "playing": SoundCloud takes a track URI happily and silently ignores a collection one, so trusting the advertised `ACTION_PLAY_FROM_URI` bit reported success and skipped every remaining step. The one case that counts as swallowed is the app carrying on with exactly what it had; "same item but now playing" is a legitimate resume. This is the same issue-and-verify rule the queue tap follows, and for the same reason — see `MediaSessionCapabilities`; (2) otherwise ask the app's `MediaBrowserService` to play through `mobile/.../music/MediaBrowserPlayback.kt` (URI first, then the shortcut's saved name as a `playFromSearch` — search is a *fallback* here, not only the artist path, because the visible open it used to defer to is not free: it foregrounds the app, and for a collection it doesn't even start playback) — the Android Auto/Assistant path, the only one that works with the screen off / app not running, since binding the browser wakes the app with no Activity launch (this is why the YT Music Liked-Music shortcut plays even after a force-stop; Spotify usually rejects unknown browser clients, so it falls through); (3) finally the visible deep-link open + a media-session nudge (`MediaBrowserPlayback` retries the play command while the freshly-woken session warms up). **Artists** are special: a `playFromUri` on an artist page only navigates, so `StreamingShortcutLinks.isPlayable` treats `ARTIST` as playable and the shortcut's saved *name* is passed as a `playFromSearch` query (the one command both YT Music and Spotify honor from outside) — for precise entities (track/album/playlist) the URI stays authoritative and search is never substituted. `forPlayback` also canonicalises YouTube share links (`youtu.be`, plain `youtube.com`, `/playlist`) into the `music.youtube.com/watch` form that actually starts playback. Dedicated one-tap actions exist for the account "Liked Songs" of YouTube Music (`PlayLikedSongsAction`, `watch?list=LM`) and Spotify (`PlaySpotifyLikedSongsAction`, `spotify:collection:tracks`), SoundCloud Likes (`PlaySoundCloudLikesAction`, `/you/likes`), and the account-wide personalized Deezer Flow (`PlayDeezerFlowAction`, `/flow`). When there is *no* current session at all (the watch's "Nothing playing" idle screen), a play/pause command resumes the last app via `AudioManager.dispatchMediaKeyEvent(KEYCODE_MEDIA_PLAY)`.

**Optional online shortcut thumbnails** (`mobile/.../music/ShortcutArtworkFetcher.kt` + `ShortcutArtworkStore.kt`): strictly opt-in (`streaming_shortcut_artwork` pref, off by default — one of the app's eight feature network paths, the others being the update check, the queue-cover fetch under *Playback queue* below, the two under *Lyrics and track metadata*, the artist-picture lookup under *Modernization roadmap*'s Artist face, and the catalogue fetch plus the Firebase sign-in/Firestore writes under *Community themes*; Crashlytics/Analytics/FCM are separate and covered under *Logging / diagnostics*), it fetches each saved shortcut's cover once from the service's public **oEmbed** endpoint (Spotify/YouTube/SoundCloud/Deezer), caches the PNG on disk keyed by link, and surfaces it in the phone list, as the assigned action's icon (`PlayPlaylistShortcutAction.defaultIcon`), and on the watch menu — the latter by attaching the PNG as a per-index DataItem asset in `PlaylistShortcutStorage.createDataRequest` (the watch's `decodeCustomList` already reads `assets[index]`, so no watch change was needed). Editing a saved shortcut propagates to every already-assigned copy via `PlaylistShortcutActionSync` (button configs + action list, matched by old link, re-committed through the normal path); the Actions screen re-reads its config in `onResume` (`ActionListViewModel.refreshFromConfig`) so a rename shows up there too.

### Playback queue (mobile)

`OpenPlaylistAction` builds the watch's queue list. Several failure modes that look identical to a user ("no queue" / "no covers" / "tapping a row does nothing") have entirely different causes, so each has dedicated machinery:

- **Encoding**: queue thumbnails are JPEG (`OpenPlaylistAction.encodeThumbnail`), deliberately *not* `BitmapUtils.serialize`, which is lossless PNG. Cover art is photographic with no alpha, so PNG is several times larger — the reasoning `MusicService.transmitToWear` already records for the single now-playing cover, but multiplied by up to 20 assets in one DataItem. The watch decodes with `BitmapUtils.deserialize` (`BitmapFactory.decodeByteArray`), which is format-agnostic, so only the sender needed changing.
- **Which controller is reported** is decided by the pure `resolveReportedSession()` (tested by `ReportedSessionTest`): the playing session, else the last reported one *while it is still live*. `ActiveMediaSessionProvider.currentController` is null whenever nothing plays, so a pause fallback must read `lastReportedController` instead — reading `currentController` meant the first pass after a pause looked right and every later pass reported null, dropping the watch to the idle screen mid-pause.
- **Acquisition** goes through `MusicService.resolvePlaybackQueue()`, not `currentMediaController.queue` directly. Some players run several `MediaSession`s at once — Retro Music ships a `WearBrowserService` session beside its playback one — and only one carries the queue, while the tracked controller is chosen by which session is *playing*. `ActiveMediaSessionProvider.siblingQueueForPackage` covers that gap before the code falls back to `recentTrackHistory` (`CustomLists.HISTORY`). A player that publishes no queue at all (pre-6.x Retro Music never called `setQueue`) genuinely cannot be helped — history is the honest answer.
- **Selection** (what a tap on a row does) has three independent ways to silently do nothing, and each is guarded separately. First, **which session the command goes to**: `resolveQueueSource()` returns the queue paired with the controller that published it (`MusicService.QueueSource`, via `ActiveMediaSessionProvider.siblingQueueSourceForPackage`), and `onCustomMenuItemPresed` sends `skipToQueueItem` to *that* controller, not to the tracked/playing one. A `queueId` indexes one specific session's queue, so in the multi-session case the acquisition bullet above describes, aiming it at the playing session addresses a queue that session has never heard of — accepted, and nothing happens. Second, **whether the command works at all**: entry ids are encoded rather than bare, `common/.../CustomLists.kt`'s `QueueEntry` writing `"<queueId>|<mediaId>"` — split once on the first `|`, the same shape and reasoning as `LibraryEntry`, since a media id may itself contain `|`. `skipToQueueItem` is then issued **unconditionally** and the result *verified*, rather than predicted from `ACTION_SKIP_TO_QUEUE_ITEM`: gating on that bit is how this regressed in the first place, since plenty of players implement the command without advertising it, and the gate diverted a working call into a fallback that did nothing. An unsupported transport command is a harmless no-op, so always trying costs nothing while guessing wrong costs the whole feature — which is why `MediaSessionCapabilities` deliberately has no `advertisesSkipToQueueItem`. `onQueueEntrySelected` samples `playbackIdentity` (active queue id + metadata media id + title) *before* issuing, waits `QUEUE_SKIP_VERIFY_MS`, and only if nothing moved plays the row's own media id through `MediaBrowserPlayback.playMediaId` — the route library/search selections already use. Retro Music is the known case for that fallback: neither of its sessions implements the command, which is again *not* the same as publishing no queue — its browser session hands out real, playable items, it just never answers that one command. The media id is round-tripped from the app's own queue, never constructed, which keeps it inside the rule `docs/player-integration-notes.md` sets out. Tapping the row that is already playing is excluded from the verify, since "nothing changed" is the correct outcome there rather than a failure. Third, **whether the message is sent at all**: `PhoneConnection.executeCustomMenuAction` (watch) runs `withContext(NonCancellable)`, because every caller closes its screen in the same gesture that selects and the send is a node lookup *then* a message — a cancel landing between the two dropped the selection entirely. `OpenPlaylistAction` encodes `activeEntryId` the same way as the rows, looking the playing item's media id up in the **full** queue rather than in the page just sent, because the watch matches it against each row's `entryId` by plain string equality. `QueueEntry.queueId` decodes malformed/`SPECIAL_ITEM_ERROR`-shaped ids to `QueueItem.UNKNOWN_ID`, which the handler treats as "no usable position" rather than passing on.
- **Paging**: the live queue is sent one page at a time — `common/.../CustomLists.kt`'s `QueuePaging` (`PAGE_SIZE` 20, `MAX_ENTRIES` 200, `nextLimit`, pinned by `QueuePagingTest`) — because every entry carries its own thumbnail asset across Bluetooth. The watch states the size it wants in the `MESSAGE_OPEN_PLAYBACK_QUEUE` payload (a 4-byte int; absent from pre-paging watch builds, which reads back as the default first page), and the phone reports how many entries exist in `customList.proto`'s `totalEntryCount` — the only way the watch can know whether offering "Load more" would get it anything. Requests are **cumulative, not incremental**: each asks for a larger prefix and replaces the whole list, because the queue is one DataItem the phone replaces wholesale. Play Services addresses assets by content hash, so covers already on the watch are not re-sent. The consequence to remember when touching this: any autonomous re-push has to reuse `MusicService.lastRequestedQueueLimit`, since `scheduleQueueRefresh` fires on every track change and a default-sized push would collapse a paged-through queue back to 20 rows under the user.
- **Where the watch's queue opens** is `wear/.../view/queue/QueueScrollPolicy.kt` (pure, JVM-tested, same shape as `QueuePaging`): it scrolls to the playing row rather than the top, and distance picks the method — within `ANIMATE_WITHIN_ROWS` it animates, because the movement shows *which way* the list went in a way a jump cannot; beyond it it jumps, because eighty rows of tracks flying past is several seconds spent arriving somewhere the user could have been shown at once.
- **Artwork** goes through `mobile/.../music/QueueArtworkResolver.kt`, a cheapest-first chain: `iconBitmap` → local `iconUri` → artwork URIs in `description.extras` → MediaStore (`loadThumbnail`, else `ALBUM_ID` → the legacy `albumart` table) → remote http(s), with `MusicService.currentAlbumArt` as a final fallback for the row whose `queueId` matches `activeQueueItemId`. That last step matters more than it looks: Media3's `MediaSessionLegacyStub` attaches a bitmap to a queue item **only** when the app embedded raw `artworkData`, while the current track's *metadata* goes through `loadBitmapFromMetadata`, which downloads `artworkUri`. A streaming client (Echo Music, YouTube Music front-ends) therefore shows art on the player while **every** queue row — including the playing one — carries nothing but a remote URL. Reusing the already-decoded player cover costs no network call and no permission. Two steps are gated:
  - MediaStore needs a media-read grant. `READ_EXTERNAL_STORAGE` stopped being grantable at `targetSdk` 33, so `READ_MEDIA_AUDIO` is declared and requested **in context** from the `queue_media_permission` row in Settings → Apps (`MiscSettingsFragment`), never at startup. Ungranted, the step is skipped silently.
  - Remote covers are the Echo Music / YouTube-Music-client case (Media3's `artworkUri` maps onto the legacy description as an http URL). Gated on `queue_remote_artwork`, which is **on by default** (`QueueArtworkResolver.REMOTE_ARTWORK_DEFAULT`) — the exception to the project's otherwise opt-in network stance, because a streaming queue has *no* other cover source, so off produced permanently blank rows rather than a degraded list; the shortcut-artwork fetch stays opt-in since it degrades to an app icon. Defaults are never persisted (`setDefaultValues` is not called anywhere), so this flips for existing installs that never touched the switch. Results are cached on disk and the requested size is rewritten into the URL first (`sizedArtworkUrl`, tested by `SizedArtworkUrlTest`): those clients publish a list-sized ~60px thumbnail, and since `shrinkPreservingRatio` only ever shrinks, fetching it verbatim left Cover-style pills visibly pixelated with no later step able to recover. The cache is `RemoteArtworkCache` (in `cacheDir`, self-trimming to `MAX_ENTRIES`), and it is deliberately **not** `ShortcutArtworkStore`, which it originally reused on the reasoning that both are plain URL-keyed PNG caches. What that missed is that their lifetimes are opposite: a shortcut thumbnail is user data, one file per saved link, backed up with the shortcut library and pruned by `retainOnly`; a queue cover is disposable and unbounded, one per remote row of every queue ever opened. Sharing the folder therefore had `retainOnly` wipe the queue cache on any shortcut edit, and — the reported failure — a few hundred queue covers pushed the `shortcutArtwork` asset store past `ConfigBackup`'s `MAX_ASSETS_PER_STORE`, which aborts the *whole* export (`Too many shortcutArtwork assets to back up`), not merely the Icons section. `WearMusicCenter.repairShortcutArtworkStore` is the one-shot that prunes an already-polluted folder, since `retainOnly` otherwise runs only when the shortcut screen is edited. The rule this leaves: a cache put in `filesDir` is not free — the backup walks everything there, so an unbounded one fails either its own store's cap or `MAX_INTERNAL_FILES`. The download applies the same hardening `ApkDownloader` documents (follow redirects, explicit `User-Agent`, `Connection: close` against Android's truncate-on-redirect pooling bug). **This is a network path: keep `docs/privacy-policy.md` and the Data Safety draft consistent when touching it.** The toggle is intentionally declared in *both* `settings.xml` (Apps) and `watch_face_settings.xml` (Panels, beside the queue styling) — it is not in `SCOPED_KEYS`, so the face-scoped data store passes it through unscoped and both rows drive the one global key.
  - Whichever step found the cover, the result passes through `common/.../BitmapBorderTrim.kt` once (`resolve` wraps the private `resolveRaw` purely so that pass lives in one place). It crops flat letterbox/pillarbox bars — YouTube Music "art track" thumbnails wrap the real square cover in them, so without it a square crop keeps the bars and the cover lands as a small square inside the circle. It was extracted from `ShortcutArtworkFetcher`, which had the identical problem with the same kind of thumbnail and is still a caller; its one piece of real judgement (`isUniformLine` — what counts as "flat") takes a pixel lambda rather than a `Bitmap`, so it is pinned by a plain JVM test. It lives in `common` because the trim has to happen on **both** sides: a cover can also reach the watch from a source the phone never re-encodes (the reused now-playing bitmap, or an older phone build), so the watch trims again in `PhoneConnection.decodeCustomList`, which is the single point every list cover it draws passes through. Trimming twice is free — an already-trimmed cover has varied edges and comes back unchanged.
  - `OpenPlaylistAction` resolves every entry's cover concurrently (`coroutineScope { ... async { QueueArtworkResolver.resolve(...) } }.awaitAll()`), not one at a time — a 20-entry queue with several slow/failing remote fetches would otherwise serialize into seconds of wall-clock delay even though each fetch is already off the main thread. `QueueArtworkResolver` logs each entry's resolution path at `Timber.v` (candidates found, which step matched, why a step was skipped) for exactly this kind of "some covers just don't show up" report.

### Config backup (mobile)

`mobile/.../config/ConfigBackup.kt` exports/imports both button configs, the action list, the `MiscPreferences.EXPORTABLE` watch-behavior settings, the custom watch-theme library (`watchThemes` — see the Watch tab section; since schema 3), and (since schema 4) the user's personal runtime data — saved playlist shortcuts, search history and track history — under a `userData` block, as one JSON document (exposed in `MiscSettingsFragment`). The button-config/action-list files are copied as opaque base64 `PersistableBundle` blobs, so the backup format doesn't need updating when configs gain fields — but adding a *new* config file or a preference that should survive reinstall means touching `CONFIG_FILES` or `MiscPreferences.EXPORTABLE`. The theme library is validated as one unit before any import write (all-or-nothing), and importing a pre-theme (schema 1/2) backup deactivates any active custom theme so the imported `wear_screen_face` can't silently rewrite a saved profile's base layout. The `userData` block holds the three storages' raw JSON strings (`playlist_shortcuts`, `search_history`, `track_history`) and is restored in the same preference transaction; importing re-syncs the shortcut library to the watch. Older backups (schema ≤ 3) simply omit `userData` and leave whatever is already on the phone.

**The app's shipped defaults are a `ConfigBackup` document, and there is a second exporter for it.** A fresh install does not start from generic first-run guesses: `GlobalActionConfig.seedBundledDefaultConfig` imports `mobile/src/main/res/raw/default_config.json` before any config file exists, so "default" means the author's own saved setup. `mobile/.../config/DefaultConfigExport.kt` is what produces that file (Settings → Developer → *Export as app defaults*, saving under the resource's own name so it can be dropped straight into `res/raw`); until it existed the shipped copy could only be updated by hand-editing an ordinary backup. It is deliberately **not** the document the Settings backup writes, and the difference is invisible by eye while getting it wrong compiles somebody's listening history into the APK — hence the `defaultConfigExport` marker block it stamps on the output. The policy is expressed over `ConfigBackupSection` rather than as a second exporter, so a new preference follows its section automatically: `HISTORY`, `PRIVACY` and `LOCAL_APP_STATE` are dropped (personal traces; consent that is each person's to give; and state recording what *this* phone has already done — shipping the last suppresses a first-run notification prompt and marks one-shot migrations complete on a device where they never ran). Two finer exclusions sit inside included sections: `MiscPreferences.APP_LANGUAGE`, which overrides the device locale and would open the app in one person's language on everyone's phone, and the `community_theme_submission` named store, which is the author's gallery identity. `DefaultConfigExportTest` pins all of it, and the export reports its own byte size because the icon stores travel inside it and therefore inside the release.

**Parcel-stability warning:** those blobs (and the on-disk config files themselves, `mobile/.../util/BundleFileSerialization.kt`) are raw `Parcel.marshall()` bytes, whose format is *not stable across Android OS versions* — a blob written on one version can throw `BadParcelableException` on another, and only **lazily** (at the first `bundle.get*()` call, far from the read site; nested bundles defer even further). This crashed the Watch tab on Android 15. Consequently: `readFromFile` force-unparcels inside its own guard, quarantines undecodable files (`<name>.corrupt`) and never throws; every deep bundle walk must still catch `RuntimeException`; `ConfigBackup.import` validates all blobs *before* writing anything (`BundleFileSerialization.isDecodable`) and throws on incompatible backups — which also makes `GlobalActionConfig`'s bundled-default seeding (`R.raw.default_config`, itself such a backup exported on some past device/OS) fall back to auto-detected defaults instead of planting an unreadable config. Writes go through temp-file + atomic rename.

### Update system (sideload self-updates)

**This whole subsystem is `github`-flavor only.** It lives in `mobile/src/github/.../update/` and `wear/src/github/.../watch/update/`, with its manifest entries (`REQUEST_INSTALL_PACKAGES` + the components) in `src/github/AndroidManifest.xml` of each module — Google Play forbids an app updating itself outside Play, so the `play` build carries none of it. `src/main` code reaches it only through `mobile/src/github|play/.../update/UpdateGateway.kt` (an `object` with a real impl in `github`, a no-op with `SUPPORTS_SELF_UPDATE = false` in `play`); the pure version comparator was split out to `mobile/src/main/.../update/AppVersionComparison.kt` because the community-theme gallery needs it in both flavors. `MiscSettingsFragment` hides the Updates category and `SettingsSearchIndex` drops its rows when `!SUPPORTS_SELF_UPDATE`. Pinned by `FlavorSelfUpdateIsolationTest`; full plan in `docs/play-store-migration-plan.md`.

The GitHub sideload build ships its own updater. Phone side lives in `mobile/src/github/.../update/`: `UpdateChecker` polls the GitHub releases API (throttled to daily; triggered from `MusicService.onCreate` and phone `MainActivity.onCreate`; prefs `update_check_enabled` / `update_include_prereleases` in the Settings tab's Updates category), `UpdateNotifier` posts the notification, and `UpdateActivity` is the single update surface (versions, release page, push-to-watch). Release assets are matched **by exact name** (`mobile-release.apk` / `wear-release.apk`) — keep naming releases that way. `WatchApkPusher` downloads the wear APK and streams it over `CommPaths.CHANNEL_WEAR_APK`; on the watch, `watch/update/ApkReceiverService` (manifest `CHANNEL_EVENT` listener) receives it, validates the package name, and commits a `PackageInstaller` session, with `InstallResultReceiver` turning `STATUS_PENDING_USER_ACTION` into a tap-to-install notification (background services can't launch the confirm dialog) and `MY_PACKAGE_REPLACED` doing post-update cleanup. Needs `REQUEST_INSTALL_PACKAGES` + the user's one-time "install unknown apps" grant on the watch. The "Update watch" button is gated on the *watch's* version, reported via the `appVersionCode`/`appVersionName` fields of `watch.proto`'s `WatchInfo` (absent on pre-2.2 watch builds). Both app modules have `buildConfig true` enabled for `BuildConfig.VERSION_NAME` access.

The **phone updates itself** through the same shape: `ApkDownloader` (shared byte-count-validated download) → `PhoneApkInstaller` → `PhoneInstallResultReceiver`, mirroring the watch's `ApkReceiverService`/`InstallResultReceiver`. Two non-obvious constraints, both learned from an unlocalized system "There was a problem parsing the package" failure with no recovery path: the download is validated as a genuine APK *for this package* (`getPackageArchiveInfo` + package-name check) **before** it ever reaches an installer, since a matching byte count still misses same-length corruption; and it is committed through a `PackageInstaller` session rather than an `ACTION_VIEW` intent at the file — so there is deliberately **no FileProvider** in `mobile/` for APKs (sessions write from a `File` directly; the old `apk_paths.xml` was removed, don't reintroduce it). Missing "install unknown apps" is reported as a `Progress.NeedsPermission` state that opens the settings screen, never as a failure.

### Custom lists (watch menu content)

Several watch-facing features are phone-side SharedPreferences storages (`mobile/.../music/*Storage.kt` — search history, playlist shortcuts, track history) delivered to the watch as **custom lists**; the list types (live queue, recently-played fallback for apps that hide their queue, search results, playlist shortcuts, search history, library page) are defined in `common/.../CustomLists.kt`, and selection/deletion round-trips through `MusicService.onCustomMenuItemPresed` and `CommPaths.MESSAGE_DELETE_CUSTOM_LIST_ITEM`. Watch-initiated search (`SearchAction`) opens voice/keyboard input on the watch; the query returns via `CommPaths.MESSAGE_PLAY_FROM_SEARCH` and is resolved with `MediaBrowserSearch` (MediaBrowserService library search — the Android Auto/Assistant mechanism, far more reliably implemented by music apps than `MediaSession.playFromSearch`).

**Library browsing** (`CustomLists.LIBRARY`) is how the watch starts something that was never saved or searched for: `OpenLibraryAction` → `MusicService.openLibraryOnWatch()` walks the playing app's `MediaBrowserService` tree one page at a time via `mobile/.../music/MediaBrowserLibrary.kt` (a deliberate sibling of `MediaBrowserSearch`, sharing its `findBrowserService`/`connect`, since searching is one stateless query while browsing is a caller-driven walk; every page connects and disconnects rather than holding another app's binding open across a killable service). Row ids are encoded by `CustomLists.kt`'s `LibraryEntry` object (`b|` browsable / `p|` playable / `^up`) — a prefix rather than a new protobuf field, because the watch has to know whether a tap swaps in the next page or closes the menu and plays. `browse()` returning null means "this app exposes no library at all", which is reported as one explanatory row and is distinct from a `Page` with no children.

The governing constraint on all of this, written up in `docs/player-integration-notes.md`: **a media id is only meaningful to the app that produced it** (Retro Music `parseInt`s it, Echo demands an `auto/` prefix, InnerTune splits on `/`), so ids are only ever round-tripped from that app's own browse/search results — never constructed — and a *browsable* id must never reach a play command. Related: `mobile/.../music/MediaSessionCapabilities.kt` decides whether a transport command is worth issuing at all, with three states rather than two — a null `PlaybackState` resolves to **true**, because a session that has published nothing has not declined anything and is usually one freshly woken by a browser binding, which is exactly the wake-then-play path everything depends on. Its limit is worth knowing before reaching for it: the bitmask reliably says what a session *claims*, not what it does, and a missing bit is routinely wrong. Use it only where a false negative is cheap (search, which has a real alternative) — never to withhold a transport command whose failure mode is a silent no-op, which is why the queue tap issues and verifies instead (see *Playback queue*).

### Lyrics and track metadata

Two watch screens are fed by **on-demand request/response**, not by the pushed `MusicState`, and the reasoning is the same for both: a surface nobody has open should cost nothing. A watch on any other face never sends the request, so the phone never makes a network call, never opens a file, and the payload never crosses Bluetooth.

**The phone always does the network call, never the watch.** A Bluetooth-only watch has no internet route of its own, so a watch-side fetch would work on the LTE models and quietly fail on every other one; it also keeps the app's whole network surface on the device `docs/privacy-policy.md` describes. **Both paths are network paths — keep the privacy policy and the Data Safety draft in step when touching them.**

Both protocols echo the requested track's title/artist back in the answer, and the watch discards a response whose track is not the one on screen: the two sides drift by a track whenever a skip is in flight, and an answer for the wrong song is worse than none because nothing about it looks wrong.

- **Lyrics** (`lyrics.proto`, `CommPaths.MESSAGE_REQUEST_LYRICS` → `MESSAGE_LYRICS_RESULT`). Phone side: `mobile/.../music/LyricsFetcher.kt` reads [LRCLIB](https://lrclib.net) — chosen because it matches on *metadata* (track/artist/duration) with no API key, account or per-service track id, which is what lets lyrics work regardless of which app is playing; `LyricsRepository.kt` caches answers **in memory only** (persisting would leave a folder of other people's copyrighted text on disk and a privacy question to answer) and deliberately does not cache failures. Watch side: `wear/.../view/lyrics/` (`LyricsActivity`/`LyricsScreen`/`LyricsViewModel`) plus `LyricsFeed.kt`, which feeds the Verse face and which `MusicViewModel` enables *only* while that face is selected. Raw LRC travels as text and is parsed on the watch by `common/.../LyricsParser.kt` (honours the file's `[offset]`; renders per-word karaoke timing as ordinary lines). Tapping a line seeks to it (`LyricsViewModel.seekToLine`): it anchors `PlaybackClock` locally *before* sending `MESSAGE_SEEK_TO`, the same order the player's own seek uses, since waiting for the Bluetooth round trip would leave the old line lit long enough to look like a missed tap. Two decisions there. It seeks to the line's exact `timeMs` with **no lead-in** — a little earlier would be kinder to a listener catching the run-up, but `LyricsParser.indexAt` would then highlight the *previous* line, so the screen would answer a tap by lighting up a different row. And it is **not** gated on `MusicState.seekable`: that bit is routinely under-reported, an ignored seek is a no-op the clock's next check undoes, and withholding it on a wrong bit loses the whole feature — the rule `MediaSessionCapabilities` records and the queue tap already follows. The rows carry `indication = null` deliberately: the tapped line becoming the current line *is* the confirmation, and a ripple would be a third thing on a screen whose design is that the accent appears in exactly two places. `common/.../LyricsStatus.kt` keeps `NONE` and `FAILED` distinct — one is an answer, the other is a missing answer, and only the second is worth a retry or a "check your connection". `MiscPreferences.LYRICS_ENABLED` is **on** by default, for `QueueArtworkResolver`'s remote-artwork reasoning rather than the shortcut-artwork opt-in stance: there is no second source for a lyric, so off does not degrade the screen, it empties it — and opening the screen is itself the consent, since nothing is fetched until someone does. The action is `ACTION_OPEN_LYRICS` / `OpenLyricsAction`, watch-local in the same sense as the playlist menu: the watch launches `LyricsActivity` directly, and the phone-side handler only runs for paths that always execute on the phone (the actions menu), where it bounces `MESSAGE_OPEN_LYRICS` back.
- **Track metadata** (`metadata.proto`, `CommPaths.MESSAGE_REQUEST_TRACK_METADATA` → `MESSAGE_TRACK_METADATA`), backing the `metadata` face and `wear/.../view/metadata/MetadataFeed.kt`. Deliberately *not* folded into `MusicState`, which is sent on every state change and rides a size-capped payload — twenty mostly-empty strings would be paid for on every pause and volume nudge by every face. `mobile/.../music/TrackMetadataReader.kt` reads two sources in cost order: the playing app's own `MediaMetadata` (free, instant), then the **file** for bitrate/sample rate/channels/size, which are properties of the encoded audio and not `MediaMetadata` fields at all — local tracks only, gated on the media-read grant, and silent when either is missing. `mobile/.../music/MusicBrainzMetadata.kt` is the optional enrichment (ISRC, label, release date, catalogue ids): free, no key, and the only realistic source for those, but the match is *fuzzy* on title+artist alone, which is why `MiscPreferences.METADATA_LOOKUP_ENABLED` is **off** by default — unlike lyrics it only ever *adds* rows to a table that already stands on the player's own tags. The phone answers **twice** for one request when it is on — immediately with what it already knows, then again with `enriched` set — so the table is on the wrist before the first packet leaves, and the watch needs `enriched` to tell a second answer from a newer track.
- Both use the `/Messages` prefix, **not** `/IdleMessages`. That prefix exists to wake a watch whose UI is not running, and both payloads are useless to a watch with no such screen open — routing them there would spin the process up to throw the answer away. `/Messages` has no manifest listener, so they reach only `PhoneConnection`'s runtime listener, alive exactly when the screen is.

The payload also carries **how it is being played**, not only what is playing: the media URI verbatim, the local file's name (queried via `OpenableColumns.DISPLAY_NAME`, since a MediaStore `content://` URI ends in a numeric row id far more often than in a name), the audio output, `MediaController.PlaybackInfo.playbackType`, and the player's download status. Two things about that block. It is a **snapshot** — the answer is asked for once per track, so a value that moves mid-track (the output device, a download completing) is right when drawn and can go stale until the next track; the alternative is a subscription pushing on every change, which is exactly what `MusicState` already refuses to do for the position. And the URI is *sent* but never *opened*: `TrackMetadataReader` filters to `content://`/`file://` before any probing, because handing an `https://` media URI to a `MediaMetadataRetriever` would make this screen perform a network download to fill in a bitrate row. The output is read from `AudioManager.getDevices(GET_DEVICES_OUTPUTS)` in a priority order rather than from a "current route" API, because there is no reliable one at `minSdk` 23 — available is a good proxy for in-use for the three cases a listener distinguishes, and casting is answered first from the session itself since the phone's own route says nothing then. `outputKind` and `downloadStatus` cross as **codes, not labels**: a phone service's `getString` does not reliably follow the in-app language pre-33, so the watch owns the localisation (a Portuguese watch showing an English row would be the visible symptom).

`common/.../TrackMetadataFields.kt` owns both halves of the face's row registry: the `Group` enum (CORE/RELEASE/CREDITS/IDENTIFIERS/TECHNICAL/PLAYBACK — each a face-scoped preference key plus its default, so the renderer and `MiscPreferences.metadataGroupPreference` cannot disagree about what exists; a new group must be added to `EXPORTABLE` and `SCOPED_KEYS` too, which `ScopedAppearanceRegistryTest` pins) and the pure numeric formatters, shared for the same reason `PaletteTransforms` and `WatchTypography` are. Grouped rather than one switch per field, because a row exists only when the player published that tag — per-field switches would mostly control rows that are not there. The face never says "unknown": it draws a row per populated field, and a short table is the honest signal that a player is stingy with metadata. It fits rows by *measuring* rather than scrolling (scrolling would fight the host's configurable up/down swipe pseudo-buttons), which is what makes the group switches load-bearing — turning off the file details is how you make room for the credits. A row declares how many lines it costs (`MetadataEntry.lines`) and the budget is spent per line rather than per row, so the full-URL row — `wide`, three lines, no label column, because no 90dp column holds a signed CDN URL — displaces others instead of overflowing off the bottom.

Two details of the face are worth knowing before touching it. The **elapsed position is drawn to the millisecond and by its own composable** (`LivePositionRow`), not from the row list: the host's position ticker is 500 ms, which would step the last three digits by 500 twice a second, so the digits in between are extrapolated from the watch's own monotonic clock — the same rule `PlaybackPositionEstimate` enforces for the sample's trip across Bluetooth, never a cross-device subtraction. It re-anchors on every sample (so a seek lands rather than being caught up to) and runs only while playing. Keeping it out of `metadataRows` is what stops its ~16 Hz refresh from rebuilding the whole table. And the row-dedup checks compare against the **metadata payload's own** title/artist, never the two lines on screen: those become status text the moment playback stops, so comparing against them made pausing produce an "Album artist" row carrying the very name the check exists to suppress, directly under an artist line reading "Playback Stopped".

### Localization

The app ships translations for 45 locales, and the UI language is a **user preference that syncs to the watch**, not just a device setting: `MiscPreferences.APP_LANGUAGE` (in `EXPORTABLE`) is picked in the phone's Settings and resolved on both sides through `common/.../AppLocales.kt`, so a phone set to Portuguese doesn't leave an English watch. The two apps *apply* it by different means, deliberately — `mobile/.../view/settings/AppLanguage.kt` uses `AppCompatDelegate.setApplicationLocales` (every phone activity is an `AppCompatActivity`, and on Android 13+ this registers with the framework's per-app language setting), while `wear/.../util/WatchLanguage.kt` wraps each activity's base context, because `MenuActivity`/`QueueActivity` are plain `ComponentActivity` and AppCompat's pre-33 backport only recreates `AppCompatActivity`. Unknown/unsupported tags resolve to the system language rather than to themselves, since a value can arrive from an imported backup or a newer build on the other device.

Adding a language means keeping four places in step, all of which must agree or the picker lies about what's translated: a `values-<code>` folder in **each** of `mobile/`, `wear/` and `common/` (each module carries its own strings; `common/` backs shared views), `AppLocales.SUPPORTED` (order = picker order), `mobile/src/main/res/xml/locales_config.xml` (the Android 13+ system picker), and the `app_language_entries`/`app_language_values` arrays.

The folder names are **not** uniformly `values-<code>`: thirty-eight of the forty-four non-English locales use the plain/region form (`values-de`, `values-pt-rBR`, …) but six use the BCP-47 form — `values-b+id`, `values-b+fil`, `values-b+he`, `values-b+zh+Hans`, `values-b+zh+Hant` and `values-b+ckb`. None of these is stylistic, and they're two distinct classes of gotcha. Android's *legacy* resource code predates a handful of ISO 639 renames and never followed them, so a folder spelled with the *current* code is silently never selected: Indonesian's legacy code is `in` not `id`, and Hebrew's is `iw` not `he` — `values-id` and `values-he` both look right and both are dead folders. Simplified and Traditional Chinese, Filipino and Central Kurdish are the other class: `zh-Hans`/`zh-Hant` need a script subtag the plain `values-<lang>` syntax has no way to express at all, and Filipino's `fil` and Central Kurdish's `ckb` are 3-letter codes with no legacy 2-letter form to fall back on. `AppLocales.SUPPORTED` and `locales_config.xml` still spell all six the modern way (`id`, `fil`, `he`, `zh-Hans`, `zh-Hant`, `ckb`) — only the *folders* differ, which is exactly why the mismatch is easy to introduce and invisible until someone runs the app in that language. Treat any newly-added language as a candidate for this trap rather than assuming the plain form works: verify the actual legacy Android/ICU code before creating the folder, the same way this section had to be corrected twice already.

**Adding an *entry* to any `<string-array>` picker is the sharper hazard**, and it has bitten repeatedly (3.1-beta2's changelog is largely this bug). `ListPreference` pairs `entries` with `entryValues` **by index**, and the `*_values` arrays live only in `values/` because they aren't translatable — so a translated `entries` array that wasn't extended does *not* degrade to English. An item missing from the end is unreachable (the five colour harmonies shipped in 3.1-beta1 could not be selected in any of the twelve translated locales); an item missing from the middle silently shifts every later label onto the wrong value (picking "Square (sharp corners)" applied Frosted edges). So a new picker option means adding it **at the same index in all forty-four translated `strings.xml` files**, not just `values/`. `mobile/src/test/.../res/TranslatedArrayAlignmentTest.kt` pins this by comparing item counts per locale.

## Build & test commands

Requires JDK 21 and an Android SDK path in `local.properties` (`sdk.dir=...`, gitignored — Android Studio creates it on first sync). After cloning, run `git submodule update --init` before building (see `wearutils/` above).

**There is no `java` on this machine's `PATH`.** `./gradlew` works only because `.claude/settings.json` sets `JAVA_HOME` to the unpacked JDK (`~/jdks/jdk-21.0.11+10`). Gradle picks that up, but anything invoking a JDK tool *directly* — `keytool` to check signing certs, `javap` to inspect a library class, `java -version` — must use the absolute path under `$JAVA_HOME/bin/`, or it fails with "command not found" rather than anything that names the real cause. `apksigner` likewise lives in the SDK (`~/android-sdk/build-tools/<ver>/`), not on `PATH`.

Standard Gradle/Android workflow (run from repo root):

```
./gradlew assembleGithubDebug        # build phone + wear debug APKs (github flavor - the usual one)
./gradlew :mobile:assembleGithubDebug # build only the mobile module
./gradlew :wear:assembleGithubDebug  # build only the wear module
./gradlew test                       # run all JVM unit tests (every flavor)
./gradlew :mobile:testGithubDebugUnitTest --tests "*.StreamIntegerTest"   # single test class
./gradlew :wear:testGithubDebugUnitTest --tests "*.StemButtonsManagerTest"
./gradlew :common:testDebugUnitTest  # common-module tests (no flavors here)
./gradlew lint                       # Android lint across modules (see caveat below)
```

Both app modules have two **product flavors** on a `distribution` dimension: `github` (default —
`assembleDebug` alone resolves to it; carries the in-app self-updater) and `play` (the Play Store
build, self-updater and `REQUEST_INSTALL_PACKAGES` stripped — Google Play forbids self-updating
apps). See the *Update system* section and `docs/play-store-migration-plan.md`. Test and assemble
task names gain the flavor (`testGithubDebugUnitTest`, `assemblePlayRelease`, `bundlePlayRelease`);
`./gradlew test` still runs every flavor's suite. `common/` has no flavors.

`lint` is **not a usable gate right now**: the modules carry a large backlog of unrelated lint errors and the task aborts before reporting, which is why checks lint would otherwise cover (e.g. `InconsistentArrays`) are pinned as plain JVM tests instead. Don't treat a lint failure as a regression from your change without checking it against `master` first.

Unit tests live under `mobile/src/test`, `wear/src/test`, and `common/src/test` (JUnit 4). `wear/build.gradle` uses the `unmock` plugin to run certain Android-framework-dependent tests on the JVM instead of mocking — see the `unMock { ... }` block when adding tests that touch `android.*` classes in `wear`.

There is no instrumented/UI test setup in this repo currently, and **nothing runs the Gradle tests but you** — the one GitHub Actions workflow (`.github/workflows/publish-community-themes.yml`) publishes approved community themes on a daily cron and never builds or tests the app. Treat `./gradlew test` as a manual gate.

Two Node suites sit outside Gradle and are not reached by `./gradlew test` (both need Node ≥20):

```
npm ci --prefix firebase && npm test --prefix firebase                       # Firestore rules, against the emulator (needs JDK 21)
npm ci --prefix .github/community-theme-publisher && \
  npm test --prefix .github/community-theme-publisher                        # publisher + Android/Node schema parity
```

The testing convention that makes that workable: whenever a decision is subtle enough to have caused a bug, it gets **extracted into a pure function with no Android dependencies** and pinned by a JVM test, rather than being tested through the Android class that calls it. `BackgroundLayerStack.parse`/`implicitStack` / `resolveServiceHold` / `resolveReportedSession` / `RotaryAction.resolve` / `PausedHoldPolicy.holdMillis` / `IdleScreenAction.forButton` vs `forAutoOpen` / `LibraryEntry` / `MediaSessionCapabilities.advertises` / `sizedArtworkUrl` / `ColorHarmony` / `SettingsSearchIndex.rank` / `QueueEntry` / `QueuePaging.nextLimit` / `BitmapBorderTrim.isUniformLine` / `PlaybackPositionEstimate` / `PlaybackSyncPolicy` / `PredictedTrackAdvance` / `QueueScrollPolicy.resolve` / `FaceRecency` / `LyricsParser` / `MusicGlyphs` / `AccentFloorStyle` / `TrackMetadataFields` are all this shape — note how many of them exist specifically to pin a *fallback* choice, which is where the bugs were. Prefer following it over adding mocks.

A second shape has grown out of that one: **tests that read the resource/registry files directly and enforce a structural invariant no single function owns**, living under `mobile/src/test/.../res/`. `TranslatedArrayAlignmentTest` is the localization one above; `AppearancePreferenceScopingTest` asserts that every key declared in `watch_face_settings.xml` is in `FaceScopedPreferences.SCOPED_KEYS`, because the Watch face screen *is* the appearance surface — an unscoped key there silently changes every face at once (how the mini-button row offset stayed global while its four siblings were scoped). Its `DELIBERATELY_GLOBAL` set is the escape hatch, and adding to it is meant to be the moment you stop and justify it. `SettingsCatalogTest` is the same shape for `SettingsCatalog` (see *Phone app UI*): every category declared in `settings.xml`/`watch_face_settings.xml` must appear in the matching category list or it is never assigned a page visibility and shows on all of them (how `cat_idle` ended up on every Settings page), and every listed category must be reachable from at least one section or its settings become unreachable. `FlavorSelfUpdateIsolationTest` (also in `res/`) pins the `github`/`play` split for the self-updater — that `src/main` and the `play` manifest carry no `REQUEST_INSTALL_PACKAGES`, no update components and no updater code, all of which is enforced only by which source set the files sit in. `ScopedAppearanceRegistryTest` (in `common`) is the registry-side counterpart to the first of those: every key in `FaceScopedPreferences.SCOPED_KEYS` must also be in `MiscPreferences.EXPORTABLE`, since `WatchPreferenceSyncCoordinator` filters on that registry and `SCOPED_DEFINITIONS` is the intersection — omit it and the phone stores the value, the phone's own preview reads it back and looks completely correct, and the wrist never hears about it while no saved theme can capture it. `CommunityThemeDefaultsParityTest` extends the shape across a language boundary — it and the Node `defaults-parity.test.mjs` read the same checked-in fixture, so the Kotlin schema and the publisher's JS mirror of it cannot drift apart unnoticed. Two more pin decisions that live only in XML and would otherwise be re-litigated by the next edit to a layout: `ThemeUiResourceContractTest` asserts the theme-library UX contracts — the removed destructive "apply to all faces" action stays absent from `watch_face_settings.xml`, every indeterminate community-theme wait uses `MusicLoadingBarsView` and never a stock `<ProgressBar>` (the house animation rule under *Modernization roadmap*), the installed marker is an icon rather than badge text, and the community dialogs go through `AlertDialog.Builder` + `applyLyraDialogStyling` rather than `MaterialAlertDialogBuilder` — while `CommunityThemeTranslationTest` requires every gallery string to exist in every supported locale, since an opt-in screen that falls back to English is the kind of gap nobody testing in their own language ever sees. `WatchPreviewParityTest` is the one that reaches across into `wear/`: the Watch tab's miniature re-implements all twenty-one faces in Canvas because `mobile` cannot depend on `wear`, so ~11,400 lines of preview mirror ~9,000 lines of Compose by hand and every failure it has produced is silent in the same way — the preference moves, the miniature does not, nothing throws, and the one screen built to show what a setting does is the one place it appears not to work. It pins four things: every face in `ThemeAppearance.ALLOWED_BASE_FACES` and every value in `wear_aod_style_values` has a branch in the preview's dispatch (a missing one silently falls through to Classic); every visual key on `watch_face_settings.xml` is actually read inside `readPreferenceSnapshot` — scoped to that function deliberately, since a key also appears in `surfaceForPreference`'s routing table and a file-wide search passes for a key that is routed to a surface and then never read; no `private fun draw*` is unreachable, which is the exact shape both `drawAdaptiveTitle` and the per-face AOD renderers took (written, documented as the path every face used, never wired to the dispatch, so the setting they implemented did nothing); and no face geometry has been re-declared as a literal instead of read from `common/.../FaceGeometry.kt`. That last one used to be a value-by-value comparison of two copies; the copies are gone. `mobile` cannot depend on `wear`, which was true and beside the point - `common` is a dependency of *both*, so the numbers a face and its miniature share now live there once and the drift is impossible rather than merely checked. What remains possible is someone writing `.52f` back into a face because the shared name was not obvious, so the rule the test keeps is the structural one. Its two escape hatches are kept apart on purpose — `NOT_PREVIEWABLE` is a decision (behaviour with nothing to draw) and `KNOWN_GAPS` is debt, and a guard fails the moment the preview starts reading a `KNOWN_GAPS` key so the entry cannot outlive the bug. **`mobile/build.gradle` declares the wear face directory as a test input**, next to the `src/main/res` line that exists for the same reason: nothing else connects the two modules, so without it editing a constant on the watch leaves the task `UP-TO-DATE` and the drift is reported only on a clean build. All of them fail with an explanatory message naming the offending file or key, so read the failure rather than adjusting the expectation.

To sideload builds onto real devices, `serve_apk.py` (repo root) serves the assembled mobile/wear APKs over HTTP on the local network (**port 8760**), build first, then `python3 serve_apk.py` and download from the phone/watch browser. It serves the `github` debug/release APKs, the `play` debug APKs (for checking that build on a device), and the `play` release `.aab` bundles (the Play Console upload).

## Signing

Release signing is pulled from an optional `keystore.properties` file at the repo root (not checked in; keys `storeFile`/`storePassword`/`keyAlias`/`keyPassword`) — see the `afterEvaluate` block in the root `build.gradle`. Note the shape, which is not the usual one: neither module declares a `release` signing config at all. Both `mobile/` and `wear/` point their release build type at `signingConfigs.debug`, and the root `afterEvaluate` **rewrites that debug config's credentials in place** when `keystore.properties` exists. So the file's presence re-signs *every* variant, debug included — which is what lets a locally built `assembleDebug` update an installed release build in place and still talk to it over the Data Layer. Without the file, everything falls back to the real debug key and release APKs are debug-signed. `release.keystore` sits at the repo root too and is gitignored via `*.keystore`; it is the *one* key both APKs must share (see "Package naming gotchas"), so losing it means no user can ever update in place.

For the planned paid Play Store listing (`docs/play-store-migration-plan.md`), the decision is that **`release.keystore` becomes the Play _app signing key_** (uploaded to Play App Signing, not just an upload key). That keeps Play-delivered installs signature-identical to sideloaded ones, so an existing sideload user updates in place from GitHub → Play rather than having to uninstall/reinstall, and future GitHub releases stay update-compatible with Play. Phone and watch are **one** Play app (same `applicationId`, one listing, one price covering both devices), so they share that key and the Data Layer keeps pairing.

## Package naming gotchas

The app was renamed from Music Center for Wear (fork of matejdro/WearMusicCenter): all code now lives under `com.svartifoss.snfell` / `com.svartifoss.snfell.common`. Older docs/commits referencing `com.matejdro.wearmusiccenter` mean the same code.

- **The three modules nest differently, and `mobile/` is the odd one.** `common/` is under `com.svartifoss.snfell.common.*` and `wear/` under `com.svartifoss.snfell.watch.*`, but phone code sits at the *bare* root `com.svartifoss.snfell.*` with no module segment — there is no `.mobile` package. So the `mobile/.../music/QueueArtworkResolver.kt` shorthand used throughout this file expands to `mobile/src/main/java/com/svartifoss/snfell/music/QueueArtworkResolver.kt`, and guessing a symmetric `…/snfell/mobile/…` path will miss every time. A few phone classes (`WearMusicCenter`, `WatchListenerService`, `NotificationService`, `WatchPreferenceSyncCoordinator`) sit loose at that root rather than in a subpackage.
- Despite living in `wear/`, the watch-side code is under the package `com.svartifoss.snfell.watch.*` (not `.wear.*`) - that's the Gradle `namespace`, used for generated R/BuildConfig classes only. All watch-side classes (`PhoneConnection`, `WatchMusicService`, `MainActivity`, etc.) are in subdirectories named `watch/communication/`, `watch/view/`, `watch/model/`, `watch/config/`, `watch/util/`.
- The Gradle **`applicationId`** **must be identical** in `mobile/` and `wear/` (both `com.svartifoss.snfell`) and both apps must be signed with the same key. The Wearable Data Layer API (`MessageClient`/`DataClient`) only routes messages/DataItems between a phone app and a watch app that share the same `applicationId` — a mismatch means the two apps never connect and both report "No watch connected". (This regressed once: the wear app was briefly given `com.svartifoss.wrfell` for a separate Play Store listing, which broke all phone⟷watch communication.) Both apps therefore ship as same-key sideloadable APKs — the identical `applicationId` is a Data Layer requirement, not a store one. `MainActivity.openWatchPlayStorePage()` (mobile) still opens `market://details?id=<WEAR_APPLICATION_ID>` (== the phone package), but with the app no longer on the Play Store this path is effectively **vestigial**; regardless, `WEAR_APPLICATION_ID` must still equal `wear/build.gradle`'s `applicationId`.
- `mobile/` still contains one deliberately un-renamed package: `com.matejdro.wearvibrationcenter.notificationprovider`. This isn't just a name to preserve — it backs a **functioning notification-access interop subsystem** (`mobile/.../notifications/NotificationProvider.kt` plus the AIDL contract in `mobile/src/main/aidl/com/matejdro/wearvibrationcenter/notificationprovider/`) that lets the separate Wear Vibration Center app read notifications through Svartifoss. Renaming the package would break that cross-app AIDL binding.
- The `wearutils/` submodule keeps its own `com.matejdro.wearutils.*` packages.

## Modernization roadmap

`docs/wear-modernization-plan.md` contains the full phased modernization strategy: Foundation (targetSdk bump — now at 35 — and deprecated API cleanup) → MediaSession mirror (watch-side `MediaSession` that forwards controls to the phone) → Tiles & Complications → in-UI navigation. Consult this doc before making architectural decisions in `wear/`.

**Current state (merged to `master`):** `WatchMediaSession` is implemented and active (Phase 1), and the Phase 2 Tiles & Complications surfaces exist: two Tiles (`watch/tile/`, built with `androidx.wear.protolayout`/`androidx.wear.tiles` — `MediaTileService.kt` for track info/transport/seek, and `ShortcutsTileService.kt` rendering the synced playlist-shortcut custom list as tappable chips, each dispatched through the invisible trampoline `ShortcutLaunchActivity`, because a Tile `Clickable` can only start an Activity — never send a Data Layer message — so it re-performs the same open-URI-on-phone + `MESSAGE_CUSTOM_LIST_ITEM_SELECTED` pair the watch menu does, see *Actions system*) and a complication data source (`watch/complication/AlbumArtComplicationDataSourceService.kt`, `androidx.wear.watchface` complications). Because these run outside the main app UI lifecycle, they fetch music state directly over the Data Layer via `CommPaths` rather than through `PhoneConnection`; the manifest-registered `MusicStateListenerService` (`watch/communication/`) requests a Tile + complication refresh whenever the phone publishes new music state — `WatchMusicService` does the same while running, but it idle-times out, and without this listener the surfaces froze on stale state. It also revives a dead `WatchMusicService` when the received state says music is playing (the phone only sends `MESSAGE_START_SERVICE` on a playback-*start* edge, so a service that died mid-playback would otherwise stay dead). A sibling `ConfigListenerService` (`watch/communication/`) does the analogous job for the button-config (`/Actions/*`) and action-menu (`/ActionList`) DataItems: those have no other always-on delivery (they arrive only through `PhoneConnection`'s runtime `DataClient` listener, live only while the connection is active), so a config edited on the phone while the watch is idle used to apply only after the user woke/tapped the watch. The manifest listener posts the frozen `DataItem` into `PhoneConnection`'s config `LiveData` — which the `WatchActionConfigProvider`/`WatchActionMenuProvider` observe with `observeForever` — so an open now-playing screen re-decodes and applies the change with no interaction.

Jetpack Compose for Wear OS (`wear.compose.material3`) is enabled in `wear/build.gradle` and used for `QueueActivity`/`QueueScreen` (`watch/view/queue/`) and `MenuActivity`/`MenuScreen` (`watch/view/menu/` — the actions/custom-list menu, which replaced the old `WearableDrawerLayout` bottom drawer; `MenuActivity` is a pure picker that returns the selection for `MainActivity` to execute). Shared Compose chrome (curved clock, scroll indicator, the pulsing `EqualizerBars`) lives in `watch/view/compose/WatchScreenChrome.kt`; those three bars are the app's single "something is happening" animation — the queue's now-playing marker, its "Load more" row, and (as `LoadingBars`, the same drawing at standalone size) every loading state in the watch app. The phone mirrors that vocabulary through `mobile/.../view/MusicLoadingBarsView.kt`, backed by the same animated-vector resources in `common/src/main/res`, for indeterminate waits in its View-based screens. An arc spinner filled the last role and was dropped for being a second vocabulary: a generic platform shape inside a screen that already had a house animation for exactly this, and one that reads as *audio*. The bars carry deliberately non-harmonic periods (480/360/560 ms) so they do not beat in step and read as one block breathing. Compose draws all three in **one** `Canvas` with the animated values read inside the draw lambda — animating each bar's `fillMaxHeight` re-ran layout for the whole row every frame and genuinely did cost the queue its scroll budget — while the View implementation explicitly starts and stops its `Animatable` as visibility changes so recycled or hidden rows cannot leave infinite animators running; design constants for all three UI stacks live in `watch/theme/WatchTheme.kt` — including the typography catalog: `MiscPreferences.WEAR_FONT` picks the track title/artist typeface via `watchFontFamily()` (system families plus bundled fonts — retro typewriters, Google Sans, Poppins, Montserrat, Marcellus, Bebas Neue, Playfair Display, Space Grotesk, Orbitron, Caveat, Inter, Atkinson Hyperlegible, Rubik, Barlow Condensed, Oswald, Lora, Fraunces, Space Mono, Archivo Black and Dancing Script). The phone's half of that mapping lives in `mobile/.../view/settings/WatchFontCatalog.kt` — extracted out of `WatchPreviewView` so the *picker* can render each option in the font it names — so a new font key means three places in step: `watchFontFamily()`/`watchFontTypeface` on the watch, `WatchFontCatalog`, and the `wear_font_entries`/`wear_font_values` arrays. A bundled font must be dropped into **both** `mobile/src/main/res/font/` and `wear/src/main/res/font/` (the preview and the watch each load their own copy) with its license text added under `licenses/<font>/`, with a direct catalog mapping for each selectable family. `WEAR_FONT` styles only the track title and artist unless `MiscPreferences.WEAR_FONT_ALL_SCREENS` is on, which extends it to the menu, the queue and the shared Compose chrome. `WEAR_FONT` is the *global* family, and five elements can each override it with a catalog key of their own — `WEAR_TITLE_FONT`, `WEAR_ARTIST_FONT`, `WEAR_CLOCK_FONT`, `WEAR_LYRICS_FONT`, `WEAR_TRACK_TIME_FONT`, all face-scoped, all resolved by a `WatchTypography.*FontKey` function taking the same shape. Every one of them defaults to the sentinel `"follow"`, and an empty or *unknown* value resolves the same way as `follow` rather than to a fixed family, since the value can arrive from an imported backup or a newer build and reverting someone to Google Sans is the more surprising answer. **What `follow` falls back *to* is a per-element decision, and it is deliberately not uniform.** Title and artist follow the global `WEAR_FONT`. Clock and lyrics follow the resolved *track* family. Playback time alone returns `null` — meaning "keep the family this face authored" — because some faces deliberately set that readout in something other than the track font, so inheriting would overwrite a design rather than preserve one. Lyrics are the case worth reading `lyricsFontKey`'s comment over: a first pass had `follow` keep each surface's own designed font (the UI font on the lyrics screen, Marcellus on Verse), which preserved every existing theme perfectly and in doing so preserved the actual complaint — change the theme's typeface and the words of the song were the one thing that did not follow, which is indistinguishable from the control not working. Verse's serif is still one tap away as an explicit choice. Resolution runs through the same `WatchTypography` functions on both sides, and all five keys are face-scoped like the rest of the appearance keys, so a saved theme carries them. Music-note characters inside lyric text are drawn as the Svartifoss mark rather than as text: lyric files are full of `♪`/`🎵` and most of the font catalog has no glyph for them, so they arrived as a fallback face, the wrong weight, or tofu. `common/.../MusicGlyphs.kt` decides what counts as a note and where the boundaries fall in a string (pure, JVM-tested); `watch/view/compose/MusicNoteText.kt` does the rendering, since only Compose can put an image inside a line of text.

New watch UI work should prefer Compose; the legacy View-based `MainActivity` (now-playing screen) remains, but its central rendering is now a swappable **now-playing face** (`watch/view/face/NowPlayingFace.kt` — a state-in/events-out contract, selected by `MiscPreferences.WEAR_SCREEN_FACE`): "classic" is the original View presentation (MainActivity itself is its implementation), "expressive" is a Compose face (`watch/view/face/ExpressiveFace.kt`, mirroring the Material 3 Expressive system media controls: cookie play/pause button, contour-following progress ring, round tonal transport buttons, accent-tinted/vignetted backdrop; queue/volume/menu access is left entirely to the user's configured mini buttons and gestures — there is no fixed default glass trio, so there's never a second, conflicting set of shortcuts), and the remaining keys — "vinyl", "poster", "studio", "halo", "aurora", "eclipse" (true-black AMOLED), "spectrum" (animated per-track bar field), "material" (capsule/tonal-surface treatment), "immersive", "depth" (three parallax layers) — are the **curated player collection** in `watch/view/face/CuratedPlayerFaces.kt`, which replaced the old standalone `VinylFace.kt`/`PosterFace.kt` Beta faces; "carousel" (a full-bleed cover rail, card silhouette from `common/.../CoverShape.kt`) is big enough to live in its own `watch/view/face/CarouselFace.kt`, as is "chat" (`watch/view/face/ChatFace.kt` — the session as a messaging thread: a title and artist bubble per played track, the current one as a wide right-aligned voice-message bubble with the cover as avatar and the waveform doubling as the progress bar). Four things about it are load-bearing. Its thread lives **in the face**, session-scoped, deliberately not from `CustomLists.HISTORY` (a persisted, user-deletable list) nor `queueCards` (what has *not* played yet) — neither answers "what this sitting played, in order", so either would show rows the user never heard; it appends inside a `LaunchedEffect`, not in the composable body, since growing a `mutableStateListOf` that the same composition reads is a write-during-composition. It filters status text out of that thread using `NowPlayingFaceState.titleIsStatus`/`artistIsStatus` (fed from the host's `titleLineIsStatus`), which exist precisely because a face that *accumulates* metadata would otherwise record "ERROR" or "Playback Stopped" as a track that played — and the strings can't be matched on, being localized into 14 languages. Its gestures hang off a large **centre region** rather than a control, because `binding.centerTapZone` is `View.GONE` for every Compose face (the `composeFace` branch in `MainActivity.applyScreenFaceNow`) so a face that wires nothing has no working centre at all — and the voice bubble is deliberately *not* clickable, since sitting over that centre and taking taps is exactly what broke play/pause in the first version. Finally it is the one curated face with a fixed action row, and that row is where it **hosts** the mini buttons rather than letting the shared View row float over them: `MiniButtonPlacement.isHostedByFace` (the one registry all three consumers read) makes `MainActivity` suppress the row and hand the face the configured slots through `NowPlayingFaceState.miniButtons`, so Chat draws one circle per configured slot, sized to re-fit for a third, each running that slot's own tap and long press. With nothing configured it falls back to the pair it has always had (queue + skip next) — the thread occupies that band, so it would otherwise ship with no shortcuts at all. The consequence to keep straight is which half of the mini-button settings reaches a hosted row: the *appearance* does (background style through `MiniButtonSurfaces`, group opacity), the *placement* cannot (the composition places them), so `WatchFacePrefsFragment` hides the curve and shape pickers for a hosting face rather than leaving pickers that change nothing — the rule Carousel's card shape already follows. It therefore no longer defaults the row off (only the edge arc), since defaulting it off would hide the buttons from the one face built to show them; `FaceScopedBooleanDefaultTest` pins that. "verse" (`watch/view/face/VerseFace.kt`) puts the song's *words* on the main screen - the line before, the line now and the line next - fed by `watch/view/lyrics/LyricsFeed.kt`, which `MusicViewModel` enables only while this face is selected (the lookup is a phone-side network call per track, so no other face pays for it). Its lyric lines are set in a serif, the one in the collection that is; everything ordinary about it - running head, elapsed time, the per-line progress hairline - goes through the shared text/progress helpers, because a face designs its own *composition*, not its own settings. A track with no synced lyric is the common case, not a failure, so it falls back to a title card rather than an error. "split" (`watch/view/face/SplitFace.kt`) is the notification-card layout: cover in the top band, a solid album-coloured panel below holding artist over title, and the source-app icon as a round badge straddling the seam. It is the only face that **paints its own opaque backdrop**, so the Album background styles have no effect on it by construction — the two-tone composition *is* the treatment, and letting the host's full-screen artwork show through would erase it (it still honours `albumArtHidden`). That is precisely why its panel has a control of its own, `common/.../SplitPanelStyle.kt` (`wear_split_panel`, face-scoped, JVM-tested): without one there is no way to change that half at all. `BLUR` (the default) lays the cover across the **whole screen** and clips the blurred copy to the panel rather than scaling a second copy into it — fitting it to the lower box would crop it differently and the seam would read as two unrelated pictures instead of one going soft. It composites artwork *over* an opaque panel (`PANEL_ART_ALPHA`), not a colour wash over artwork: the same blend either way, but this order keeps the panel's luminance anchored to `panelArgb`, which is the value `AdaptiveTextContrast.prefersDarkText` decides the text colour from. It blurs through the shared `BitmapBlur` rather than Compose's `Modifier.blur`, which is a no-op below Android 12 and would leave older watches a sharp photograph — a different design, not a degraded one. `WatchPreviewView.drawSplitPlayer` mirrors all of it. Its text colour is decided, not assumed: the panel is the album's colour and can land anywhere from near-black to near-white, so both it and the badge glyph run through `AdaptiveTextContrast.prefersDarkText`, whose `relativeLuminance` is hand-rolled free of `android.*` precisely so the phone preview and the watch make the identical call from a JVM-tested function. "note" (`watch/view/face/NoteFace.kt`) is the minimal one: a black backdrop (its `defaultForFace` is `HIDDEN`), a small cover disc and one centred `Artist: Title` sentence built as a single `AnnotatedString` so it wraps as a sentence rather than as a label and a value. Its disc is cut to `wear_note_cover_shape`, the second consumer of `common/.../CoverShape.kt` (Carousel's `wear_carousel_card_shape` is the first) — one shape vocabulary, two keys, because a rail of cards and a thumbnail beside a line of text want opposite answers from it and one shared value would make choosing for either restyle the other. It keeps its mini-button row (it leaves the bottom band free, so that row is the only way to reach anything) but still defaults the edge arc off. It also draws its cover disc regardless of `albumArtHidden` — the one departure from the convention that a small cover is decoration a "hide artwork" background may remove, because its own default backdrop *is* that style and honouring the flag would ship the face permanently empty. "metadata" (`watch/view/face/MetadataFace.kt`) inverts the collection's premise: every other face is built around the artwork and treats the tags as a caption, this one shows a small cover and then as much of the record's actual detail as the screen holds — fed by the on-demand path in *Lyrics and track metadata* above, so no other face pays for it. Split and Verse share `FaceScopedPreferences.SELF_COMPOSED_FACES` (mini-button row and edge arc off), with `SPLIT_DEFAULTS`/`NOTE_DEFAULTS`/`VERSE_DEFAULTS`/`CHAT_DEFAULTS` layering each face's own on top (Chat left that set when it began hosting the row — it keeps the edge arc off and nothing else); all of them hang their gestures off the shared `CenterGestureRegion` in `FaceChrome.kt`. "artist" (`watch/view/face/ArtistFace.kt`) inverts what the collection is built around one more time: the backdrop is a picture of the **performer** rather than the sleeve, the largest type is their name with the source mark in front of it as a bullet, and the track sits a step below at what is elsewhere the artist's size. Four things are load-bearing. **The face neither fetches nor paints that picture.** The host substitutes it for the album cover in the one artwork pipeline before the face runs (`MainActivity.resolveBackdropArtwork`, fed by `phoneAlbumArt`/`phoneBackdropArt`), which is what makes every background style, artwork filter, shading layer and accent floor apply to it — and what makes the album-accent palette, the clock included, resolve from the picture actually on screen instead of a sleeve nobody can see. Painting it in the face would have cost all of that; Split's opaque backdrop is the documented exception, not a precedent. **Which picture is a *source*, not a treatment,** and the two are separate controls: `common/.../AlbumArtSource.kt` (`wear_album_art_source`, face-scoped, JVM-tested - local/online/artist plus the two device-local sources `custom_image`/`custom_folder` covered under *Community themes*, unknown values resolving to `local` because that is the only one that needs neither a network request nor a file this device may not have) decides *which* picture, while `ALBUM_ART_STYLE` keeps deciding how it is treated. It briefly was a value inside the style enum, which meant choosing the photograph forfeited every treatment and choosing a treatment forfeited the photograph. **The lookup is the app's only network call made on behalf of a purely visual choice:** `mobile/.../music/OnlineArtworkFetcher.kt` queries Deezer's keyless `search?q=` (the source Retro Music and its forks use — Android has no artist images anywhere: not MediaStore, not `MediaMetadata`, and a player that shows them keeps them in private storage), caching through `OnlineArtworkCache` in `cacheDir` for `RemoteArtworkCache`'s reason. One response carries `album.cover_xl` and `artist.picture_xl` side by side, which is why both sources cost the same single request. That cache stores a **miss** as well as a hit, or an artist Deezer has never heard of is re-queried on every track of their album; `MISS_TTL_MS` keeps a dropped connection from becoming permanent. The bytes travel as `CommPaths.ASSET_BACKDROP_ART` beside the cover - one asset for both sources, since the watch's only question is "is there a backdrop other than the cover" - with `MusicState.hasBackdropArt`/`backdropArtPending` distinguishing the three states the watch must not confuse — *nobody asked*, *still looking*, *asked and there is none* — since only the last means "fall back to the cover now" and treating the middle one as final blinks the backdrop on every track change. **The artist line is the big one, and it goes through `ArtistLineText` like every other face's.** That helper now owns the overflow modes itself (`MiscPreferences.WEAR_ARTIST_TEXT_MODE`, delegating to `AdaptiveTitleText` for anything but `static`), which is what let this face drop its own machinery. Reading the *title's* mode here is what made a long name wrap to two lines: that key defaults to `smart`, whose cascade ends in a wrap, where the artist line has always been one line. The artist picker offers only the three single-line modes, because every face reserves exactly one line for the credit. And it paints **no scrim of its own** - legibility over artwork is the shared shading stack's job, and a scrim welded into one composition is a second, unremovable answer to a question the user already controls. Its block measures the round screen's real chord through `RoundScreenText` at the depth the *placement controls* put it, not at the depth it was drawn; and its `CenterGestureRegion` is a fraction of the screen (`FaceGeometry.Artist.CENTER_REGION_FRACTION`), never `screen` - that region *consumes* touches, so a full-screen one silently disables the quadrant taps, the swipes and the mini-button row underneath.

**Where a face's block of track text sits is a user choice on every face, and the `follow` sentinel is what makes that safe.** `common/.../TextBlockPlacement.kt` (pure, JVM-tested) decodes `wear_text_block_align` (start/center/end) and `wear_text_block_position` (top/middle/bottom), both face-scoped and both defaulting to `FOLLOW` — *keep the composition this face authored*. That default is why the two rows can be offered on all twenty-two faces rather than on a hand-kept allow-list the way `wear_title_centered` is: no saved theme and no published community theme changes appearance because the keys now exist, and a face whose text position is its identity is untouched until someone deliberately overrides it. Faces never switch on the enums. They pass what they designed to `FaceChrome`'s `blockAlignment`/`blockTextAlign`/`blockArrangement`/`blockPlacement` and draw what comes back, so the fallback lives in one place instead of at every call site — the arrangement whose absence caused both the title effects that defaulted to null and were never opted into, and the artist lines that styled a bare `Text`. Two halves are needed and both are wired: `blockTextAlign` is applied *inside* `AdaptiveTitleText`, `ArtistLineText`, `TitleLineText` and `TrackTimeText` at the point each hands an alignment to a `Text`, so no call site can opt out by accident; and the **container** must follow too, since a wrap-content line has no spare width for an alignment to act in — hence `blockAlignment`/`blockPlacement` on each face's own text Column. The View faces (Classic, Matejdro) are anchored from `MainActivity.applyClassicTextPlacement`, which moves gravity only and never the row order or the band geometry. `WatchPreviewView` mirrors it through `blockAlign`/`blockAnchorXFor`/`blockAnchorY`, and there the override applies **only where the face designed a centred line**: Compose gets alignment free from a filled `Text`, but a `Canvas` draws from a point, and a face that already anchors to an edge (Chat's bubbles, Note's sentence) passes its own x that must not be shifted by half a band.

**A per-face default only works if both overloads resolve it.** `FaceScopedPreferences.getString` and `getBoolean` must walk the identical four steps (explicit `key@face` → `perFaceDefault` → legacy global → definition default). The boolean one has now dropped the `perFaceDefault` step **twice**, and the failure is quiet and specific: the phone data store consults it on both, so the settings switch shows the face default while the watch shows the definition default, and the only way a user can reconcile them is to toggle the switch — which writes an explicit `key@face` and hits the one branch that always worked. `FaceScopedBooleanDefaultTest` pins it. Curated faces share one interaction contract: the single visual focus toggles play/pause, double-tap opens quick actions, long-press opens the queue; previous/next/menu/volume are deliberately left to the configurable mini buttons and gestures. Their gradients/progress/accents come from album-art-derived palettes (`watch/theme/AlbumPalette.kt`), and each ships a dedicated ambient variant. All Compose faces render in the single `ComposeView` (`composeFaceKind` picks which) layered between the gesture layers and the overlays, keep the expressive face's bottom pill-trio geometry so the shared mini-buttons/quick-panel fit unchanged, ship their own outline AOD variant (AOD "follow" maps each Compose face to itself), and share small building blocks via `FaceChrome.kt`. A new face key must also be added to `ThemeAppearance.ALLOWED_BASE_FACES` (the canonical registry both sides validate against — also the source the on-watch picker's `WatchFaceCatalog` derives from, so a face registered there cannot go missing from the picker), the phone's `wear_screen_face_entries/values` arrays, `WatchThemeRepository`'s face-name map, `MainActivity`'s `composeFaceKind` list *and* its `when` that constructs the composable, the visual-AOD-face set in `WatchFacePrefsFragment.updateAodDetailVisibility`, and given a miniature in `WatchPreviewView` (which carries several `when` branches keyed by face — grep the key of an existing curated face to find them all). Four copies of the registry live outside Kotlin and each fails silently in its own way, so a face reaches them too: the `originalityApplicableFaces` lists in `common/src/main/assets/community-theme-constraints.json`, the literal list in `firestore.rules`, `ALLOWED_BASE_FACES` in the publisher's `schema.mjs` (whose `defaultSettingsForFace` must also mirror any `perFaceDefault` the face declares), and `docs/admin/admin.js` — plus the shared `common/src/test/resources/community-theme-defaults.properties` fixture, which is what makes the Kotlin and Node halves provably agree. The face *count* is also written out in prose in four user-facing spots that no test pins — `README.md` twice (the screenshot caption and the **Twenty-one now-playing faces** feature row, which also *names* the faces) and `docs/index.html` twice (the hero paragraph and the faces-wall heading; note its stats strip does carry a hardcoded "Watch faces" tile) — so update all four with the registry.

**Not every face is a Compose face, and `matejdro` is the proof.** It is the homage to matejdro's WearMusicCenter, the app this one is a fork of, and it is deliberately the *second View face* rather than a twenty-first Compose one. The reason is a single line in `applyScreenThemeNow`: for any face in `composeFaces` the four quadrant hint icons are forced `GONE`, and those icons *are* the original's control surface, so rebuilding it in Compose would have lost the one thing it exists to preserve. Nothing in `wear/` tests `screenFace == "classic"` — the whole module branches on `screenFace in composeFaces` — so a second View face falls out of the existing structure: leaving it off that set gives it Classic's entire presentation (`classicTextBlock`, `playerBackground`, `centerTapZone`, the quadrant icons, the Classic AOD via `"follow"`), and `applyClassicBandGeometry` supplies the only difference, which is the composition itself: artist and title as two *proportional bands* filling the block (`FaceGeometry.Matejdro`) instead of a centred wrap-content group. That band is also why `OutlineTextView.fitsWithinViewHeight` exists — `fitsWithinLineLimit` deliberately ignores the view's height because on a wrap-content line that height is a consequence of the size, which is not true of a fixed band, and without the opt-in the cascade picks its ceiling for a short title and lets the band clip it. Everything else about how the original looked — white artist line, the system typeface (`"roboto"`; the original bundled no font and set no `fontFamily`, so the homage ships nothing and adds no licence), no progress, no mini buttons, no source badge, no track time, the evenly darkened cover — is an ordinary preference, shipped as `FaceScopedPreferences.MATEJDRO_DEFAULTS` and pinned by `MatejdroFaceTest`. It is deliberately absent from `PlayerEditorModel.TITLE_CENTERED_FACES` (its bands already fill the text area, so the anchor has no slack to use and `applyClassicTitleAnchor` skips it) and present in `CONTROL_STYLE_FACES` (it draws Classic's quadrant hints through the same branch). Two things about it were got wrong first time and are worth not repeating. Its text area is Classic's, with **no margin of its own**: `music_screen_text_margin` is 30dp in `values` and **0dp** in `values-round`, so reading the first alone and forcing 30dp everywhere added that margin on top of the `BoxInsetLayout` inset and made every line visibly smaller than the face being reproduced — the phone miniature shares the same `classicTextInset` for exactly that reason. And the band has to be given to the *line*, not to the row around it: `text_artist` sits inside `classic_artist_row` (this app's addition for the source mark, which the original had no equivalent of), and leaving it `wrap_content` there left the sizing cascade with a width that was whatever the text already measured and a height that was a consequence of the current size, so the artist could never grow into the band. It is also **archived** (`ArchivedFaces.KEYS`) — a period piece rather than a daily face — which is not a cosmetic flag: the community base-face registries are "allowed minus archived", so moving a face in or out of that set means adding to or removing it from `firestore.rules`, `schema.mjs`, `docs/admin/admin.js`, the constraints asset's `originalityApplicableFaces` lists **and** the shared defaults fixture, all five together. They were left stale at "eleven" through two releases before being corrected for 3.1; the drift is invisible until someone reads the docs. **A face is an assembly of pieces, not a monolith.** The distinction that matters: a face owns its *composition* - what goes where, at what size, in what shape - and never its *settings*. Concretely, every Compose face must render its backdrop through `PlayerBackgroundTreatment(state)` — one composable, which walks the whole ordered background stack in a single Canvas (Split alone calls `PlayerBackgroundLayers(state)` after its own opaque panel) — rather than painting its own; must take its title colour from `titleTextColor(state, designed)`, its artist colour from `state.artistColor`, its fonts from `state.titleFont`/`state.artistFont` and its typography from `state.titleTypography`/`state.artistTypography`; and must route any progress element through `state.progressColor`. Painting `.background(Color.Black)` on the root is the specific mistake to watch for - it silently makes every one of the ~20 Album background styles, the blur radius, and the whole shading group render as a black screen on that face. Carousel had exactly that bug and its fix is recorded in its own source; Verse shipped with it and was corrected the same way. The counterpart rule is that a distinctive *treatment* belongs in a shared registry so any face can wear it and a custom theme can save it - `common/.../AccentFloorStyle.kt` (the accent wash pooled along the bottom edge — `MiscPreferences.WEAR_ACCENT_FLOOR`, off everywhere but Verse; drawn by `watch/view/compose/AccentFloorGlow.kt` as one entry in the stack `PlayerBackgroundTreatment` walks, so it lands above the backdrop and below the content — and, since 4.0, at whatever depth in that stack the user put it, its falloff a function of distance from the *centre* because a flat vertical gradient cuts a chord across a round display and reads as a rectangle behind the bezel) is the worked example: it was extracted out of the lyrics screen and the Verse face precisely because a treatment welded into one composition cannot be put on another. Deliberate exceptions exist and are documented at their sites (Split's opaque two-tone backdrop, Note's cover disc, Expressive's and Material's always-drawn rings, Chat's waveform), but each one costs a user a preference, so adding to that list is a decision, not a shortcut. A face whose defaults fight the standard chrome gets an entry in `FaceScopedPreferences.perFaceDefault` instead of special-casing at the draw site — `SELF_COMPOSED_FACES` (Split, Verse) turns the mini-button row and the edge progress arc off, because those two compose the whole screen edge to edge and the shared chrome lands *on top of* the composition rather than beside it. Hosting the row (Chat, above) is the other answer to the same collision and the better one where a face already has somewhere to put the buttons: the chrome stops being something to hide and becomes part of the composition. (Note these are defaults only: the keys stay face-scoped and switchable, and `perFaceDefault` returns `String?` for every type, so a boolean default is the string `"false"`.) Faces retired for known problems go into `ArchivedFaces.KEYS` (`common/.../ThemeAppearance.kt`; `view/watchface/theme/WatchThemesActivity.kt` keeps a `typealias` so the phone's call sites stay put) rather than being deleted: that one set hides them from both the face picker and the Watch-themes list, which used to keep separate copies and drift, and the developer "Show archived options" switch reveals them. All input handling (quadrants, swipes, stem, rotary, mini buttons, quick panel) is face-agnostic and stays in MainActivity; the hidden classic views keep being updated (ambient mode and the quick panel read from them).

**Colour treatments and typography** both resolve in `common` so the watch, the phone preview and the settings UI cannot disagree. `SurfaceColorTreatment` is the vocabulary (Normal/Desaturated/Expressive plus the harmony cases Complementary/Triadic/Analogous/Monochrome/Duotone); `ColorHarmony` holds the derivation math and `ColorModifier` (`wear_color_modifier`: none/vibrant/pastel/warm/cool) the orthogonal tone filter applied afterwards; `SurfacePaletteResolver.derive()` is the **single entry point** all three callers use — wear `MainActivity.resolveSurfacePalette`/`applyAccentColor`, `WatchPreviewView`, and `ColorTreatmentPreference`'s swatch dialog. Every treatment deliberately anchors its **primary** to the album's own hue and rotates only the companion slots, so switching treatments alone never changes the main accent; `wear_color_hue_shift` (0–359°, applied last inside `derive`) turns all three slots together, which varies that primary while preserving each harmony's internal angles. It is skipped for `NORMAL` — that colour was picked by hand, so rotating it would render something other than what the picker showed. Adding a treatment means a case in the enum + resolver and an entry in both `wear_color_treatment_*` and `wear_component_color_treatment_*` arrays; nothing else. Two rules the harmony math enforces and `ColorHarmonyTest` pins: a hue rotation is meaningless below `CHROMATIC_SATURATION_FLOOR`, so near-greyscale artwork degrades to a tonal ladder instead of yielding three identical greys; and a neutral source is never clamped up into the legible saturation band, which would invent a tint the cover never had. `WatchTypography` does the same job for the per-element title/artist controls (weight — a free 1–1000 value, not stepped — italic, scale, opacity, tracking, and `case` — [`TextCase`](common/.../TextCase.kt): Normal/UPPERCASE/lowercase, `WEAR_TITLE_TEXT_CASE`/`WEAR_ARTIST_TEXT_CASE`, applied last inside `AdaptiveTitleText`'s `String` overload and `ArtistLineText` so it always wins over whatever case a face's own composition already produced — plus source-icon scale/opacity), returning primitives so Compose faces, the classic View face and the preview's `Paint` each apply them their own way. `AdaptiveTitleText`'s `AnnotatedString` overload (Note's own) deliberately does not apply `case` itself — a generic transform over an already-built multi-span string risks shifting a span boundary if casing changes a run's character count (German ß→SS) — so Note cases its title and artist text before building either span, not after. **The artist line has one entry point on each side and neither is optional**: `FaceChrome.ArtistLineText` on the watch and `WatchPreviewView.drawArtistLine` in the preview. A face that styles a bare `Text` reads whichever of the seven controls it happens to name and silently drops the rest — which is exactly what happened: `ArtistLineText` was called from two sites in `CuratedPlayerFaces` while twelve bare `Text`s passed nothing but `state.artistFont`, so across most of the collection the artist weight, size, tracking and opacity moved the *title* and left the artist untouched, with the phone preview honestly mirroring a watch that was itself ignoring the setting; Chat's title bubble had the same gap in the other direction — it read only family, colour and size, so weight, tracking and case had nothing to move there either. `ArtistLineTypographyTest` (in `wear`) pins it as a source sweep, since what goes wrong is never the drawing but a call site opting out of the merge without saying so. **The title has the same rule and one more helper**, because it failed the same way twice: `AdaptiveTitleText` is the entry point for a title that owns its band (it may shrink, wrap or scroll to fit), and `FaceChrome.TitleLineText` — `ArtistLineText`'s exact shape, for the title — is the one for a title that does not, which is Chat's start-aligned bubble and Metadata's fixed two-line header. Both drew a bare `Text` before, so Chat pinned the weight to Bold and Metadata dropped size, tracking, case and opacity, while both looked wired up because family, colour and slant did work. `TitleTextEffectsTest` pins it with the same sweep and the same shape of exemption list. Its `ALLOWED_BARE_ARTIST_FONT` names every legitimate exception and they fall into three groups: the seven **ambient** variants (AOD is styled by `WEAR_AOD_*` and must *not* read the awake artist spec — that would be the bug in the other direction), the sites passing the artist family as a **track-time** face's authored family through `TrackTimeText`/`TrackFooter`, and the Metadata table's body rows. Two artist lines genuinely cannot use the helper — Chat's start-aligned bubble and Note's single `Artist: Title` sentence, where the artist is a span rather than a line — so they apply the spec inline and a second test lists every property each must keep carrying. Note deliberately shares the *title's* scale across the whole sentence: two independent sizes inside one run stop it reading as a sentence, which is the whole composition. **Every default is the exact identity, and identity means "keep what this face designed"** — weight 400 leaves a deliberately-bold face bold rather than flattening it to 400. AOD is deliberately *not* affected: it has its own `WEAR_AOD_*` controls. These controls live in the Watch tab's own **Typography** section (`WatchFacePrefsFragment.SECTION_TYPOGRAPHY`, backed by the hidden `cat_wf_typography_*` categories in `watch_face_settings.xml`) rather than under Style/Colors, so the font/title/artist/icon controls aren't buried among layout and colour settings. Colour is intentionally separate: the Colors page begins with the global **Colors from the music** controls and then holds the title/artist/clock colour overrides.

How a title that *doesn't fit* behaves is the sibling control `MiscPreferences.WEAR_TITLE_TEXT_MODE` (`wear_title_text_mode`, face-scoped): `smart` (the default — shrink, then wrap, then scroll), `marquee` (one scrolling line), `wrap`/`wrap3`/`wrap5` (two/three/five lines then an ellipsis), `static` (one ellipsized line, never shrunk or scrolled) and `shrink`. It exists because every face used to hardcode one strategy and they silently disagreed — Vinyl/Halo/Eclipse/Expressive always scrolled, Poster/Studio/Aurora wrapped to two lines then truncated, Spectrum only truncated — so the same long title was fully legible on one face and cut off on the next with no setting anywhere to explain why. Like `MiniButtonPlacement` and `MiniButtonSurfaces`, it is a shared decision with **three renderers that must agree**: Compose faces call `AdaptiveTitleText` in `FaceChrome.kt`, the classic View face calls `OutlineTextView.setSizingMode`, and `WatchPreviewView` mirrors the same cascade in its `TitlePlan`. The failure mode is quiet in the usual direction — a face that draws its title with a bare `Text`/`TextView` instead of going through `AdaptiveTitleText` opts out of the setting without erroring, and the preview goes on claiming the setting applies. Note was that face: its whole composition is one two-colour `Artist: Title` sentence, which the `String` entry point could not express, so it drew a fixed three-line wrap and the setting did nothing there — hence `AdaptiveTitleText`'s `AnnotatedString` overload, with the `String` one delegating to it so each mode still has one implementation.

Two more text helpers resolve in `common` for the same preview-must-not-lie reason. `AdaptiveTextContrast.kt` keeps album-derived text legible against the artwork actually behind it: a fixed lightness floor (`WatchTheme.accentForText`) can only ever be right for one assumed background, so this measures the luminance of *the band the line occupies* — not the whole cover, which averages away exactly the local contrast that matters — and pushes lightness apart while keeping hue/saturation, so the line still reads as the album's colour rather than as white. What it measures now goes through `backdropLuminance(style) { sample }` on both sides (wear `MainActivity.sampleBackdropLuminance`, the preview's namesake): a background style with `hidesArtwork` paints a black field, and sampling the cover then answers about a picture nobody can see — that is how a bright album darkened the clock to near-invisibility on Frame, whose backdrop defaults to `HIDDEN`. The artwork case stays an approximation (the dim scrim and the authored treatments darken unevenly), but every one of those errors runs in the same direction, so it under-lifts rather than inverting. It is opt-in per element (`WEAR_ARTIST_ADAPTIVE_CONTRAST` and the clock's equivalent) precisely because a hand-tuned palette shouldn't be silently corrected, and applies only to the album-colour mode (White/custom are explicit choices; Dynamic resolves legibility its own way). `RoundScreenText.kt` holds the geometry for keeping a text block inside a round screen: the usable chord collapses fast towards the top and bottom, so hand-tuned side padding is only ever correct for the line count its author tested — the moment a title wrapped, the second line sat deeper and ran into the bezel. It returns width as a fraction of screen width at a given depth, clamped so a very low band can't collapse into a one-character column. Carousel is its first consumer. `AlbumAccentSelection.kt` decides *which* swatch of the cover becomes the accent in the first place, and exists because the two sides had quietly disagreed for as long as both existed: the watch took Palette's balanced answer and the phone preview took the vibrant one, each with a comment claiming it matched the other. `selectPrimaryAccent(vibrant, swatches, source, minShare)` is now the one function all three consumers call — wear `MainActivity`, `MediaTileService` and `WatchPreviewView` — with the disagreement promoted to a user choice, `MiscPreferences.WEAR_ALBUM_ACCENT_SOURCE` (face-scoped, in `SCOPED_KEYS`): `BALANCED` takes the vibrant swatch only when it covers at least `minShare` of the dominant swatch's pixels and the dominant colour otherwise, so a lens flare on a mostly-blue cover can't turn the UI red while the blurred backdrop behind it stays blue; `VIBRANT` takes it regardless, which is the trade `BALANCED` refuses. Unknown values resolve to `BALANCED` because that is what every existing install already renders. A null return means "no colour information at all" and is reported as *keep the accent already showing*, never as a colour. The watch caches the extracted palette per bitmap, so `lastPaletteAccentSource` has to be part of the cache key — changing the setting otherwise does nothing until the track changes.

One font in the `WEAR_FONT` catalog, **Google Sans Flex** (`WatchTypography.FLEX_FONT_KEY`), is a true OpenType variable font with six axes (`wght`, `wdth`, `opsz`, `slnt`, `GRAD`, `ROND`; bounds pinned to the bundled font's own `fvar` table, not guessed). `wght`/`slnt` reuse the per-element weight/italic controls above (so Flex doesn't add a second, conflicting weight control); the other four — width, optical size, grade, roundness — belong to the family that selected Flex: Title and Artist follow the global set by default but each gets its own set behind its Flex button after an explicit Flex selection, exactly like Clock, Lyrics and playback time. A `follow` selection keeps using the global axes. The legacy `cat_wf_typography_flex` category stays hidden and inflated for search/storage metadata; `WatchFacePrefsFragment.initTypographyDependencies` refreshes the editor button instead of revealing that category. `WatchTypography.flexVariationSettings()` builds the one variation string both sides render from: the watch's classic face resolves it via `WatchTheme.flexTypeface` (`Typeface.Builder(File)` — the font resource has no direct-from-resource-id builder constructor, so it's extracted to a cache file once per process), Compose faces via `WatchTheme.flexFontFamily` (`Font(resId, variationSettings = FontVariation.Settings(...))`, gated behind `@OptIn(ExperimentalTextApi::class)`), and the phone preview via its own identical `Typeface.Builder(File)` path — same extract-to-cache trick, since `mobile` cannot depend on `wear`. The bundled `google_sans_flex.ttf` (~4.1MB, in both `mobile/src/main/res/font/` and `wear/src/main/res/font/`, OFL-licensed under `licenses/google-sans-flex/`) is the true variable master, not a static instance — smaller combined than the two static Google Sans weights it sits alongside.

The colour treatments above only *compute* a distinct secondary/tertiary — on the classic face, nothing drew them anywhere visible (progress bar and artist text render only the primary slot, and every album-derived treatment deliberately keeps the primary close to the raw accent), so switching Expressive→Triadic looked like a no-op. `CircularProgressSeekBar`'s `RingStyle.SOLID` (the default ring style) now paints a primary→secondary→tertiary sweep gradient instead of a flat fill, but *only* when `ColorHarmony.hueDistance` between them clears `MIN_DUOTONE_HUE_GAP` — so Normal/Desaturated/Expressive/Monochrome (whose secondary/tertiary sit close in hue) render pixel-identical to before, and only the hue-rotating treatments (Triadic, Complementary, Analogous, Duotone) visibly change. Normal stays in that group *by construction, not by coincidence*: `WEAR_NORMAL_COLOR_MULTI` (default **on**) makes it derive a secondary/tertiary from the picked colour via `PaletteTransforms.sameHueTone` at .42/.68 lightness rather than filling all three slots with it, so its triad is a tonal ladder — same hue, so `hueDistance` stays at zero and the ring never gradients, while any surface that reads the companion slots does get real tones. Turning the switch off restores the flat three-identical-slots triad. The flag is a `derive()` parameter rather than a lookup inside it, so all three callers must pass it (wear `MainActivity`, `WatchPreviewView`, and `ColorTreatmentPreference`, which is fed it by `WatchFacePrefsFragment`) or the swatch dialog and the preview will disagree with the wrist. It is face-scoped alongside `wear_normal_color` — it was briefly not, which made it the one key on the Watch face screen that changed every face at once and left `AppearancePreferenceScopingTest` failing. It has since been generalized from Normal-only to **every** treatment: off, the whole surface paints one colour. The collapse is applied *last* — after the treatment, hue shift and modifier — by the pure `SurfacePaletteResolver.flatten`, which is split out precisely because `derive` goes through androidx ColorUtils and so cannot be JVM-tested, while "collapse to the primary, never to a companion" can (`SurfaceColorTreatmentTest`). Applying it last is what keeps the main colour identical with the palette on or off, so the switch reads as simplifying the theme rather than changing it. The key name stays `wear_normal_color_multi` for lossless migration, the same historical-name pattern as `wear_classic_icons_visible`; only the *picker* (`wear_normal_color`) is still Normal-only in the settings UI. `WatchPreviewView.drawEdgeSeekRing`'s `"solid"` branch mirrors the same conditional gradient so the phone preview doesn't lie about what the watch will show.

The title and artist can each cast a **shadow**, and it is deliberately *not* a sixth field on `WatchTypography.TextSpec`. `common/.../TextShadow.kt` owns it: five authored presets (`TextShadowStyle`) rather than four numeric controls, because radius, offset and alpha have strongly correlated good answers and offering them separately mostly yields combinations nobody wants — intensity stays a number because it is the one axis worth dialling. `TextSpec` stays what it is so `isIdentity` goes on meaning "the glyph styling changes nothing", the check every renderer uses to skip its styling path. Four things about it. **The colour is resolved by the renderer, never by the reader**: `WatchTypography.titleShadow`/`artistShadow` return the user's choice, and `TextShadowSpec.resolveColor(mode, custom, accent)` turns it into ARGB — the `album` mode against the *face-wide primary* (so it wears the same treatment, hue shift and modifier as everything else), falling back to black while `Palette.generate` is still on its way. That is why the wear side recomputes it in `applyAccentColor`, the one place accent-derived values may live. **A zero blur radius is not a faint blur to either platform** — `Paint.setShadowLayer` reads it as *no shadow layer* and Compose as a hard edge — so `TextShadowSpec.radiusDp` floors a blurred style just above zero and both renderers floor the pixel radius again; `TextShadowSpecTest` pins it. **Compose delivers it through `LocalTextStyle`**, not as a parameter: `AdaptiveTitleText` has four rendering branches and two are separate composables, so a provider reaches all four (including the shrink cascade's intermediate measurements) where a parameter would have reached some of them — `ArtistLineText` is a single `Text` and passes it directly. **And on the title side the three effects default off `NowPlayingFaceState` inside the helper** (`shadow: Shadow? = state.titleShadow` and its outline/backdrop siblings, which is why `AdaptiveTitleText` takes the state at all): they were plain nullable parameters defaulting to null, so all fifteen call sites had to opt *in* and not one did. The host resolved them, put them on the face state and nothing read them — so the title shadow, outline and backdrop worked on the classic View face and in the phone's own preview, which read the specs directly, and were inert on every Compose face. That is the worst arrangement there is: the screen built to show what a setting does was the only place it appeared to work. And **AOD is deliberately excluded on both sides** — `applyAmbientPresentation` nulls the face state's shadows and clears the View layers, `applyClassicTextShadows` re-checks `isAmbient` because a track change can land mid-ambient — since AOD is styled by `WEAR_AOD_*` and a blur lights more pixels for longer, which is what the burn-in jiggle exists to avoid. The phone preview applies it at `trackTextTypeface`, the one choke point both elements already share (two dozen call sites draw a title), paired with `resetTrackTextPaint` and with a per-frame `clearShadowLayer` in `onDraw` so a missed reset can never cross frames.

Two siblings of the shadow followed, and both are shaped by what the *three* renderers can agree on rather than by what any one of them could do. `common/.../TextOutline.kt` strokes the glyphs: an outline is genuinely **two drawing passes** — no text API on either platform strokes and fills at once — so the width is a *fraction of the text size* rather than dp (a stroke that reads as a keyline on a 30sp title closes the counters of a 12sp artist line, and `AdaptiveTitleText` shrinks its own text, so a pixel width resolved by the host would be wrong at every size the cascade lands on). Each renderer therefore gets the fraction and computes pixels at the draw. Compose renders the two passes as two `AdaptiveTitleText` copies in a `Box`, and three details there are load-bearing: the caller's `modifier` goes on the **Box** (a `weight`/`align` must stay a child of its Row/Column scope), `propagateMinConstraints = true` hands the children the Box's own minimum width so a `fillMaxWidth` caller keeps behaving as before (without it a filled title silently becomes wrap-content and its `textAlign` stops meaning anything), and `onLineCount` is reported by the fill pass alone. The classic View strokes in `OutlineTextView.onDraw` and cannot set the stroke colour through `paint.color` — `TextView` re-applies the current text colour at the top of every `onDraw`, so a `PorterDuff.Mode.SRC_IN` colour filter is used instead, which is applied after that and never triggers the `invalidate()` a `setTextColor` would. `common/.../TextBackdrop.kt` is the plate behind the line, and its vocabulary is narrow **because Compose paints it through `TextStyle.background`**, which fills the line box and offers no padding, radius or width: a rounded pill or a full-width band would mean the watch and its own preview disagreeing about what the setting does, which is the drift `WatchPreviewParityTest` exists to catch and would miss, since both sides would be "working". So the styles differ only in how much of that box is filled. `OutlineTextView` draws the same box from `layout.getLineLeft/Right/Top/Bottom` rather than as a View background — the View is `match_parent` on every face, so a background would be a band across the screen instead of a plate behind the words — and `WatchPreviewView` draws it from the paint's font metrics for the same reason. All three effects share `TextShadowColorMode` and `TextShadowSpec.resolveColor`, so an "album" shadow, outline and backdrop on one line are provably the same colour rather than three implementations that agree today. And all three are cleared on both sides when ambient starts.

The edge ring's **position mark** — the radial tick crossing the progress band — is `common/.../SeekMarkerVisibility.kt` (`MiscPreferences.WEAR_SEEK_MARKER`, face-scoped, pure and JVM-tested). It was built for one job: during a drag the arc belongs to the finger, so nothing else says where the track *is*, and the tick is the reference point being left behind. That is still the default (`drag`), and an unknown or absent value resolves there for `PausedHoldPolicy`'s reason — the value can arrive from a backup, a community theme or a newer phone. The other three modes (`always`, `drag_paused`, `paused`) exist because the same mark reads as a **playhead** at rest, which is legible where the end of a smooth arc over a busy cover is not. Two details are load-bearing. **Where it sits differs between the two cases**: during a drag it marks `dragOriginProgress` (which keeps advancing, because the track keeps playing), and at rest it follows `displayProgress` — anchoring it to the origin in both would freeze a stale mark wherever the last drag started. And it is drawn **inside** `CircularProgressSeekBar.onDraw`'s early return, not beside it: the tick is a mark *on* the band, so with the ring hidden it would be a lone dash at the screen edge. That same dependency is why it is the one Player-page choice row gated by a *preference* rather than by the face — `PlayerEditorModel.appliesToFace` stays pure and face-only, `WatchFacePrefsFragment.renderPlayerEditor` filters the row on `wear_edge_progress_visible`, and `WatchSearchTargetResolver` redirects a search for it to that switch. `WatchPreviewView` mirrors it through `drawEdgeSeekMarker`; note that the ring's style table and its layout geometry now live in two functions (`drawEdgeSeekRingStyle` and `edgeSeekRingMetrics`) rather than one, so `PanelOptionRenderingContractTest` joins both bodies — scoping to either half alone silently loses the other's value table.

Orthogonal to face *structure* is the control-style treatment `ScreenTheme` (`common/.../ScreenTheme.kt`, pref `MiscPreferences.WEAR_SCREEN_THEME`: default / minimal / compact / cinema / vivid / contrast / amoled / hidden — "hidden" draws no control icons while keeping touch targets and accessibility actions active). It lives in `common` so the phone preview and the watch decode exactly the same tokens and can't drift apart (the wear-side `watch/view/face/ScreenTheme.kt` is just typealiases into it); `common/.../OverlayBackdrop.kt` does the same for the volume/seek/quick-panel overlay backdrops. It is *not* universal, despite only ever touching `ScreenThemeTokens.iconAlpha`/`iconScale`: it reaches whichever face actually draws icon glyphs through it, which is Classic, the icon-transport curated faces (Vinyl/Poster/Studio/Halo/Aurora/Eclipse/Spectrum/Material) and Expressive, plus Frame and Ribbon whose transient tap-confirmation glyph (via `CenterGestureRegion`'s optional `state` parameter) honours it even though neither keeps a permanent on-screen icon. The other eight faces (Immersive, Depth, Carousel, Chat, Split, Note, Verse, Metadata) either have no icon-based transport at all or call `CenterGestureRegion` without `state`, so the setting reached nothing there — `PlayerEditorModel.CONTROL_STYLE_FACES` is the resulting allow-list the Player page's **Control style** row now gates on, the same `appliesToFace` mechanism `CAROUSEL_SHAPE`/`SPLIT_PANEL` already use. Per-element visibility follows the same shared-pref pattern: `WEAR_SHOW_TRACK_TITLE` / `WEAR_SHOW_TRACK_ARTIST` (status/error text stays visible regardless), `WEAR_PLAYER_CONTROLS_VISIBLE` (persisted under its old key `wear_classic_icons_visible` so existing installs and backups migrate losslessly), and separate internal-progress (`WEAR_INTERNAL_PROGRESS_VISIBLE`) vs. edge-progress (`WEAR_EDGE_PROGRESS_VISIBLE`) visibility with independent edge-seek enablement.

**Album-derived colour lands asynchronously**, and anything resolved outside `applyAccentColor` will therefore read the *previous* track's accent. `Palette.generate` is a callback, so on a track change the art path starts extraction and continues immediately; `applyAccentColor` is what finally assigns `currentAccentColor` and it is the single place every dependent value is recomputed (title/artist/progress/shading/AOD tint into face state, plus `styleScreenButtons`, `applyAlbumArtScrim`, `applyPlayerBackground`). The awake clock was the one exception — `resolveClockColor` reads `currentAccentColor` but `applyClockAppearance` was only called from the art path, i.e. before extraction finished — so it stayed one track behind until an unrelated preference change refreshed it. It is now called at the end of `applyAccentColor` too, mirroring the `applyAmbientViewColors` call the ambient branch already made for the same reason. Anything new that derives from the accent belongs inside that function, not beside the call to it. The *result* is published to `watch/view/panel/AlbumPaletteCache.kt`, a one-entry process-scoped memo keyed by bitmap identity **and** `AlbumAccentSource` (the source decides which swatch becomes the primary, so one cover legitimately has two answers — the same reason `lastPaletteAccentSource` is part of the extraction guard). That exists because the dedicated Volume and Progress screens are separate Activities that re-extracted the same `PhoneConnection.albumArt` instance from scratch, so opening one flashed the fallback sage `theme_accent` before snapping to the album's colour. Both extractions agree exactly, down to the fallback, so the cache hands over one answer rather than approximating another. `rememberPanelPalette` (`PanelPalette.kt`, the one place both panel screens resolve their colours — they previously ran identical copies of it) *seeds its state* from the cache rather than only consulting it in a `LaunchedEffect`: an effect runs after the first frame is drawn, so even an instant answer would still have flashed the fallback once.

The always-on display is separately configurable via `MiscPreferences.WEAR_AOD_STYLE` ("follow"/"classic"/"chrono" plus one per Compose face — "expressive", "material", "eclipse", "poster", "studio", "immersive", "carousel", "chat", "split", "note", "verse"; the removed "minimal" is still mapped to "classic" on both sides so a stored value keeps working, and the list must stay in step with `wear_aod_style_values`) plus per-element toggles (`WEAR_AOD_SHOW_ART`/`_CLOCK`/`_TRACK_INFO`/`_TRANSPORT`/`_PROGRESS`/`_PILLS`), an outline color mode (`WEAR_AOD_COLOR_MODE` white/album/custom, lightness-lifted on the watch for legibility on black) and a brightness scale (`WEAR_AOD_INTENSITY`), all configured in the phone's Watch face tab: the classic AOD is the original View presentation, every Compose AOD is that face with `NowPlayingFaceState.ambient` set (outline-only, animation-free, same geometry as the awake face so wake-up taps land on the intended button), and "chrono" is a standalone `ChronoAmbientFace` — a big centred clock on pure black with the title beneath; `MainActivity.applyAmbientPresentation()` is the single place that styles ambient, and every variant keeps the burn-in pixel jiggle. Touch is never delivered to apps in ambient (the system wakes the watch instead) — only stem buttons/rotary work there, so AOD "buttons" are display-only by platform constraint.

**Every AOD control has to be read by every AOD face, and a face that skips one fails silently.** A face receives everything it draws as one `NowPlayingFaceState`, so reading the wrong field — or none — compiles, renders, looks right, and simply makes a switch on the phone do nothing on that one style, in the one mode nobody inspects closely. Both halves of that have already happened. The artwork controls (`WEAR_AOD_SHOW_ART`, `WEAR_AOD_ART_TREATMENT`, `AMBIENT_ALBUM_ART_OPACITY`) reach a face through `ambientAlbumArt`/`ambientAlbumArtBlurred`/`ambientAlbumArtAlpha`, published by `applyAmbientAlbumArt` from the same `resolveAodArtwork` answer the host backdrop uses (via `ambientArtworkForFace`, the ambient sibling of `filteredArtworkForFace` — deliberately over the *raw* cover, since the ambient treatment is independent and the awake filter and frosted rim must not ride underneath it) and released in `onExitAmbient`. **`albumArt` is the awake cover and is always the wrong field in ambient**: it carries the awake treatment and is published whether the AOD asked for a cover or not, which is how Carousel's ambient card — the one ambient face that draws a cover at all — kept showing a picture the user had switched off, under the interactive filter, at a hardcoded opacity. `WEAR_AOD_SHOW_TRACK_INFO` is the same trap: Metadata drew its identity and rows unconditionally, so the switch emptied ten styles and did nothing on the eleventh. `AmbientFaceContractTest` (wear) is the source sweep that pins all of it — no ambient face reads `state.albumArt`, an ambient cover carries all three artwork controls, every ambient face consults `ambientShowTrackInfo`. Its counterpart `WatchPreviewParityTest.theAmbientMiniaturesDrawCoversWhereTheWatchDoes` pins the other direction, because the preview drifted too: it filled Ribbon's five card windows and Frame's image well with covers while `RibbonAmbient`/`FrameAmbient` draw those as empty hairlines. Which faces carry a cover in ambient is a design decision; that the two renderers agree about it is not.

`ButtonAction.isCoverArt` is the flag that separates **genuine artwork from an app-launcher icon**, and it is not the same question as `iconTintable`: an app icon is full-colour and so untintable too, which is why an "open app" row grew to album-cover size and got cropped into a circle. The rule is written **twice** — `MenuScreen.leadsWithArtwork` and the inflated quick-panel rows in `MainActivity.renderQuickPanelExtraActions` — and both had it wrong; the quick panel is the easy one to miss, because its *pill background* check already read `isCoverArt` correctly while the leading icon beside it did not, so half the row behaved. Both now derive three sizes from two flags: `isCoverArt` → cover, `!isCoverArt && !iconTintable` → app icon (`APP_ICON_DP`/`APP_ICON_SIZE`, kept in step by name since the two surfaces list the same actions), `iconTintable` → glyph. Only `PlayPlaylistShortcutAction` sets it, and only when the *fetched* thumbnail exists — the destination app's launcher icon is a real image but stretching it across a pill reads as a smeared logo. Three sizes result, not two: cover art fills the pill, an app icon keeps its own colours at glyph size, a monochrome template glyph stays a glyph.

Surface-level visual styling (volume overlay, quick panel, queue screen) is independently user-selectable per surface via `MiscPreferences` string prefs (e.g. `WEAR_VOLUME_STYLE`), each decoded to a local `*Style` enum (see `CircularVolumeBar.VolumeStyle`) with a `fromPref()` mapper — new styles are additive enum cases plus a `when` branch in that surface's paint/draw logic, not a new preference.

**The background is an ordered stack, not three fixed slots** — `common/.../BackgroundLayerStack.kt` (pure, JVM-tested), persisted as one string in `MiscPreferences.WEAR_BACKGROUND_LAYERS` (`wear_background_layers`, face-scoped, exportable). Up to eight layers, each a `WASH` (an authored `PlayerBackgroundStyle`), a `SHADE` (a `PlayerShadingStyle`) or a `FLOOR` (an `AccentFloorStyle`), each with a 0–150 % strength and — for the last two — a colour mode. Three states, and the difference between the first two is load-bearing: **absent** (`""`, or anything the parser refuses) means nobody has composed one, and every renderer falls back to `implicitStack`, the exact equivalent of the legacy `album_art_style` / `wear_player_shading_style` / `wear_accent_floor` arrangement — which is also what a watch build older than the key does with it, so a phone that has moved on degrades to the previous look rather than to none; **empty** (`"1"`) is a decision, bare artwork; and an **explicit** stack replaces all three legacy slots at once, never some of them. Parsing is fail-closed on the *whole* value, because dropping the one layer a reader did not understand would silently render a different composition than the one that was saved. The artwork itself is never a layer — `ALBUM_ART_STYLE` keeps owning how the bitmap is treated, since `albumArtHidden`, `usesBlurRadius` and `backdropLuminance` all read that facet far outside this file, and a photograph is opaque anyway — but the *wash* half of that same preference is, which is what makes an authored background reorderable. `SELF_BACKDROP_FACES` (Split alone) is told its base wash never reaches the screen, so the seed does not add one the face has never shown. Four renderers walk the same resolved list: `FaceChrome.PlayerBackgroundTreatment` (Compose), `PlayerBackgroundDrawable` (Classic — it composes `PlayerShadingDrawable` per layer rather than growing a second copy of that vocabulary, which is why Classic's separate `album_art_scrim` View is gone: two sibling Views can only ever be in the order the layout declares), `WatchPreviewView.drawBackgroundLayers`, and `panel/PanelAppearance` for the dedicated Volume/Progress screens. The phone edits it in the Background page's contextual editor (below), never through a `ListPreference` — a layer's style is not a preference — though the *pickers* it offers come from the real `ListPreference` objects, so archived filtering and translations stay in one place. The community contract carries it as a **new rule kind**: `community-theme-constraints.json` is schema **2** with a `layerRules` section declaring the whole grammar (version marker, depth, encoded length, opacity range, the colour vocabulary and the value set each kind draws from), mirrored in `CommunityThemeConstraints.LayerStackRule` and `schema.mjs`'s `layerStackMatches`, and pinned against the Kotlin enums by `CommunityThemeVocabularyParityTest`. It is also the one setting whose public value may exceed the shared 128-character cap — `maxPublicTextLengthFor` / `maxSettingTextLength` read the ceiling off its own rule, because length was never what made these values safe.

**`hidesArtwork` used to mean two things at once, and the flat album fills forced them apart.** Its doc said the flag marks a style that "paints black" — `HIDDEN` and `ECLIPSE` both do — and `AdaptiveTextContrast.backdropLuminance` relied on that, returning `HIDDEN_BACKDROP_LUMINANCE` (zero) for any such style. The three flat album fills carried over from the panel catalogue hide the artwork just as completely but paint an *album tone*, which can be light; marking them with the flag alone would have told adaptive contrast the ground was black and darkened text that needed lifting — silent, and only on light covers. So `PlayerBackgroundStyle` now carries `flatAlbumFill: AlbumFillSlot?` alongside the flag, and `backdropLuminance` takes a `flatFillLuminance` lambda that both renderers answer from the same triad they paint from. Two details of that signature are deliberate: the new lambda sits **before** `artworkBandLuminance`, because that one is the trailing lambda every existing caller passes unnamed and reordering would have silently rebound them; and a null answer still falls back to black, so `HIDDEN` and `ECLIPSE` are untouched.

**A drawn pattern is written once, in `common`, and Compose reaches it through `nativeCanvas`.** `OverlayBackdropPatterns` takes an `android.graphics.Canvas`, which looks at first like a reason for Compose faces to re-author each pattern in `DrawScope` - and re-authoring hand-drawn geometry is precisely the drift `WatchPreviewParityTest` exists to prevent, only worse here because a dot pitch or a facet seed that differs slightly is invisible in review and obvious on the wrist. `drawIntoCanvas { it.nativeCanvas }` removes the need: the Compose face, `PlayerBackgroundDrawable` and `WatchPreviewView` all call the same function. The two things each caller still has to supply correctly are the bounds (`DrawScope` gets them from its own `size`, via `patternBounds()`) and a **real** density - these patterns size their pitch and line weights in dp, so `PlayerBackgroundDrawable` takes one as a constructor parameter rather than reaching for `Resources.getSystem()`, which reports the default display and not the watch's; the preview passes `PreviewGeometry.dpScale`, its own miniature's equivalent.

**Adding a `PlayerBackgroundStyle` touches *two* value sets in the constraints asset, not one.** `albumArtStyle` is the obvious one; `backgroundLayerWash` is the second, because a `BackgroundLayerStack` layer of kind `WASH` draws a player background style and the layer grammar enumerates its own vocabulary. Miss it and the style is selectable and renders correctly everywhere, while any theme that puts it in a background stack becomes unsubmittable — `CommunityThemeVocabularyParityTest`'s layer-grammar check is what catches it, and it is the only thing that does. The picker side has a matching pair: the additive `album_art_style_extra_*` arrays plus the literal expected list in `AppearanceOptionCatalogTest`, which pins the values by name rather than by count.

**Porting a treatment between the two catalogues carries the composition, not the opacity.** A `PlayerBackgroundStyle` wash sits *over artwork* and works by alpha; an `OverlayBackdrop` **is** the surface, with controls on it, so the same hues have to be carried at a lightness a control can be read against — what ports is where the colour sits and which way it runs. Each addition to `OverlayBackdrop` touches six places and every one of them is guarded: the enum case and its `fromPreference` mapping (`OverlayBackdropTest` requires an explicit mapping for every value), `OverlayBackdropDrawables.build`, `WatchPreviewView.drawConfiguredOverlayBackdrop` (`PanelOptionRenderingContractTest` requires both), the additive picker arrays in `panel_options.xml` plus their pt-rBR twin and the count in `PanelOptionCatalogTest`, the `overlayBackdrop` value set in `community-theme-constraints.json`, and — the one with no test behind it — a branch in `MainActivity.quickPanelBackdropColor`, which decides whether the quick panel's centred text flips light or dark. That last one is exhaustive over the enum, so the compiler catches a missing branch, but not a *wrong* one: the value has to be the tone the centre of the panel actually lands on, which for a backdrop whose glow sits off-centre (Rose, Mirage, Bloom) is the dark base rather than the glow. Two idioms make the port mechanical: a radial glow is a `GradientDrawable` with `RADIAL_GRADIENT` on the watch and `drawBackdropBloom` in the preview, quoting the identical centre and width fraction; anything that needs real geometry — a slab across part of the width, an inset rule — goes through `PatternDrawable`, which hands you a canvas and bounds, because a `LayerDrawable` inset cannot express a fraction of an unknown width.

**Pair the two background catalogues by what they draw, never by name or palette.** A survey that matched on names put eight effects down as "the same under a different name"; comparing the renderers, only three were (`ocean`/`deep_ocean`, `sunset`/`sunrise`, `prismatic`/`prism`, all now sharing a label). `tidal` draws cubic wave paths where `tideline` is a vertical ramp, `cloud` is three radial blooms where `smoke` is a grey diagonal, `nocturne` carries a glow and scattered points where `midnight` is a ramp, `glass_veil` has a sweep-gradient rim where `glass` is a flat wash — four pairs that are not equivalent at all and belong in the "missing on the other side" column. The unification is deliberately **label-only**: the persisted values never moved, so no alias, no migration and no published theme is affected, and the picker is the only place a user ever sees the difference. Note also that the panel's `split` and `duotone` had drifted into the same left-to-right ramp while `split` shared the label "Split tone" with a player style that draws two tones divided by a line — `split` now draws that, which removes the label collision and the duplicate at once.

**A name shared by `PlayerBackgroundStyle` and `OverlayBackdrop` must draw the same treatment.** The two enums were authored separately and seven names ended up in both; `expressive`/`expressive_no_blur` were deliberate equivalents and `halo`/`spotlight` close relatives, but `ember`, `horizon` and `aurora` drew unrelated compositions — a corner glow against a diagonal wash, a darkened lower band against a bright middle band, two ribbon glows against a linear gradient. The panel three were aligned to the player's geometry (same centres, same relative radii), keeping only the one difference the surface forces: a panel carries controls, so it keeps a dark field under the composition where the player face can sit on bare artwork. Values were **not** renamed, so published community themes are unaffected. When adding a treatment to either enum, check the other for the name first. The radius unit is the trap that goes with this: `OverlayBackdropDrawables` takes `screenWidthPx` (the **full** width, because `GradientDrawable.gradientRadius` has no fractional form outside XML) while `WatchPreviewView.PreviewGeometry.radius` is **half** of it — every existing bloom quoted the watch's fraction against the preview's half-width base, so every panel bloom was drawn at half size in the preview. `drawBackdropBloom` now converts internally and its parameter is documented as a fraction of the width, so both sides can quote the identical number.

**Player shading** (the darkening overlay for legibility, `common/.../PlayerShading.kt` / `PlayerShadingDrawable.kt` on the watch, mirrored in `WatchPreviewView`) is one layer kind in that stack, and its three legacy controls remain the fallback when no stack is stored. All face-scoped: a **style** (`wear_player_shading_style`), a **numeric intensity** (`album_art_dim_strength`, a 0–150 % value read as `percent/100f`; the old named `wear_player_shading_intensity` soft/balanced/strong pref is retained only to migrate legacy values — `PlayerShadingIntensity.percentFor`), and a **colour** (`wear_shading_color_mode`: black / album accent / desaturated / custom `wear_shading_custom_color`, resolved to a dark chromatic tone via `PaletteTransforms.shadingTone`). The clamp ceiling is the shared `SHADING_MAX_MULTIPLIER` const, not a hardcoded 1.0. Note the hard boundary this draws: `PlayerShadingDrawable` renders *over* the artwork and never receives the bitmap, so every treatment it can offer only darkens — a real edge blur is impossible there. That's why frosting is an **artwork** style instead (`common/.../FrostedEdges.kt`, an `ALBUM_ART_STYLE` value composed once where the bitmap is known, blurring through the shared `BitmapBlur` for the same API-31/`RenderNode` reason, and consumed by the classic face, every Compose face and the phone preview alike). Anything new that has to *see* the cover belongs on that side of the line. Authored *background* styles (Expressive, Poster, …) render their designed look independent of the "Dim album art" toggle — that toggle governs only the separate legibility scrim over plain artwork. Built-in face scopes intentionally stay independent; if someone wants one as an editable starting point, the Watch themes catalogue duplicates that face into **My themes** instead of bulk-overwriting every other face.

Two watch-lifetime behaviours: the classic idle "Nothing playing" screen taps through to configured stopped-config gestures, but a play/pause command with no session resumes the last app (`AudioManager` PLAY key, see *Actions system*); and `MiscPreferences.WEAR_KEEP_SCREEN_ON` (applied by `wear/.../util/KeepScreenOn.kt`, which re-applies rather than sets once — the preference is phone-owned and can flip, or the face under it change, while a screen is open — and clears the flag as well as setting it) holds the player awake against the system's inactivity timeout, and is **face-scoped** rather than global: whether a screen should be held is a property of the composition in front of you, so a face you read wants it while the one you glance at should not pay its battery cost. It defeats the *timeout* only - lowering the wrist is a system gesture no window flag overrides, which is why the screens that must survive it (the lyrics screen) carry an ambient variant instead. The queue and menu deliberately do not consult it: they belong to no face. `MiscPreferences.WEAR_CLOSE_ON_IDLE` (default on, `MusicViewModel`) auto-closes the app ~60 s after reaching the truly-idle state, distinct from the user-configurable `CLOSE_TIMEOUT` which covers the paused case and stays off unless set.

The idle screen is otherwise driven by `common/.../IdleScreenAction.kt` (resume / shortcuts / menu / search / queue / none): `WEAR_IDLE_BUTTON_ACTION` picks its main button and `WEAR_IDLE_AUTO_OPEN` optionally jumps straight to one of those screens when the app opens with no session. The two decode through *different* fallbacks on purpose — an unrecognised button value resolves to `RESUME` (the user should still be left a way to start playback), an unrecognised auto-open value to `NONE`, and `RESUME` is excluded from `AUTO_OPEN_CHOICES` entirely, because starting playback merely because the app was opened is a surprise rather than a shortcut. The idle screen also shows the **stopped**-config mini buttons, which is exactly where the "start something" shortcuts live.
