# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Svartifoss — an Android app that lets a paired Wear OS watch control music playback on the phone (and on the watch itself), with customizable physical buttons / digital crown / gestures. **Sideload-only**: the phone and watch APKs are installed manually from GitHub releases (watch install via Wear Installer), or via the **self-hosted F-Droid repo** served from GitHub Pages (`docs/fdroid/repo/` — signed index + APK; app metadata in `docs/fdroid/metadata/`, fdroid-server config template in `docs/fdroid/config.yml.example`; the real `config.yml`/keystore are gitignored secrets). `fastlane/` at the repo root holds store-listing metadata shared by F-Droid/Play tooling. It is *not* on the Play Store — a split free-phone-app / paid-watch-app listing was drafted (see `docs/play-console-*.md`) but the author shelved it, not a store enforcement action. A future Play Store attempt is more likely to be a single listing with in-app premium unlocks (Play Billing) than the old split-app model. Both APKs must still share the same `applicationId` and signing key (see "Package naming gotchas" below).

## Module layout

This is a multi-module Gradle (Groovy DSL) Android project, configured in `settings.gradle` / `build.gradle` / `libs.toml` (version catalog):

- `mobile/` — the phone app. Reads the currently playing media session, executes actions (play/pause/skip/volume/Tasker tasks/open other apps), and syncs config/state to the watch over the Wearable Data Layer API. Uses **Dagger 2** (`di/AppComponent.kt`, manual `dagger-android` injection) for DI.
- `wear/` — the watch app. Renders the on-watch UI (now-playing screen, action menu, volume bar), receives button/crown/gesture input, and talks to the phone. Uses **Hilt** for DI (different DI framework than `mobile/` — don't assume Dagger conventions carry over).
- `common/` — shared code linked into both `mobile` and `wear`: communication path constants (`CommPaths.kt`), action/button-config models, protobuf schemas (`src/main/proto/*.proto` — actions, music, watch, notifications, custom lists), shared views/drawables.
- `wearutils/` — a **git submodule** (https://github.com/gabrielluizone/WearUtils, this repo's fork of matejdro/WearUtils) with its own `libs.toml`. If this directory is empty, run `git submodule update --init` before building — Android Studio/Gradle sync will fail otherwise.

Root directories that are *not* part of the build: `icons/` (tracked; raw Material Symbols SVG downloads used as source material when adding drawables), `archived/` (parked scraps), `licenses/` (tracked; per-font license texts for the bundled typefaces), `wearmediatemplate/` (Google's Wear OS media-controls design guidance — screenshots plus `media-expressive.md` — kept as reference material for face styling), and the gitignored local reference folders `retromusic/` and `redesign/`. Several stray build outputs / scratch files also sit at the repo root and are **not** build inputs (`full.apk`, `part.apk`, `mobile-debug.apk`, a bundled `com.google.android.wearable.media.sessions_*.apk`, `svartifoss_config.json`, `run.md`, `promp.txt`, `CHANGELOG.pdf`, `RELEASE_3.md` (a drafted GitHub release announcement, not shipping docs), assorted screenshot `*.png` scratch files) — ignore them.

### Phone ⟷ watch communication

All communication goes through the Google Play Services **Wearable Data Layer API** (`MessageClient`/`DataClient`), with paths centralized in `common/.../CommPaths.kt`. Key entry points:
- Phone side: `WatchListenerService` (`WearableListenerService`) receives messages and forwards to `MusicService`; `WatchInfoProvider`/`ButtonConfigTransmitter`/`ActionListTransmitter` push config to the watch.
- Watch side: `PhoneConnection`, `WatchMusicService`, `PreferencesReceiver`, `IdleMessageListener` handle the corresponding receiving/sending logic.
- Communication is bidirectional. The watch reports *back* to the phone with `WatchInfoSender` (`watch/communication/WatchInfoSender.kt`), which sends the watch's own button hardware capabilities as a `WatchInfo` (from `watch.proto`) so the phone knows which physical buttons exist. (Note the phone-side `WatchInfoProvider` is a different thing — it *pushes* config to the watch.)
- Payloads for structured data (action lists, button configs, watch info) are serialized with **protobuf** using the schemas in `common/src/main/proto/`.
- Watch-facing settings are declared in `common/.../MiscPreferences.kt`, edited in the phone's settings UI, and synced phone → watch (received by `PreferencesReceiver`). Add new watch-behavior toggles there, not in watch-local prefs. Phone→watch delivery is owned process-wide by `mobile/.../WatchPreferenceSyncCoordinator.kt` (started in `WearMusicCenter.onCreate`): it listens for default-SharedPreferences changes, debounces/conflates them, pushes via `PreferencePusher` with exponential-backoff retry, and re-publishes once per process start to repair a stale watch — don't add per-screen push listeners (fragment-lifecycle listeners stranding edits is exactly the bug it replaced). It only syncs keys in `MiscPreferences.EXPORTABLE` (plus the `WEAR_DEV_*` diagnostics keys), so a new watch-facing preference must be added to `EXPORTABLE` to reach the watch at all.
- Structured notifications reach the watch via `notifications.proto`, `CommPaths.DATA_NOTIFICATION` (`/Notification`), decoded into `watch/model/Notification.kt`.
- **Media notification actions:** the phone mirrors the active media notification's action buttons to the watch as `MediaAction` entries inside `music.proto`'s `MusicState` (label + rasterized PNG icon + a locale-independent `semantic` hint). `PendingIntent`s can't cross the Data Layer, so `mobile/.../notifications/MediaNotificationActions.kt` is a process-local registry: it keeps the `PendingIntent` on the phone, sends an opaque id to the watch, and resolves the id back when the watch taps the action (the `semantic` field is presentation-only, never an execution token). `MediaActionIdentity.kt` classifies action semantics. These feed the watch's quick-actions panel; MediaSession custom actions are the fallback when no notification actions exist.
- **Logging / diagnostics:** the phone runs **Timber + Firebase Crashlytics** (`mobile/.../logging/TimberCrashlytics.kt`, `CrashlyticsExceptionWearHandler.kt`); the watch forwards its own logs on request via `MusicCenterLogRequestReceiver` (extends `WearLogRequestReceiver` from `wearutils`) over `CommPaths.MESSAGE_SEND_LOGS` (`/SendLogs`) + `CHANNEL_LOGS` (`/Channel/Logs`), so a watch-side crash surfaces in the phone's Crashlytics. Firebase Crashlytics and (since 2.2.1) Firebase Analytics are both active — keep the Data Safety / privacy docs consistent with that. Crash reporting is user-optional: `mobile/.../logging/CrashReporting.kt` centralizes the opt-out (Settings → Data & support → Privacy) — Crashlytics auto-upload stays disabled and finalized reports are sent manually only after the current privacy choice has been read; opting out also deletes queued unsent reports.
- **Developer announcements** also ride Firebase, but as push rather than diagnostics: `mobile/.../notifications/AnnouncementNotifications.kt` mirrors `CrashReporting`'s single-gate shape, subscribing/unsubscribing the device to one fixed FCM topic (`"announcements"`) as `MiscPreferences.ANNOUNCEMENTS_ENABLED` (Settings → Data & support → Privacy, on by default) changes — there is no backend, so a Firebase Console campaign targeting that topic is the entire delivery mechanism, and the app never holds a token/user list itself. `AnnouncementMessagingService` (manifest-registered `FirebaseMessagingService`) renders the received message as a notification.

### Watch-side data flow

`PhoneConnection` (Hilt `@Singleton`) listens to `DataClient` updates and exposes `LiveData` properties (`musicState`, `rawPlaybackConfig`, `rawStoppedConfig`, `customList`, etc.). The two separate configs — playing vs. stopped — let users assign different button actions depending on whether music is currently playing.

`MusicViewModel` (`@HiltViewModel`) consumes `PhoneConnection` LiveData and drives `MainActivity`. It owns `WatchActionConfigProvider` (one for each config) which decodes protobuf action configs from the phone into `ButtonAction` objects keyed by `ButtonInfo`.

`WatchMusicService` is a foreground `LifecycleService` that stays alive while music is playing or the UI is open, keeping `PhoneConnection` active. It shuts down after an idle timeout when neither condition holds. Every full-screen watch activity (now-playing, queue, menu) binds a `UiOpenServiceConnection` to hold the service while it's in the foreground — the Compose windows are opaque, so `MainActivity` underneath them gets stopped and can't be the one keeping the service alive.

`WatchMediaSession` (`watch/communication/WatchMediaSession.kt`) is a `MediaSessionCompat` proxy: it mirrors phone playback state (metadata, playback state, album art, volume) received from `PhoneConnection`, and forwards transport controls (play/pause toggle, skip, seek, volume) back to the phone over the Data Layer. It is owned and lifecycle-managed by `WatchMusicService`. This is the architectural keystone that enables Wear OS system media surfaces, Tiles, and Complications to see and control the phone's music.

### Watch input handling

`MainActivity` handles six input categories:

1. **Screen gestures** — `FourWayTouchLayout` (from `common/`) divides the screen into quadrants; taps in each quadrant are reported as a `ScreenQuadrant` gesture mapped through button config.
2. **Full-screen swipes** — up/down/left swipes on the now-playing screen are pseudo-buttons (`SwipeGesture` in `common/`, buttonCodes chosen outside the quadrant range) flowing through the same `ButtonInfo`/config pipeline as quadrant taps. Right swipe is deliberately never intercepted — it's the system-wide Wear OS dismiss gesture.
3. **Physical stem buttons** — `StemButtonsManager` (`wear/.../view/StemButtonsManager.kt`) translates raw `KeyEvent` sequences into single-tap, double-tap, or long-press gestures per configured button. Includes an ambient-mode phantom-click workaround.
4. **Rotary encoder / digital crown** — handled via `RotaryEncoderHelper` directly in `MainActivity`. On devices with discrete rotary input, crown turns are simulated as button presses (`SpecialButtonCodes.TURN_ROTARY_CW/CCW`) through `StemButtonsManager`, so they're user-configurable like any button. Otherwise, continuous scroll deltas change volume — or scrub the playback timeline instead when the `MiscPreferences.ROTARY_SEEK` preference is on — subject to a configurable deadzone and sensitivity.
5. **On-screen mini buttons** — up to three *visible* configurable buttons (`ScreenButtons` in `common/`, codes 7–9, tap + long-press) rendered as a fixed overlay near the bottom of the now-playing screen; ordered after `center_tap_zone` in the layout so they win touch dispatch over the center play/pause zone and `FourWayTouchLayout`. Row offset is tunable via `MiscPreferences.WEAR_SCREEN_BUTTONS_OFFSET` (phone developer settings).
6. **Quick actions panel** — an overlay opened by double-tapping the center of the now-playing screen (rendered in `MainActivity`): three round configurable slots plus a full-width row (`QuickPanelButtons` in `common/`, codes 10–13, continuing the pseudo-button range). Unconfigured slots now default to mirroring the current media notification's *real* actions (labels + icons, executed on the phone via `MediaNotificationActions` — see the communication section), with MediaSession custom actions as fallback and the older Like / Shuffle / Repeat + "Up Next" queue-preview row behind that; a `NullAction` assignment hides a slot. The phone writes quick-panel assignments into *both* the playing and stopped configs so the panel behaves the same regardless of playback state.

Resolved actions don't always round-trip to the phone: `MusicViewModel.executeActionOnWatch` intercepts actions that make sense locally (opening the menu/queue, opening search input, volume UI) and only sends the rest to the phone for execution.

### Phone app UI

The phone UI is a single activity (`mobile/.../view/mainactivity/MainActivity.kt`) that swaps fragments via a bottom navigation bar: `WatchFaceFragment` (Watch face — see below), `ControlsFragment` (a ViewPager2 with swipeable "Music playing" / "No playback" tabs, each page a `ButtonConfigFragment` — the two configs are presented as states of one feature, not separate nav destinations), `ActionListFragment`, and `SettingsHomeFragment` (a ViewPager2 of `MiscSettingsFragment` sections: General, Behavior/watch, Automation, Apps, Data & support — `MiscSettingsFragment.SECTION_*` args filter which preference categories from `settings.xml` each page shows; service-specific integrations live under Apps — playlist shortcuts (`PlaylistShortcutsActivity`) match a link's source service via `music/StreamingShortcutLinks.kt`'s pure link-detection helper (YouTube Music, Spotify, Deezer, Tidal, Apple Music, Amazon Music, SoundCloud, or a generic fallback), shared with `MusicService`'s launch-intent resolution — these are link shortcuts, not account/API integrations, so the target streaming app still decides whether playback actually starts — see *Actions system* below for how shortcut launches and the autoplay nudge actually work). The usage guide (`TutorialFragment`) is not a tab: it opens in `HelpActivity` from the toolbar's help button. A left navigation drawer holds only app/about info (version, author), not navigation. The activity also owns cross-fragment chrome: the toolbar (plus the `toolbar_main` options menu), a mini player (driven by a `MediaController` bound to the active media session, with queue and detail dialogs), and a shared FAB whose click is dispatched to the current fragment via the `FabFragment` interface.

The **Watch tab** (`mobile/.../view/watchface/`) is the visual customization surface for the watch's now-playing screen: `WatchPreviewView` (a Canvas miniature of the watch honoring the same preference keys the watch reads — face, screen theme, album art style/dim, accent color modes, mini-button appearance/offset — with a miniature per face) docked above a nested `WatchFacePrefsFragment` (`res/xml/watch_face_settings.xml`). The preview is **contextual**: `WatchPreviewView` has a `PreviewSurface` enum (player, AOD, volume, seek, quick panel, queue, mini buttons) and `surfaceForPreference()` maps the preference key being edited to the watch surface it affects, so touching e.g. `wear_volume_style` temporarily previews the volume overlay instead of the player. The miniature shows the phone's *actual* current track when one is playing — `WatchFaceFragment` observes `MainActivity.activeMediaSession()` and feeds art/title/artist into `WatchPreviewView.setNowPlaying()` (Palette-extracts the accent from the real art), a 500ms ticker drives `setPlayback()` so the progress ring/track-time/play-pause state animate live, and `MiniButtonIconLoader` reads the *playing* button-config file off disk (`action_config_playing`, mirroring `DiskButtonConfigStorage`'s format) so the preview's bottom row shows only the mini buttons the user actually configured, with their real icons — all falling back to a built-in sample otherwise. `WatchPreviewView` sizes text to the wear faces' sp values against a 192dp reference watch; keep those (and the cookie/ring geometry) in sync when changing the wear faces. Those appearance preferences were *moved* out of `settings.xml` — the Settings tab keeps behavior-only options — so a watch-appearance preference belongs in `watch_face_settings.xml`, and any new key must also be reflected in `WatchPreviewView.refresh()`/drawing if it changes the screen's look. Shared Lyra preference chrome (HSV color picker dialog, runtime-accent dialog tinting) lives in `view/settings/LyraPreferenceUi.kt`, used by both preference screens. Album-accent → surface-color math (tonal containers, the legacy blur-radius downscale) lives in `common/.../PaletteTransforms.kt` so `WatchPreviewView` and the wear faces/overlays consume the identical functions instead of copies that can drift (same rationale for `common/.../BitmapBlur.kt`, the shared artwork blur — repeated bilinear down/up sampling rather than `RenderEffect`, which is API 31+ and needs a `RenderNode`, so it works on every supported watch and in the phone preview alike); `WatchPreviewView` still duplicates the parts that can't be shared that way — cookie/ring geometry — since `mobile` cannot depend on `wear`, so keep those in sync by hand when changing the wear faces.

Watch-tab **appearance preferences are scoped per face**: `common/.../FaceScopedPreferences.kt` stores each appearance key in its `SCOPED_KEYS` set as `"<baseKey>@<face>"` and resolves reads as explicit per-face value → per-face default → legacy global value → definition default (one carve-out: a *non-default* legacy `wear_album_art_style` value beats the per-face default, because `default_config.json` seeds `cover` on every install so key presence alone isn't user intent). The per-face defaults give album-accent faces "tonal" quick-panel/queue/volume and "expressive" seek surfaces, give each face its matching background via `PlayerBackgroundStyle.defaultForFace()` (`common/.../PlayerBackgroundStyle.kt` — the artwork/background treatment enum, selectable independently of the structural face and rendered on the watch by `watch/view/PlayerBackgroundDrawable.kt`), and deliberately *beat* a pre-scoping global value (that value was never chosen for the face). The Watch-tab preference screens write through `mobile/.../view/settings/FaceScopedPreferenceDataStore.kt` (scoping by the current `wear_screen_face`), the flat SharedPreferences phone→watch sync carries the scoped entries unchanged, and the watch resolves through the same common object — so the settings UI, the preview, and the watch can't disagree. A new watch-appearance preference that should be per-face must be added to `SCOPED_KEYS`; behavior prefs and the face selector itself stay global, and `wear_quick_panel_source` is deliberately unscoped (it drives a phone-side binding with no per-face notion).

Scoping arrived in 3.0, so an in-place upgrade from 2.x carries one pre-scoping global value that keeps bleeding into whichever per-face defaults it happens to match — `mobile/.../view/watchface/FaceResetMigrationPrompt.kt` (called once from phone `MainActivity.onCreate`) recommends "Reset all faces to default" exactly once per device. It cannot detect the upgrade from its own preference key (new in the same build that reads it, so a fresh install and an upgrade look identical on the run that matters); it compares `PackageInfo.firstInstallTime` vs `lastUpdateTime` instead. Its reset path is `WatchFacePrefsFragment.resetAllFaces(context, prefs)` — shared with the Watch tab's button, so keep them one function.

**Custom watch themes** layer on top of face scoping: `common/.../ThemeAppearance.kt` decides which appearance context is active — `AppearanceContext.BuiltIn` (the per-face resolution above) or `AppearanceContext.Custom`. The phone keeps a library of up to 24 named profiles in `mobile/.../view/watchface/theme/WatchThemeRepository.kt` (managed in `WatchThemesActivity`, opened from the Watch tab), stored as JSON in a *separate* named SharedPreferences file — deliberately, since the default prefs file is mirrored wholesale to the watch. Applying a profile materializes exactly one complete snapshot into the fixed `custom_active` scope (`"<key>@custom_active"`) plus metadata prefs (`wear_active_custom_theme_id` / `_schema` / `_complete` / `_revision`) in a single default-prefs transaction. Both the watch and the preview resolve through `ThemeAppearance.resolve()`; a Custom context reads *only* the snapshot (never legacy globals or `key@<face>` values) and falls back to the built-in base face whenever the snapshot is incomplete or its schema mismatches — so a partially synced theme can never activate. The snapshot's key set derives from `FaceScopedPreferences.SCOPED_DEFINITIONS` (= `EXPORTABLE` ∩ `SCOPED_KEYS`), so a new scoped appearance preference must be in both registries or profile capture/import will silently drop it.

The redesigned phone theme is internally named **Lyra** (resource names like `dialog_bg_lyra`, `lyra_*` selectors). The accent color can be static, user-picked, or dynamically extracted from album art; `view/LyraAccent.kt` is the single source of truth for resolving the currently displayed accent outside `MainActivity` (standalone dialog activities use it to match what's on screen).

### Actions system (mobile)

Button presses/gestures map to `PhoneAction` subtypes (`mobile/.../actions/`), each with a corresponding `ActionHandler<T>` implementation (playback, volume, app-launch, Tasker, open menu/playlist, etc.). New actions typically need: an action class, a handler, a binding in `di/ActionHandlersModule.kt`, and an entry in the relevant action list (`RootActionList`, `PlaybackActionList`, `VolumeActionList`).

The saved streaming-shortcuts library doubles as an action-picker category (`StreamingShortcutActionList`): each saved link becomes an assignable `PlayPlaylistShortcutAction`. **Streaming-shortcut launches are watch-initiated:** modern Android blocks a background phone service from starting activities, so an action can carry an optional `remoteUri` (`actions.proto`, present on both button-config and action-menu entries; format `targetPackage|uri` or a bare URI, produced by `PlayPlaylistShortcutAction.remoteUri`). When the watch resolves such an action, `MusicViewModel` does two things at once: it opens the URI on the phone via `RemoteActivityHelper.startRemoteActivity` (watch `MainActivity.openUriOnPhone`, which rejects unsafe URI schemes first), *and* still round-trips the action so `MusicService.playDeepLink` runs on the phone.

`playDeepLink` (mobile) is the actual playback engine and tries progressively stronger contracts because merely *opening* a link only navigates, it doesn't play: (1) if the target app already has any active session (found across **all** active sessions via `ActiveMediaSessionProvider.controllerForPackage`, not just the tracked "current" one), issue `playFromUri`; (2) otherwise ask the app's `MediaBrowserService` to play through `mobile/.../music/MediaBrowserPlayback.kt` — the Android Auto/Assistant path, the only one that works with the screen off / app not running, since binding the browser wakes the app with no Activity launch (this is why the YT Music Liked-Music shortcut plays even after a force-stop; Spotify usually rejects unknown browser clients, so it falls through); (3) finally the visible deep-link open + a media-session nudge (`MediaBrowserPlayback` retries the play command while the freshly-woken session warms up). **Artists** are special: a `playFromUri` on an artist page only navigates, so `StreamingShortcutLinks.isPlayable` treats `ARTIST` as playable and the shortcut's saved *name* is passed as a `playFromSearch` query (the one command both YT Music and Spotify honor from outside) — for precise entities (track/album/playlist) the URI stays authoritative and search is never substituted. `forPlayback` also canonicalises YouTube share links (`youtu.be`, plain `youtube.com`, `/playlist`) into the `music.youtube.com/watch` form that actually starts playback. Dedicated one-tap actions exist for the account "Liked Songs" of YouTube Music (`PlayLikedSongsAction`, `watch?list=LM`) and Spotify (`PlaySpotifyLikedSongsAction`, `spotify:collection:tracks`). When there is *no* current session at all (the watch's "Nothing playing" idle screen), a play/pause command resumes the last app via `AudioManager.dispatchMediaKeyEvent(KEYCODE_MEDIA_PLAY)`.

**Optional online shortcut thumbnails** (`mobile/.../music/ShortcutArtworkFetcher.kt` + `ShortcutArtworkStore.kt`): strictly opt-in (`streaming_shortcut_artwork` pref, off by default — one of only three network paths, with the update check and the opt-in queue-cover fetch under *Playback queue* below), it fetches each saved shortcut's cover once from the service's public **oEmbed** endpoint (Spotify/YouTube/SoundCloud/Deezer), caches the PNG on disk keyed by link, and surfaces it in the phone list, as the assigned action's icon (`PlayPlaylistShortcutAction.defaultIcon`), and on the watch menu — the latter by attaching the PNG as a per-index DataItem asset in `PlaylistShortcutStorage.createDataRequest` (the watch's `decodeCustomList` already reads `assets[index]`, so no watch change was needed). Editing a saved shortcut propagates to every already-assigned copy via `PlaylistShortcutActionSync` (button configs + action list, matched by old link, re-committed through the normal path); the Actions screen re-reads its config in `onResume` (`ActionListViewModel.refreshFromConfig`) so a rename shows up there too.

### Playback queue (mobile)

`OpenPlaylistAction` builds the watch's queue list. Two failure modes that look identical to a user ("no queue" / "no covers") have entirely different causes, so both have dedicated machinery:

- **Encoding**: queue thumbnails are JPEG (`OpenPlaylistAction.encodeThumbnail`), deliberately *not* `BitmapUtils.serialize`, which is lossless PNG. Cover art is photographic with no alpha, so PNG is several times larger — the reasoning `MusicService.transmitToWear` already records for the single now-playing cover, but multiplied by up to 20 assets in one DataItem. The watch decodes with `BitmapUtils.deserialize` (`BitmapFactory.decodeByteArray`), which is format-agnostic, so only the sender needed changing.
- **Which controller is reported** is decided by the pure `resolveReportedSession()` (tested by `ReportedSessionTest`): the playing session, else the last reported one *while it is still live*. `ActiveMediaSessionProvider.currentController` is null whenever nothing plays, so a pause fallback must read `lastReportedController` instead — reading `currentController` meant the first pass after a pause looked right and every later pass reported null, dropping the watch to the idle screen mid-pause.
- **Acquisition** goes through `MusicService.resolvePlaybackQueue()`, not `currentMediaController.queue` directly. Some players run several `MediaSession`s at once — Retro Music ships a `WearBrowserService` session beside its playback one — and only one carries the queue, while the tracked controller is chosen by which session is *playing*. `ActiveMediaSessionProvider.siblingQueueForPackage` covers that gap before the code falls back to `recentTrackHistory` (`CustomLists.HISTORY`). A player that publishes no queue at all (pre-6.x Retro Music never called `setQueue`) genuinely cannot be helped — history is the honest answer.
- **Artwork** goes through `mobile/.../music/QueueArtworkResolver.kt`, a cheapest-first chain: `iconBitmap` → local `iconUri` → artwork URIs in `description.extras` → MediaStore (`loadThumbnail`, else `ALBUM_ID` → the legacy `albumart` table) → remote http(s), with `MusicService.currentAlbumArt` as a final fallback for the row whose `queueId` matches `activeQueueItemId`. That last step matters more than it looks: Media3's `MediaSessionLegacyStub` attaches a bitmap to a queue item **only** when the app embedded raw `artworkData`, while the current track's *metadata* goes through `loadBitmapFromMetadata`, which downloads `artworkUri`. A streaming client (Echo Music, YouTube Music front-ends) therefore shows art on the player while **every** queue row — including the playing one — carries nothing but a remote URL. Reusing the already-decoded player cover costs no network call and no permission. Two steps are gated:
  - MediaStore needs a media-read grant. `READ_EXTERNAL_STORAGE` stopped being grantable at `targetSdk` 33, so `READ_MEDIA_AUDIO` is declared and requested **in context** from the `queue_media_permission` row in Settings → Apps (`MiscSettingsFragment`), never at startup. Ungranted, the step is skipped silently.
  - Remote covers are the Echo Music / YouTube-Music-client case (Media3's `artworkUri` maps onto the legacy description as an http URL). Gated on `queue_remote_artwork`, which is **on by default** (`QueueArtworkResolver.REMOTE_ARTWORK_DEFAULT`) — the exception to the project's otherwise opt-in network stance, because a streaming queue has *no* other cover source, so off produced permanently blank rows rather than a degraded list; the shortcut-artwork fetch stays opt-in since it degrades to an app icon. Defaults are never persisted (`setDefaultValues` is not called anywhere), so this flips for existing installs that never touched the switch. Results are cached on disk and the requested size is rewritten into the URL first (`sizedArtworkUrl`, tested by `SizedArtworkUrlTest`): those clients publish a list-sized ~60px thumbnail, and since `shrinkPreservingRatio` only ever shrinks, fetching it verbatim left Cover-style pills visibly pixelated with no later step able to recover — reusing `ShortcutArtworkStore`, which is a plain URL-keyed PNG cache with no shortcut-specific notion. The download applies the same hardening `ApkDownloader` documents (follow redirects, explicit `User-Agent`, `Connection: close` against Android's truncate-on-redirect pooling bug). **This is a network path: keep `docs/privacy-policy.md` and the Data Safety draft consistent when touching it.** The toggle is intentionally declared in *both* `settings.xml` (Apps) and `watch_face_settings.xml` (Panels, beside the queue styling) — it is not in `SCOPED_KEYS`, so the face-scoped data store passes it through unscoped and both rows drive the one global key.
  - `OpenPlaylistAction` resolves every entry's cover concurrently (`coroutineScope { ... async { QueueArtworkResolver.resolve(...) } }.awaitAll()`), not one at a time — a 20-entry queue with several slow/failing remote fetches would otherwise serialize into seconds of wall-clock delay even though each fetch is already off the main thread. `QueueArtworkResolver` logs each entry's resolution path at `Timber.v` (candidates found, which step matched, why a step was skipped) for exactly this kind of "some covers just don't show up" report.

### Config backup (mobile)

`mobile/.../config/ConfigBackup.kt` exports/imports both button configs, the action list, the `MiscPreferences.EXPORTABLE` watch-behavior settings, the custom watch-theme library (`watchThemes` — see the Watch tab section; since schema 3), and (since schema 4) the user's personal runtime data — saved playlist shortcuts, search history and track history — under a `userData` block, as one JSON document (exposed in `MiscSettingsFragment`). The button-config/action-list files are copied as opaque base64 `PersistableBundle` blobs, so the backup format doesn't need updating when configs gain fields — but adding a *new* config file or a preference that should survive reinstall means touching `CONFIG_FILES` or `MiscPreferences.EXPORTABLE`. The theme library is validated as one unit before any import write (all-or-nothing), and importing a pre-theme (schema 1/2) backup deactivates any active custom theme so the imported `wear_screen_face` can't silently rewrite a saved profile's base layout. The `userData` block holds the three storages' raw JSON strings (`playlist_shortcuts`, `search_history`, `track_history`) and is restored in the same preference transaction; importing re-syncs the shortcut library to the watch. Older backups (schema ≤ 3) simply omit `userData` and leave whatever is already on the phone.

**Parcel-stability warning:** those blobs (and the on-disk config files themselves, `mobile/.../util/BundleFileSerialization.kt`) are raw `Parcel.marshall()` bytes, whose format is *not stable across Android OS versions* — a blob written on one version can throw `BadParcelableException` on another, and only **lazily** (at the first `bundle.get*()` call, far from the read site; nested bundles defer even further). This crashed the Watch tab on Android 15. Consequently: `readFromFile` force-unparcels inside its own guard, quarantines undecodable files (`<name>.corrupt`) and never throws; every deep bundle walk must still catch `RuntimeException`; `ConfigBackup.import` validates all blobs *before* writing anything (`BundleFileSerialization.isDecodable`) and throws on incompatible backups — which also makes `GlobalActionConfig`'s bundled-default seeding (`R.raw.default_config`, itself such a backup exported on some past device/OS) fall back to auto-detected defaults instead of planting an unreadable config. Writes go through temp-file + atomic rename.

### Update system (sideload self-updates)

Because the app is sideload-only, it ships its own updater. Phone side lives in `mobile/.../update/`: `UpdateChecker` polls the GitHub releases API (throttled to daily; triggered from `MusicService.onCreate` and phone `MainActivity.onCreate`; prefs `update_check_enabled` / `update_include_prereleases` in the Settings tab's Updates category), `UpdateNotifier` posts the notification, and `UpdateActivity` is the single update surface (versions, release page, push-to-watch). Release assets are matched **by exact name** (`mobile-release.apk` / `wear-release.apk`) — keep naming releases that way. `WatchApkPusher` downloads the wear APK and streams it over `CommPaths.CHANNEL_WEAR_APK`; on the watch, `watch/update/ApkReceiverService` (manifest `CHANNEL_EVENT` listener) receives it, validates the package name, and commits a `PackageInstaller` session, with `InstallResultReceiver` turning `STATUS_PENDING_USER_ACTION` into a tap-to-install notification (background services can't launch the confirm dialog) and `MY_PACKAGE_REPLACED` doing post-update cleanup. Needs `REQUEST_INSTALL_PACKAGES` + the user's one-time "install unknown apps" grant on the watch. The "Update watch" button is gated on the *watch's* version, reported via the `appVersionCode`/`appVersionName` fields of `watch.proto`'s `WatchInfo` (absent on pre-2.2 watch builds). Both app modules have `buildConfig true` enabled for `BuildConfig.VERSION_NAME` access.

The **phone updates itself** through the same shape: `ApkDownloader` (shared byte-count-validated download) → `PhoneApkInstaller` → `PhoneInstallResultReceiver`, mirroring the watch's `ApkReceiverService`/`InstallResultReceiver`. Two non-obvious constraints, both learned from an unlocalized system "There was a problem parsing the package" failure with no recovery path: the download is validated as a genuine APK *for this package* (`getPackageArchiveInfo` + package-name check) **before** it ever reaches an installer, since a matching byte count still misses same-length corruption; and it is committed through a `PackageInstaller` session rather than an `ACTION_VIEW` intent at the file — so there is deliberately **no FileProvider** in `mobile/` for APKs (sessions write from a `File` directly; the old `apk_paths.xml` was removed, don't reintroduce it). Missing "install unknown apps" is reported as a `Progress.NeedsPermission` state that opens the settings screen, never as a failure.

### Custom lists (watch menu content)

Several watch-facing features are phone-side SharedPreferences storages (`mobile/.../music/*Storage.kt` — search history, playlist shortcuts, track history) delivered to the watch as **custom lists**; the list types (live queue, recently-played fallback for apps that hide their queue, search results, playlist shortcuts, search history) are defined in `common/.../CustomLists.kt`, and selection/deletion round-trips through `MusicService.onCustomMenuItemPresed` and `CommPaths.MESSAGE_DELETE_CUSTOM_LIST_ITEM`. Watch-initiated search (`SearchAction`) opens voice/keyboard input on the watch; the query returns via `CommPaths.MESSAGE_PLAY_FROM_SEARCH` and is resolved with `MediaBrowserSearch` (MediaBrowserService library search — the Android Auto/Assistant mechanism, far more reliably implemented by music apps than `MediaSession.playFromSearch`).

### Localization

The app ships translations for 13 locales, and the UI language is a **user preference that syncs to the watch**, not just a device setting: `MiscPreferences.APP_LANGUAGE` (in `EXPORTABLE`) is picked in the phone's Settings and resolved on both sides through `common/.../AppLocales.kt`, so a phone set to Portuguese doesn't leave an English watch. The two apps *apply* it by different means, deliberately — `mobile/.../view/settings/AppLanguage.kt` uses `AppCompatDelegate.setApplicationLocales` (every phone activity is an `AppCompatActivity`, and on Android 13+ this registers with the framework's per-app language setting), while `wear/.../util/WatchLanguage.kt` wraps each activity's base context, because `MenuActivity`/`QueueActivity` are plain `ComponentActivity` and AppCompat's pre-33 backport only recreates `AppCompatActivity`. Unknown/unsupported tags resolve to the system language rather than to themselves, since a value can arrive from an imported backup or a newer build on the other device.

Adding a language means keeping four places in step, all of which must agree or the picker lies about what's translated: a `values-<code>` folder in **each** of `mobile/`, `wear/` and `common/` (each module carries its own strings; `common/` backs shared views), `AppLocales.SUPPORTED` (order = picker order), `mobile/src/main/res/xml/locales_config.xml` (the Android 13+ system picker), and the `app_language_entries`/`app_language_values` arrays.

## Build & test commands

Requires JDK 21 and an Android SDK path in `local.properties` (`sdk.dir=...`, gitignored — Android Studio creates it on first sync). After cloning, run `git submodule update --init` before building (see `wearutils/` above).

Standard Gradle/Android workflow (run from repo root):

```
./gradlew assembleDebug              # build phone app debug APK
./gradlew :mobile:assembleDebug      # build only the mobile module
./gradlew :wear:assembleDebug        # build only the wear module
./gradlew test                       # run all JVM unit tests

./gradlew :wear:testDebugUnitTest --tests "*.StemButtonsManagerTest"
./gradlew :common:testDebugUnitTest  # common-module tests
./gradlew lint                       # Android lint across modules
```

Unit tests live under `mobile/src/test`, `wear/src/test`, and `common/src/test` (JUnit 4). `wear/build.gradle` uses the `unmock` plugin to run certain Android-framework-dependent tests on the JVM instead of mocking — see the `unMock { ... }` block when adding tests that touch `android.*` classes in `wear`.

There is no instrumented/UI test setup in this repo currently.

To sideload builds onto real devices, `serve_apk.py` (repo root) serves the assembled mobile/wear debug and release APKs over HTTP on the local network (port 8765) — build first, then `python3 serve_apk.py` and download from the phone/watch browser.

## Package naming gotchas

The app was renamed from Music Center for Wear (fork of matejdro/WearMusicCenter): all code now lives under `com.svartifoss.snfell` / `com.svartifoss.snfell.common`. Older docs/commits referencing `com.matejdro.wearmusiccenter` mean the same code.

- Despite living in `wear/`, the watch-side code is under the package `com.svartifoss.snfell.watch.*` (not `.wear.*`) - that's the Gradle `namespace`, used for generated R/BuildConfig classes only. All watch-side classes (`PhoneConnection`, `WatchMusicService`, `MainActivity`, etc.) are in subdirectories named `watch/communication/`, `watch/view/`, `watch/model/`, `watch/config/`, `watch/util/`.
- The Gradle **`applicationId`** **must be identical** in `mobile/` and `wear/` (both `com.svartifoss.snfell`) and both apps must be signed with the same key. The Wearable Data Layer API (`MessageClient`/`DataClient`) only routes messages/DataItems between a phone app and a watch app that share the same `applicationId` — a mismatch means the two apps never connect and both report "No watch connected". (This regressed once: the wear app was briefly given `com.svartifoss.wrfell` for a separate Play Store listing, which broke all phone⟷watch communication.) Both apps therefore ship as same-key sideloadable APKs — the identical `applicationId` is a Data Layer requirement, not a store one. `MainActivity.openWatchPlayStorePage()` (mobile) still opens `market://details?id=<WEAR_APPLICATION_ID>` (== the phone package), but with the app no longer on the Play Store this path is effectively **vestigial**; regardless, `WEAR_APPLICATION_ID` must still equal `wear/build.gradle`'s `applicationId`.
- `mobile/` still contains one deliberately un-renamed package: `com.matejdro.wearvibrationcenter.notificationprovider`. This isn't just a name to preserve — it backs a **functioning notification-access interop subsystem** (`mobile/.../notifications/NotificationProvider.kt` plus the AIDL contract in `mobile/src/main/aidl/com/matejdro/wearvibrationcenter/notificationprovider/`) that lets the separate Wear Vibration Center app read notifications through Svartifoss. Renaming the package would break that cross-app AIDL binding.
- The `wearutils/` submodule keeps its own `com.matejdro.wearutils.*` packages.

## Modernization roadmap

`docs/wear-modernization-plan.md` contains the full phased modernization strategy: Foundation (targetSdk bump — now at 35 — and deprecated API cleanup) → MediaSession mirror (watch-side `MediaSession` that forwards controls to the phone) → Tiles & Complications → in-UI navigation. Consult this doc before making architectural decisions in `wear/`.

**Current state (merged to `master`):** `WatchMediaSession` is implemented and active (Phase 1), and the Phase 2 Tiles & Complications surfaces exist: two Tiles (`watch/tile/`, built with `androidx.wear.protolayout`/`androidx.wear.tiles` — `MediaTileService.kt` for track info/transport/seek, and `ShortcutsTileService.kt` rendering the synced playlist-shortcut custom list as tappable chips, each dispatched through the invisible trampoline `ShortcutLaunchActivity`, because a Tile `Clickable` can only start an Activity — never send a Data Layer message — so it re-performs the same open-URI-on-phone + `MESSAGE_CUSTOM_LIST_ITEM_SELECTED` pair the watch menu does, see *Actions system*) and a complication data source (`watch/complication/AlbumArtComplicationDataSourceService.kt`, `androidx.wear.watchface` complications). Because these run outside the main app UI lifecycle, they fetch music state directly over the Data Layer via `CommPaths` rather than through `PhoneConnection`; the manifest-registered `MusicStateListenerService` (`watch/communication/`) requests a Tile + complication refresh whenever the phone publishes new music state — `WatchMusicService` does the same while running, but it idle-times out, and without this listener the surfaces froze on stale state. It also revives a dead `WatchMusicService` when the received state says music is playing (the phone only sends `MESSAGE_START_SERVICE` on a playback-*start* edge, so a service that died mid-playback would otherwise stay dead). A sibling `ConfigListenerService` (`watch/communication/`) does the analogous job for the button-config (`/Actions/*`) and action-menu (`/ActionList`) DataItems: those have no other always-on delivery (they arrive only through `PhoneConnection`'s runtime `DataClient` listener, live only while the connection is active), so a config edited on the phone while the watch is idle used to apply only after the user woke/tapped the watch. The manifest listener posts the frozen `DataItem` into `PhoneConnection`'s config `LiveData` — which the `WatchActionConfigProvider`/`WatchActionMenuProvider` observe with `observeForever` — so an open now-playing screen re-decodes and applies the change with no interaction.

Jetpack Compose for Wear OS (`wear.compose.material3`) is enabled in `wear/build.gradle` and used for `QueueActivity`/`QueueScreen` (`watch/view/queue/`) and `MenuActivity`/`MenuScreen` (`watch/view/menu/` — the actions/custom-list menu, which replaced the old `WearableDrawerLayout` bottom drawer; `MenuActivity` is a pure picker that returns the selection for `MainActivity` to execute). Shared Compose chrome (curved clock, scroll indicator, spinner) lives in `watch/view/compose/WatchScreenChrome.kt`; design constants for all three UI stacks live in `watch/theme/WatchTheme.kt` — including the typography catalog: `MiscPreferences.WEAR_FONT` picks the track title/artist typeface via `watchFontFamily()` (system families plus bundled fonts — retro typewriters, Google Sans, Poppins, Montserrat, Marcellus; keep that mapping in sync with the phone's `wear_font_values` array and `WatchPreviewView`'s typeface mapping). A bundled font must be dropped into **both** `mobile/src/main/res/font/` and `wear/src/main/res/font/` (the preview and the watch each load their own copy) with its license text added under `licenses/<font>/`, with a keyword easter egg (`lainFont()`) that overrides the chosen font when the track/artist text matches Serial Experiments Lain-adjacent keywords.

New watch UI work should prefer Compose; the legacy View-based `MainActivity` (now-playing screen) remains, but its central rendering is now a swappable **now-playing face** (`watch/view/face/NowPlayingFace.kt` — a state-in/events-out contract, selected by `MiscPreferences.WEAR_SCREEN_FACE`): "classic" is the original View presentation (MainActivity itself is its implementation), "expressive" is a Compose face (`watch/view/face/ExpressiveFace.kt`, mirroring the Material 3 Expressive system media controls: cookie play/pause button, contour-following progress ring, round tonal transport buttons, accent-tinted/vignetted backdrop; queue/volume/menu access is left entirely to the user's configured mini buttons and gestures — there is no fixed default glass trio, so there's never a second, conflicting set of shortcuts), and the remaining keys — "vinyl", "poster", "studio", "halo", "aurora", "eclipse" (true-black AMOLED), "spectrum" (animated per-track bar field), "material" (capsule/tonal-surface treatment), "immersive" — are the **curated player collection** in `watch/view/face/CuratedPlayerFaces.kt`, which replaced the old standalone `VinylFace.kt`/`PosterFace.kt` Beta faces. Curated faces share one interaction contract: the single visual focus toggles play/pause, double-tap opens quick actions, long-press opens the queue; previous/next/menu/volume are deliberately left to the configurable mini buttons and gestures. Their gradients/progress/accents come from album-art-derived palettes (`watch/theme/AlbumPalette.kt`), and each ships a dedicated ambient variant. All Compose faces render in the single `ComposeView` (`composeFaceKind` picks which) layered between the gesture layers and the overlays, keep the expressive face's bottom pill-trio geometry so the shared mini-buttons/quick-panel fit unchanged, ship their own outline AOD variant (AOD "follow" maps each Compose face to itself), and share small building blocks via `FaceChrome.kt`. A new face key must also be added to `ThemeAppearance.ALLOWED_BASE_FACES` (the canonical registry both sides validate against), the phone's `wear_screen_face_entries/values` arrays, `WatchThemeRepository`'s face-name map, and given a miniature in `WatchPreviewView`. All input handling (quadrants, swipes, stem, rotary, mini buttons, quick panel) is face-agnostic and stays in MainActivity; the hidden classic views keep being updated (ambient mode and the quick panel read from them).

**Colour treatments and typography** both resolve in `common` so the watch, the phone preview and the settings UI cannot disagree. `SurfaceColorTreatment` is the vocabulary (Normal/Desaturated/Expressive plus the harmony cases Complementary/Triadic/Analogous/Monochrome/Duotone); `ColorHarmony` holds the derivation math and `ColorModifier` (`wear_color_modifier`: none/vibrant/pastel/warm/cool) the orthogonal tone filter applied afterwards; `SurfacePaletteResolver.derive()` is the **single entry point** all three callers use — wear `MainActivity.resolveSurfacePalette`/`applyAccentColor`, `WatchPreviewView`, and `ColorTreatmentPreference`'s swatch dialog. Every treatment deliberately anchors its **primary** to the album's own hue and rotates only the companion slots, so switching treatments alone never changes the main accent; `wear_color_hue_shift` (0–359°, applied last inside `derive`) turns all three slots together, which varies that primary while preserving each harmony's internal angles. It is skipped for `NORMAL` — that colour was picked by hand, so rotating it would render something other than what the picker showed. Adding a treatment means a case in the enum + resolver and an entry in both `wear_color_treatment_*` and `wear_component_color_treatment_*` arrays; nothing else. Two rules the harmony math enforces and `ColorHarmonyTest` pins: a hue rotation is meaningless below `CHROMATIC_SATURATION_FLOOR`, so near-greyscale artwork degrades to a tonal ladder instead of yielding three identical greys; and a neutral source is never clamped up into the legible saturation band, which would invent a tint the cover never had. `WatchTypography` does the same job for the per-element title/artist controls (weight — a free 1–1000 value, not stepped — italic, scale, opacity, tracking, plus source-icon scale/opacity), returning primitives so Compose faces, the classic View face and the preview's `Paint` each apply them their own way. **Every default is the exact identity, and identity means "keep what this face designed"** — weight 400 leaves a deliberately-bold face bold rather than flattening it to 400. AOD is deliberately *not* affected: it has its own `WEAR_AOD_*` controls. These controls live in the Watch tab's own **Typography** section (`WatchFacePrefsFragment.SECTION_TYPOGRAPHY`, `cat_wf_typography_*` categories in `watch_face_settings.xml`) rather than under Style/Colors, so the font/title/artist/icon controls aren't buried among layout and colour settings.

One font in the `WEAR_FONT` catalog, **Google Sans Flex** (`WatchTypography.FLEX_FONT_KEY`), is a true OpenType variable font with six axes (`wght`, `wdth`, `opsz`, `slnt`, `GRAD`, `ROND`; bounds pinned to the bundled font's own `fvar` table, not guessed). `wght`/`slnt` reuse the per-element weight/italic controls above (so Flex doesn't add a second, conflicting weight control); the other four — width, optical size, grade, roundness — are deliberately *global*, not per-element, and only shown (`cat_wf_typography_flex`, toggled live by `WatchFacePrefsFragment.initTypographyDependencies`) once Flex is actually selected. `WatchTypography.flexVariationSettings()` builds the one variation string both sides render from: the watch's classic face resolves it via `WatchTheme.flexTypeface` (`Typeface.Builder(File)` — the font resource has no direct-from-resource-id builder constructor, so it's extracted to a cache file once per process), Compose faces via `WatchTheme.flexFontFamily` (`Font(resId, variationSettings = FontVariation.Settings(...))`, gated behind `@OptIn(ExperimentalTextApi::class)`), and the phone preview via its own identical `Typeface.Builder(File)` path — same extract-to-cache trick, since `mobile` cannot depend on `wear`. The bundled `google_sans_flex.ttf` (~4.1MB, in both `mobile/src/main/res/font/` and `wear/src/main/res/font/`, OFL-licensed under `licenses/google-sans-flex/`) is the true variable master, not a static instance — smaller combined than the two static Google Sans weights it sits alongside.

The colour treatments above only *compute* a distinct secondary/tertiary — on the classic face, nothing drew them anywhere visible (progress bar and artist text render only the primary slot, and every album-derived treatment deliberately keeps the primary close to the raw accent), so switching Expressive→Triadic looked like a no-op. `CircularProgressSeekBar`'s `RingStyle.SOLID` (the default ring style) now paints a primary→secondary→tertiary sweep gradient instead of a flat fill, but *only* when `ColorHarmony.hueDistance` between them clears `MIN_DUOTONE_HUE_GAP` — so Normal/Desaturated/Expressive/Monochrome (whose secondary/tertiary sit close in hue) render pixel-identical to before, and only the hue-rotating treatments (Triadic, Complementary, Analogous, Duotone) visibly change. `WatchPreviewView.drawEdgeSeekRing`'s `"solid"` branch mirrors the same conditional gradient so the phone preview doesn't lie about what the watch will show.

Orthogonal to face *structure* is the universal control-style treatment `ScreenTheme` (`common/.../ScreenTheme.kt`, pref `MiscPreferences.WEAR_SCREEN_THEME`: default / minimal / compact / cinema / vivid / contrast / amoled / hidden — "hidden" draws no control icons while keeping touch targets and accessibility actions active). It lives in `common` so the phone preview and the watch decode exactly the same tokens and can't drift apart (the wear-side `watch/view/face/ScreenTheme.kt` is just typealiases into it); `common/.../OverlayBackdrop.kt` does the same for the volume/seek/quick-panel overlay backdrops. Per-element visibility follows the same shared-pref pattern: `WEAR_SHOW_TRACK_TITLE` / `WEAR_SHOW_TRACK_ARTIST` (status/error text stays visible regardless), `WEAR_PLAYER_CONTROLS_VISIBLE` (persisted under its old key `wear_classic_icons_visible` so existing installs and backups migrate losslessly), and separate internal-progress (`WEAR_INTERNAL_PROGRESS_VISIBLE`) vs. edge-progress (`WEAR_EDGE_PROGRESS_VISIBLE`) visibility with independent edge-seek enablement.

The always-on display is separately configurable via `MiscPreferences.WEAR_AOD_STYLE` ("follow"/"classic"/"expressive"/"minimal") plus per-element toggles (`WEAR_AOD_SHOW_ART`/`_CLOCK`/`_TRACK_INFO`/`_TRANSPORT`/`_PROGRESS`/`_PILLS`), an outline color mode (`WEAR_AOD_COLOR_MODE` white/album/custom, lightness-lifted on the watch for legibility on black) and a brightness scale (`WEAR_AOD_INTENSITY`), all configured in the phone's Watch face tab: the classic AOD is the original View presentation, the expressive AOD is `ExpressiveFace` with `NowPlayingFaceState.ambient` set (outline-only, animation-free, same geometry as the awake face so wake-up taps land on the intended button), and "minimal" is dimmed text on pure black; `MainActivity.applyAmbientPresentation()` is the single place that styles ambient, and every variant keeps the burn-in pixel jiggle. Touch is never delivered to apps in ambient (the system wakes the watch instead) — only stem buttons/rotary work there, so AOD "buttons" are display-only by platform constraint.

Surface-level visual styling (volume overlay, quick panel, queue screen) is independently user-selectable per surface via `MiscPreferences` string prefs (e.g. `WEAR_VOLUME_STYLE`), each decoded to a local `*Style` enum (see `CircularVolumeBar.VolumeStyle`) with a `fromPref()` mapper — new styles are additive enum cases plus a `when` branch in that surface's paint/draw logic, not a new preference.

**Player shading** (the darkening overlay for legibility, `common/.../PlayerShading.kt` / `PlayerShadingDrawable.kt` on the watch, mirrored in `WatchPreviewView`) has three user controls, all face-scoped: a **style** (`wear_player_shading_style`), a **numeric intensity** (`album_art_dim_strength`, a 0–150 % value read as `percent/100f`; the old named `wear_player_shading_intensity` soft/balanced/strong pref is retained only to migrate legacy values — `PlayerShadingIntensity.percentFor`), and a **colour** (`wear_shading_color_mode`: black / album accent / desaturated / custom `wear_shading_custom_color`, resolved to a dark chromatic tone via `PaletteTransforms.shadingTone`). The clamp ceiling is the shared `SHADING_MAX_MULTIPLIER` const, not a hardcoded 1.0. Authored *background* styles (Expressive, Poster, …) render their designed look independent of the "Dim album art" toggle — that toggle governs only the separate legibility scrim over plain artwork; the shared "apply this look to all faces" action in the Watch tab (`WatchFacePrefsFragment.applyCurrentAppearanceToAllFaces`) copies the current scope's explicit `SCOPED_KEYS` values onto every face.

Two watch-lifetime behaviours: the classic idle "Nothing playing" screen taps through to configured stopped-config gestures, but a play/pause command with no session resumes the last app (`AudioManager` PLAY key, see *Actions system*); and `MiscPreferences.WEAR_CLOSE_ON_IDLE` (default on, `MusicViewModel`) auto-closes the app ~60 s after reaching the truly-idle state, distinct from the user-configurable `CLOSE_TIMEOUT` which covers the paused case and stays off unless set.
