# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Svartifoss — an Android app that lets a paired Wear OS watch control music playback on the phone (and on the watch itself), with customizable physical buttons / digital crown / gestures. **Sideload-only**: the phone and watch APKs are installed manually from GitHub releases (watch install via Wear Installer). A self-hosted F-Droid repo used to be served from GitHub Pages under `docs/fdroid/`; it was retired in 3.1-beta2 having fallen three versions behind, and GitHub releases are now the single distribution channel — don't reintroduce it without being asked. `fastlane/` at the repo root still holds store-listing metadata (descriptions, screenshots) in the Fastlane layout, now only of use to a future store attempt. It is *not* on the Play Store — a split free-phone-app / paid-watch-app listing was drafted (see `docs/play-console-*.md`) but the author shelved it, not a store enforcement action. A future Play Store attempt is more likely to be a single listing with in-app premium unlocks (Play Billing) than the old split-app model. Both APKs must still share the same `applicationId` and signing key (see "Package naming gotchas" below).

## Module layout

This is a multi-module Gradle (Groovy DSL) Android project, configured in `settings.gradle` / `build.gradle` / `libs.toml` (version catalog):

- `mobile/` — the phone app. Reads the currently playing media session, executes actions (play/pause/skip/volume/Tasker tasks/open other apps), and syncs config/state to the watch over the Wearable Data Layer API. Uses **Dagger 2** (`di/AppComponent.kt`, manual `dagger-android` injection) for DI.
- `wear/` — the watch app. Renders the on-watch UI (now-playing screen, action menu, volume bar), receives button/crown/gesture input, and talks to the phone. Uses **Hilt** for DI (different DI framework than `mobile/` — don't assume Dagger conventions carry over).
- `common/` — shared code linked into both `mobile` and `wear`: communication path constants (`CommPaths.kt`), action/button-config models, protobuf schemas (`src/main/proto/*.proto` — actions, music, watch, notifications, custom lists), shared views/drawables.
- `wearutils/` — a **git submodule** (https://github.com/gabrielluizone/WearUtils, this repo's fork of matejdro/WearUtils) with its own `libs.toml`. If this directory is empty, run `git submodule update --init` before building — Android Studio/Gradle sync will fail otherwise.

Root directories that are *not* part of the build: `icons/` (tracked; raw Material Symbols SVG downloads used as source material when adding drawables), `archived/` (parked scraps), `licenses/` (tracked; per-font license texts for the bundled typefaces), `wearmediatemplate/` (Google's Wear OS media-controls design guidance — screenshots plus `media-expressive.md` — kept as reference material for face styling), and the gitignored local reference folders `retromusic/`, `echo/` (a full local checkout of the Echo Music source — one of the three players `docs/player-integration-notes.md` documents from source, so read it there rather than guessing) and `redesign/`. Several stray build outputs / scratch files also sit at the repo root and are **not** build inputs (`full.apk`, `part.apk`, `mobile-debug.apk`, a bundled `com.google.android.wearable.media.sessions_*.apk`, `svartifoss_config.json`, `run.md`, `promp.txt`, `CHANGELOG.pdf`, `RELEASE_3.md` (a drafted GitHub release announcement, not shipping docs), assorted screenshot `*.png` scratch files, the gitignored `.playwright-mcp/` capture dir) — ignore them.

### Phone ⟷ watch communication

All communication goes through the Google Play Services **Wearable Data Layer API** (`MessageClient`/`DataClient`), with paths centralized in `common/.../CommPaths.kt`. Key entry points:
- Phone side: `WatchListenerService` (`WearableListenerService`) receives messages and forwards to `MusicService`; `WatchInfoProvider`/`ButtonConfigTransmitter`/`ActionListTransmitter` push config to the watch.
- Watch side: `PhoneConnection`, `WatchMusicService`, `PreferencesReceiver`, `IdleMessageListener` handle the corresponding receiving/sending logic.
- Communication is bidirectional. The watch reports *back* to the phone with `WatchInfoSender` (`watch/communication/WatchInfoSender.kt`), which sends the watch's own button hardware capabilities as a `WatchInfo` (from `watch.proto`) so the phone knows which physical buttons exist. (Note the phone-side `WatchInfoProvider` is a different thing — it *pushes* config to the watch.)
- Payloads for structured data (action lists, button configs, watch info) are serialized with **protobuf** using the schemas in `common/src/main/proto/`.
- Watch-facing settings are declared in `common/.../MiscPreferences.kt`, edited in the phone's settings UI, and synced phone → watch (received by `PreferencesReceiver`). Add new watch-behavior toggles there, not in watch-local prefs. Phone→watch delivery is owned process-wide by `mobile/.../WatchPreferenceSyncCoordinator.kt` (started in `WearMusicCenter.onCreate`): it listens for default-SharedPreferences changes, debounces/conflates them, pushes via `PreferencePusher` with exponential-backoff retry, and re-publishes once per process start to repair a stale watch — don't add per-screen push listeners (fragment-lifecycle listeners stranding edits is exactly the bug it replaced). It only syncs keys in `MiscPreferences.EXPORTABLE` (plus the `WEAR_DEV_*` diagnostics keys), so a new watch-facing preference must be added to `EXPORTABLE` to reach the watch at all. Delivery is **two transports for one payload**, not a choice between them: the `/Settings` DataItem stays the durable source of truth (survives watch reboot/process death, and owns key *removals* via its inventory logic), while the same snapshot also goes out over `MessageClient` (`CommPaths.MESSAGE_APPLY_PREFERENCES`, encoded by `common/.../WatchPreferenceMessage.kt`, received by `wear/.../PreferenceMessageReceiver.kt`) because DataItems are eventually-consistent and under doze don't land until the watch next wakes — that lag was the "setting only applies after I tap the watch" bug. The message carries a monotonic sequence so a delayed older snapshot can't clobber a newer one, and applies *additively* (never deletes), so a dropped message can't remove a preference. Two rules keep that pair honest, and both were learned from the same failure — a watch frozen on the last values it managed to receive, showing an old theme in an old language while the phone's settings screen looked entirely correct. **One snapshot feeds both transports, and both filter on `shouldSyncWatchPreference`.** `PreferencePusher` takes a `SharedPreferences` and reads `all` from it, so the DataItem used to carry the phone's *entire* default preference file — the saved streaming shortcuts, the search history and the track history all live there as JSON blobs, as does every phone-only setting — none of which the watch reads, all of it spending the same 100 KB per-item budget the watch-facing keys need. `SnapshotPreferences` (a read-only view inside the coordinator) hands the pusher exactly the filtered map the message already used. **And the message is sent unconditionally, before the DataItem put rather than inside its `try`.** It used to run after a successful put, so one rejected put took the whole channel down: the retry re-sends the identical payload, which means a snapshot the Data Layer refuses fails forever while the message that would still have worked was never reached. The snapshot grows with the number of *explicitly set* face-scoped keys and "Apply this look to all faces" writes every one of them onto all eighteen faces in a single tap, so that ceiling is reachable by ordinary use — `warnIfSnapshotIsOversized` logs once as it approaches, because nothing else about the symptom points anywhere near the cause.
- Structured notifications reach the watch via `notifications.proto`, `CommPaths.DATA_NOTIFICATION` (`/Notification`), decoded into `watch/model/Notification.kt`.
- **Media notification actions:** the phone mirrors the active media notification's action buttons to the watch as `MediaAction` entries inside `music.proto`'s `MusicState` (label + rasterized PNG icon + a locale-independent `semantic` hint). `PendingIntent`s can't cross the Data Layer, so `mobile/.../notifications/MediaNotificationActions.kt` is a process-local registry: it keeps the `PendingIntent` on the phone, sends an opaque id to the watch, and resolves the id back when the watch taps the action (the `semantic` field is presentation-only, never an execution token). `MediaActionIdentity.kt` classifies action semantics. The same listener also feeds `mobile/.../notifications/AppGlyphStore.kt`, a **persistent** package→PNG cache of each media app's notification small icon. It has to be persistent rather than read live out of `MediaNotificationActions`: that registry holds what is posted *now*, while the rows that want a glyph are launcher rows ("Play YouTube Music"), and the whole reason to tap one is that the app is not playing — so the notification is exactly what does not exist at that moment. Reading live would have shown the glyph only for apps the user did not need to launch. `AppPlayAction`/`PlayPlaylistShortcutAction`'s app-icon fallback prefer it over `getApplicationIcon`, and `MusicService`'s source icon falls back to it before the launcher icon (a cold start would otherwise show a full-colour icon on Split's seam for the first track and the glyph from the second on). A caller that takes the glyph **must** also report `iconTintable = true` — the bytes are a flat-white template on transparency, so untinted on a light surface it is an invisible white shape; that is why `PlayPlaylistShortcutAction` carries image and tintability together in one `AppMark` rather than deciding them in two independent getters. **Action icons are rasterized at transmit time**, so learning a glyph does not by itself update anything already on the watch — the store therefore keeps a persisted generation counter and `MusicService` re-sends the action list and both button configs (`ActionList.retransmit`/`ButtonConfig.retransmit`, which push without a disk write, since a notification arriving in the background has no business rewriting the user's config file). Both halves are needed: the live listener covers a glyph learned while the service is up, and `needsRetransmit` at startup covers the ordinary case where it was learned while the service was stopped — without it the bytes are already on disk next launch, `remember` takes its "nothing changed" branch, and the launcher icon stays on the watch permanently. These feed the watch's quick-actions panel; MediaSession custom actions are the fallback when no notification actions exist.
- **Service lifetime / the persistent notification:** `MusicService` is a foreground service, and `promoteToForeground()` must answer **every** `startForegroundService()` aimed at it (see its own comment) — so it runs at the top of `onStartCommand` before any branch, including the ones that immediately stop. Its notification carries "Stop" (`ACTION_STOP_SELF`) and "Force stop" (`ACTION_FORCE_STOP`); the latter unbinds the notification listener and then kills the process outright. Because that is deliberately *not* an orderly shutdown, two things cannot be left implicit: the notification is taken down explicitly (`removeServiceNotifications()`, also called from `onDestroy` for the ordinary path) rather than relying on service teardown, which may never run before the kill and left "Music control active" stranded in the shade; and the listener unbind calls `NotificationService.requestUnbindNow()` — which reaches the connected listener instance directly, since it is in this same process — falling back to the `ACTION_UNBIND_SERVICE` `startService` message only when none is connected, because the process may die before it can deliver anything to itself. If the unbind is missed the system rebinds the listener, revives the process, and `onListenerConnected` starts `MusicService` again, posting the notification right back. Note what `requestUnbindNow` deliberately does **not** use: `NotificationListenerService.requestUnbind(ComponentName)`, the static overload, exists only from **API 35** while the instance method has been there since 24 — it is present in `compileSdk 36`'s `android.jar`, so calling it compiles cleanly and then throws `NoSuchMethodError` at runtime on every older device. That trap is general here: `compileSdk` is 36 against `minSdk` 23, and with `lint` unusable as a gate (see *Build & test commands*) nothing catches a too-new API but the device itself — so check the actual `@since` of any framework method that isn't obviously ancient, rather than trusting that it resolved. Both actions also notify the **watch** (`CommPaths.MESSAGE_STOP_WATCH_APP` / `MESSAGE_FORCE_STOP_WATCH_APP`, handled by `IdleMessageListener` → `watch/communication/WatchAppShutdown.kt`), since the watch is a separate app on a separate device that nothing else would ever tell — it used to keep its ongoing-activity chip and `WatchMediaSession` proxy pointed at a service that no longer existed. Two constraints there. The send must **not** run on `lifecycleScope`: both callers `stopSelf()` immediately after, and that scope is cancelled at `onDestroy` milliseconds later, which cancelled the very send — hence the process-scoped `SHUTDOWN_SCOPE`. And Force stop waits for the send to complete before killing, with an unconditional `FORCE_STOP_KILL_MAX_DELAY_MS` backstop, because a fixed short delay regularly lost the Bluetooth hand-off while an unbounded wait would make Force stop do nothing when no watch is reachable. On the watch side `WatchAppShutdown` is a plain listener list, deliberately not a `LiveData`: a singleton `LiveData` replays its last value and would close the app again on next open, and `SingleLiveEvent` only trades that for holding the event until an observer is STARTED — i.e. closing the app in the user's face when they next bring it up. `removeServiceNotifications` deliberately spares `NOTIFICATION_ID_SERVICE_ERROR` — that one is not a status readout but the standing prompt to grant notification access, and this service stopping is the normal *consequence* of not having it, so clearing it would delete the only route back to the setting.
- **Logging / diagnostics:** the phone runs **Timber + Firebase Crashlytics** (`mobile/.../logging/TimberCrashlytics.kt`, `CrashlyticsExceptionWearHandler.kt`); the watch forwards its own logs on request via `MusicCenterLogRequestReceiver` (extends `WearLogRequestReceiver` from `wearutils`) over `CommPaths.MESSAGE_SEND_LOGS` (`/SendLogs`) + `CHANNEL_LOGS` (`/Channel/Logs`), so a watch-side crash surfaces in the phone's Crashlytics. Firebase Crashlytics and (since 2.2.1) Firebase Analytics are both active — keep the Data Safety / privacy docs consistent with that. Crash reporting is user-optional: `mobile/.../logging/CrashReporting.kt` centralizes the opt-out (Settings → Data & support → Privacy) — Crashlytics auto-upload stays disabled and finalized reports are sent manually only after the current privacy choice has been read; opting out also deletes queued unsent reports.
- **Developer announcements** also ride Firebase, but as push rather than diagnostics: `mobile/.../notifications/AnnouncementNotifications.kt` mirrors `CrashReporting`'s single-gate shape, subscribing/unsubscribing the device to one fixed FCM topic (`"announcements"`) as `MiscPreferences.ANNOUNCEMENTS_ENABLED` (Settings → Data & support → Privacy, on by default) changes — there is no backend, so a Firebase Console campaign targeting that topic is the entire delivery mechanism, and the app never holds a token/user list itself. `AnnouncementMessagingService` (manifest-registered `FirebaseMessagingService`) renders the received message as a notification.

### Watch-side data flow

`PhoneConnection` (Hilt `@Singleton`) listens to `DataClient` updates and exposes `LiveData` properties (`musicState`, `rawPlaybackConfig`, `rawStoppedConfig`, `customList`, etc.). The two separate configs — playing vs. stopped — let users assign different button actions depending on whether music is currently playing.

`MusicViewModel` (`@HiltViewModel`) consumes `PhoneConnection` LiveData and drives `MainActivity`. It owns `WatchActionConfigProvider` (one for each config) which decodes protobuf action configs from the phone into `ButtonAction` objects keyed by `ButtonInfo`.

`WatchMusicService` is a foreground `LifecycleService` that keeps `PhoneConnection` active. Why it is staying alive is decided by the pure `resolveServiceHold(uiOpen, musicPlaying, hasTrack)` (top of the same file, tested by `ServiceHoldTest`), which has **three** states, not two: `ACTIVE` (UI open or music playing), `PAUSED_TRACK`, and `IDLE`. The middle one exists because the app is only reachable from the watch face while this service is up — it carries the ongoing-activity chip and the proxy `WatchMediaSession` — so tearing it down on the short idle timer meant an ordinary pause evicted the app and getting back to a paused track cost a trip through the launcher. How long a paused track holds is a user choice decoded by `common/.../PausedHoldPolicy.kt` (`MiscPreferences.WEAR_PAUSED_HOLD`, default 30 minutes; `"always"`/negative → `FOREVER`, `0` → no hold, anything unparseable → the default rather than `NO_HOLD`, so a corrupt value can't silently restore the bug). Every full-screen watch activity (now-playing, queue, menu) binds a `UiOpenServiceConnection` to hold the service while it's in the foreground — the Compose windows are opaque, so `MainActivity` underneath them gets stopped and can't be the one keeping the service alive.

`WatchMediaSession` (`watch/communication/WatchMediaSession.kt`) is a `MediaSessionCompat` proxy: it mirrors phone playback state (metadata, playback state, album art, volume) received from `PhoneConnection`, and forwards transport controls (play/pause toggle, skip, seek, volume) back to the phone over the Data Layer. It is owned and lifecycle-managed by `WatchMusicService`. This is the architectural keystone that enables Wear OS system media surfaces, Tiles, and Complications to see and control the phone's music.

**On-watch face picker** (`wear/.../view/facepicker/`): long-pressing the centre of the player opens `FacePickerActivity`, so a face can be changed from the wrist. Three things about it are deliberate. It is **its own Activity**, not an overlay in `MainActivity` — that is what makes the right-swipe close the *picker* back to the player (via `SwipeToDismissBox`, as the queue and menu do) instead of exiting the app. It is a **vertical** list rather than a horizontal gallery like the system's watch-face picker, because a left-to-right drag *is* the Wear OS dismiss gesture and a horizontal pager would have to fight it for every swipe. And the choice is **written locally *and* sent to the phone** (`CommPaths.MESSAGE_SET_SCREEN_FACE` → `MusicService.applyScreenFaceFromWatch`): the local write is what applies it instantly, but preferences are phone-owned and `WatchPreferenceSyncCoordinator` re-publishes the whole snapshot once per process start, so a watch-only write would be silently reverted. The local write must also `PreferencesBus.postValue(prefs)` — `MainActivity` re-reads its appearance only when that bus emits and does *not* reload in `onStart`, so without it the player keeps rendering the old face. The picker lists the user's **saved custom themes** alongside the built-in faces, so the payload has two forms: a bare face key, or `custom:<themeId>`. `WatchThemeRepository` publishes the library to the watch as a JSON id/name/baseFace array in `MiscPreferences.WEAR_AVAILABLE_CUSTOM_THEMES` (a synced pref, not a DataItem — the profile *contents* stay phone-local), which `WatchFaceCatalog.optionsFor(currentFace, customThemesJson)` merges with `ALLOWED_BASE_FACES` minus `ArchivedFaces.KEYS`; so a repository change that doesn't rewrite that key leaves the wrist picker showing a stale list. `applyScreenFaceFromWatch` routes the two forms differently, and must: a `custom:` id goes through `WatchThemeRepository.applyProfile`, which materializes the whole snapshot, while a bare face key is written directly and **clears** any active custom theme, for the reason `ConfigBackup.import` does the same — a custom theme owns its own base layout, so a bare `wear_screen_face` write landing underneath one rewrites a saved profile rather than switching away from it. The local-write half therefore cannot apply a theme at all: `normalizeBaseFace` rejects a `custom:`-prefixed value, so writing the payload straight into `wear_screen_face` resolved to `classic` and picking your own theme visibly switched the watch to the wrong face. `FacePickerActivity.applyFace` writes the option's **base face** locally instead (the one part of a theme the watch can honestly render alone) and lets the phone deliver the snapshot; picking a *built-in* face additionally clears `WEAR_ACTIVE_CUSTOM_THEME_ID`/`_COMPLETE` locally, mirroring `applyScreenFaceFromWatch`, because otherwise `resolve()` keeps returning the active `Custom` context and the pick appears to do nothing. `WEAR_AVAILABLE_CUSTOM_THEMES` is also republished once per process start from `WearMusicCenter` (`WatchThemeRepository.publishAvailableThemes`): only `saveState` wrote it, so a library built before the key existed never reached the watch at all — the same class of staleness the preference snapshot re-publish exists for. Ordering is by recency first, then registry order: `watch/.../view/facepicker/FaceRecency.kt` (pure over a plain map, JVM-tested) records last-used timestamps **watch-locally** — never in `MiscPreferences.EXPORTABLE`, both because which faces this wrist uses is not a property of the theme and because the preference sync only deletes keys a previous phone snapshot declared phone-owned, so a key the phone has never heard of survives every sync; adding them would put a Bluetooth write on every face change for no benefit. Saved custom themes sort ahead of built-ins. Rows carry the shared palette glyph, deliberately: a per-face Canvas miniature was tried and removed — at row size the sketches read as approximations of faces rather than as the faces, which is worse than an honest generic icon. Which gesture does what is `common/.../CenterLongPressAction.kt` (faces/queue/none, pinned by `CenterLongPressActionTest`); anything unset resolves to **faces**. It deliberately does *not* consult the legacy `WEAR_CENTER_LONG_PRESS_QUEUE` boolean — it briefly did, on the reasoning that an install which opted into long-press-for-queue should keep it, but that boolean is off by default so for almost everyone it only kept the gesture inert, and for the few who had set it the result was the queue opening where they were reaching for the picker. The queue has other routes; an on-watch face change had none. `WearMusicCenter.repairCenterLongPressPreference` is the one-shot that undoes the short-lived migration which had written `"queue"` through, narrowed to exactly that state so a later deliberate choice is never reverted.

### Playback position on the watch

The watch is told the position only when something *else* changes — `MusicService` deliberately suppresses position-only retransmissions (`equalsIgnoringTime`), which is right (constant Bluetooth traffic to say nothing) but means that for most of a track the watch is not reading a position, it is **predicting** one. The progress ring, the track time and the synced-lyrics screen all ride on that prediction, and the lyrics screen is what turns a one-second error from invisible into obvious.

**Never subtract one device's clock from the other's.** This is the rule the whole subsystem exists to enforce. The original design sent the sample time as a phone epoch timestamp and had the watch subtract it from its own `System.currentTimeMillis()` — correct only if the two wall clocks agree, and Wear OS syncs a watch's clock from its phone with tolerance, not exactly. Whatever they differed by became a fixed offset on every predicted position for a whole track, which produced two symptoms that look unrelated: lyrics consistently ahead of or behind the song, and a visible step on every pause/resume (a paused state predicts nothing, so only the playing one carried the skew). The fix is `MusicState.positionAgeMs` (and the same field on `PlaybackSync`) — a **duration**, how stale the sample already was when the phone built the payload, measured entirely with the phone's own clock; the watch adds however long it has held the payload, measured entirely with its own `elapsedRealtime`. `positionUpdateTime` is still sent for old watch builds, and `-1` on `positionAgeMs` makes a new watch fall back to the old subtraction for old phone builds. `common/.../PlaybackPositionEstimate.kt` owns the arithmetic (JVM-tested; never returns negative — the legacy path could, which ran the lyric backwards past the start of the track).

Four pieces sit on top of that:

- **One anchor, not three** — `wear/.../communication/PlaybackClock.kt`. The position used to be derived independently in the player ViewModel, the lyrics ViewModel and the media-session proxy, each re-extrapolating from `PhoneConnection.musicStateArrivalRealtimeMs` and none of them ever corrected. That is why the lyrics screen appeared to sync when opened and never again — the open *was* the resync, because a fresh observer replayed the last state and re-anchored on it. `PlaybackClock` holds the single anchor, updated from a `MusicState`, from a local event (seek, optimistic play/pause, predicted advance — position known *now*, zero staleness), or from a sync reply. Deliberately not thread-safe: everything touching it is on the main thread, and synchronizing would only hide a caller that wandered off.
- **Correction over a round trip** — `CommPaths.MESSAGE_REQUEST_PLAYBACK_SYNC` / `MESSAGE_PLAYBACK_SYNC` (`PlaybackSync` in `music.proto`). `positionAgeMs` measures staleness at the *sender*, so the one leg it cannot describe is the flight between devices. The watch stamps a request with its own monotonic clock, the phone echoes that token back untouched (so no clock is ever compared across devices), and the watch halves the measured round trip. `common/.../PlaybackSyncPolicy.kt` (pure, JVM-tested) holds the three rules: throw the sample away when the round trip is too long for the symmetry assumption; below `IGNORE_THRESHOLD_MS` do nothing, between there and `STEP_THRESHOLD_MS` apply a fraction so successive checks converge invisibly, past it snap (a visibly wrong line should not be eased into place); and back off the interval each time a check finds nothing, dropping to the floor the moment one does.
- **Two transports for the state itself** — `CommPaths.MESSAGE_MUSIC_STATE` sends the same `MusicState` as `DATA_MUSIC_STATE` over `MessageClient`, the shape `MESSAGE_APPLY_PREFERENCES` already uses beside `/Settings`. The DataItem stays the durable source of truth and carries the album-art/source-icon **assets**; the message carries none (a message cannot hold them) and exists because the replication layer's latency was not merely cosmetic — it put a lasting offset on the predicted position. Whichever arrives first is applied and the other is discarded by content.
- **Predicting the track boundary** — `wear/.../view/PredictedTrackAdvance.kt` (pure, JVM-tested). When the watch already holds the queue and the current track has run its full duration, the next entry is knowable before the phone says so, which removes the worst-felt latency in the app (players routinely drop out of the playing state at a boundary, so `onMetadataChanged` is late, and the cover then travels as the slowest Data Layer asset). It is **a prediction, never a second source of truth** — a real state is applied verbatim the moment it arrives, agreeing or not (`MusicViewModel.resolvePrediction`) — so every rule in it refuses to predict rather than guessing (shuffle, repeat-one, an implausible duration): a refused prediction costs only today's latency, a wrong one shows a track that is not playing.

### Watch input handling

`MainActivity` handles six input categories:

1. **Screen gestures** — `FourWayTouchLayout` (from `common/`) divides the screen into quadrants; taps in each quadrant are reported as a `ScreenQuadrant` gesture mapped through button config.
2. **Full-screen swipes** — up/down/left swipes on the now-playing screen are pseudo-buttons (`SwipeGesture` in `common/`, buttonCodes chosen outside the quadrant range) flowing through the same `ButtonInfo`/config pipeline as quadrant taps. Right swipe is deliberately never intercepted — it's the system-wide Wear OS dismiss gesture.
3. **Physical stem buttons** — `StemButtonsManager` (`wear/.../view/StemButtonsManager.kt`) translates raw `KeyEvent` sequences into single-tap, double-tap, or long-press gestures per configured button. Includes an ambient-mode phantom-click workaround.
4. **Rotary encoder / digital crown** — handled via `RotaryEncoderHelper` directly in `MainActivity`. On devices with discrete rotary input, crown turns are simulated as button presses (`SpecialButtonCodes.TURN_ROTARY_CW/CCW`) through `StemButtonsManager`, so they're user-configurable like any button. Otherwise, continuous scroll deltas do whatever `common/.../RotaryAction.kt` resolves — volume / seek / **off** (`MiscPreferences.WEAR_ROTARY_ACTION`, falling back to the legacy `ROTARY_SEEK` boolean when the three-way key was never written) — subject to a configurable deadzone and sensitivity. `OFF` exists and is *swallowed* rather than passed on because rotary input is not only the crown: every non-Classic Galaxy Watch reports a finger circling the **touch bezel** as rotary scroll, which is physically the same gesture as an edge-seek drag on the progress ring. For the same reason `MainActivity` drops rotary events outright while `binding.seekBar.isSeekDragging` — otherwise an edge-seek drag popped the volume overlay open and the seek never happened.
5. **On-screen mini buttons** — up to three *visible* configurable buttons (`ScreenButtons` in `common/`, codes 7–9, tap + long-press) rendered as a fixed overlay near the bottom of the now-playing screen (except on a face that hosts them inside its own composition — see `MiniButtonPlacement.isHostedByFace` and Chat below); ordered after `center_tap_zone` in the layout so they win touch dispatch over the center play/pause zone and `FourWayTouchLayout`. Row offset is tunable via `MiscPreferences.WEAR_SCREEN_BUTTONS_OFFSET` (phone developer settings). Where and how the row sits is `common/.../MiniButtonPlacement.kt`, decoded from `screen_buttons_curve_style`: what began as a pure bezel-curve amount (flat → curved/curved_extreme) gained a second, orthogonal axis whose values relocate the row entirely — `spread` (bottom row, pushed to the screen edges) or a rail down `side_left`/`side_right`/`side_split` (split rail: first configured button left, the rest right) — rather than only bending it, because to a user "how are the mini buttons arranged" is one question, not two pickers. Consumed identically by wear `MainActivity` and `WatchPreviewView`, the usual shared-resolver pattern so the preview can't show a bottom row while the wrist shows a side rail. Their *colour* is the sibling resolver `common/.../MiniButtonSurfaces.kt` — `resolve(style, palette)` is the pure, JVM-tested decision table for `screen_buttons_bg_style` and `paletteFor` derives the expressive/glow tones every caller must agree on. It has three consumers now (the View row's `styleScreenButton`, the Chat face's Compose circles, `WatchPreviewView`), and the two that predated it had already drifted: the preview stroked `glow_exp` with the un-lifted tone and chose its icon colour on a naive luminance split where the watch used the WCAG crossover. `FOLLOW_FACE` (`"glass"`, the default) is the one value that resolves to *no* colour — `followsFaceNeutral`, meaning the drawing surface supplies its own neutral skin, which is what lets Chat keep its accent circle until a style is picked.
6. **Quick actions panel** — an overlay opened by double-tapping the center of the now-playing screen (rendered in `MainActivity`): three round configurable slots plus a full-width row (`QuickPanelButtons` in `common/`, codes 10–13, continuing the pseudo-button range). Unconfigured slots now default to mirroring the current media notification's *real* actions (labels + icons, executed on the phone via `MediaNotificationActions` — see the communication section), with MediaSession custom actions as fallback and the older Like / Shuffle / Repeat + "Up Next" queue-preview row behind that; a `NullAction` assignment hides a slot. The phone writes quick-panel assignments into *both* the playing and stopped configs so the panel behaves the same regardless of playback state.

Resolved actions don't always round-trip to the phone: `MusicViewModel.executeActionOnWatch` intercepts actions that make sense locally (opening the menu/queue, opening search input, volume UI) and only sends the rest to the phone for execution.

### Phone app UI

The phone UI is a single activity (`mobile/.../view/mainactivity/MainActivity.kt`) that swaps fragments via a bottom navigation bar: `WatchFaceFragment` (Watch face — see below), `ControlsFragment` (a ViewPager2 with swipeable "Music playing" / "No playback" tabs, each page a `ButtonConfigFragment` — the two configs are presented as states of one feature, not separate nav destinations), `ActionListFragment`, and `SettingsHomeFragment` (a ViewPager2 of `MiscSettingsFragment` sections: General, Behavior/watch, Automation, Apps, Data & support — `MiscSettingsFragment.SECTION_*` args select a page, and which preference categories from `settings.xml` that page shows is looked up in `view/settings/SettingsCatalog.kt` (see below); service-specific integrations live under Apps — playlist shortcuts (`PlaylistShortcutsActivity`) match a link's source service via `music/StreamingShortcutLinks.kt`'s pure link-detection helper (YouTube Music, Spotify, Deezer, Tidal, Apple Music, Amazon Music, SoundCloud, or a generic fallback), shared with `MusicService`'s launch-intent resolution — these are link shortcuts, not account/API integrations, so the target streaming app still decides whether playback actually starts — see *Actions system* below for how shortcut launches and the autoplay nudge actually work). The usage guide (`TutorialFragment`) is not a tab: it opens in `HelpActivity` from the toolbar's help button. A left navigation drawer holds only app/about info (version, author), not navigation. The activity also owns cross-fragment chrome: the toolbar (plus the `toolbar_main` options menu), a mini player (driven by a `MediaController` bound to the active media session, with queue and detail dialogs), and a shared FAB whose click is dispatched to the current fragment via the `FabFragment` interface. Missing notification access — without which the app cannot see what is playing at all — interrupts with a dialog **once** (`showNotificationServiceWarning`, gated by the persisted `NOTIFICATION_ACCESS_PROMPTED_PREF`), then persists as a tappable banner row under the toolbar that opens the same dialog (`refreshNotificationAccessBanner`, driven from `onResume` so it clears itself the moment the grant is made). The dialog is dismissible while the condition stays true, so re-showing it every resume — the previous behavior — taxed precisely the user who had read it and chosen to grant it later.

The **Watch tab** (`mobile/.../view/watchface/`) is the visual customization surface for the watch's now-playing screen: `WatchPreviewView` (a Canvas miniature of the watch honoring the same preference keys the watch reads — face, screen theme, album art style/dim, accent color modes, mini-button appearance/offset — with a miniature per face) docked above a nested `WatchFacePrefsFragment` (`res/xml/watch_face_settings.xml`). The preview is **contextual**: `WatchPreviewView` has a `PreviewSurface` enum (player, AOD, volume, seek, quick panel, queue, mini buttons) and `surfaceForPreference()` maps the preference key being edited to the watch surface it affects, so touching e.g. `wear_volume_style` temporarily previews the volume overlay instead of the player. The miniature shows the phone's *actual* current track when one is playing — `WatchFaceFragment` observes `MainActivity.activeMediaSession()` and feeds art/title/artist into `WatchPreviewView.setNowPlaying()` (Palette-extracts the accent from the real art), a 500ms ticker drives `setPlayback()` so the progress ring/track-time/play-pause state animate live, and `MiniButtonIconLoader` reads the *playing* button-config file off disk (`action_config_playing`, mirroring `DiskButtonConfigStorage`'s format) so the preview's bottom row shows only the mini buttons the user actually configured, with their real icons — all falling back to a built-in sample otherwise. `WatchPreviewView` sizes text to the wear faces' sp values against a 192dp reference watch; keep those (and the cookie/ring geometry) in sync when changing the wear faces. Those appearance preferences were *moved* out of `settings.xml` — the Settings tab keeps behavior-only options — so a watch-appearance preference belongs in `watch_face_settings.xml`, and any new key must also be reflected in `WatchPreviewView.refresh()`/drawing if it changes the screen's look. Shared Lyra preference chrome (HSV color picker dialog, runtime-accent dialog tinting) lives in `view/settings/LyraPreferenceUi.kt`, used by both preference screens. `ResettableNumericEditTextPreference`'s "Reset to default" **applies and dismisses** rather than filling the field in: it must go through `callChangeListener` (plain `setText` persists in silence, so the contextual preview and the dependency wiring are never told), and it cannot reach the field through `getView()` — that is always null on a `PreferenceDialogFragmentCompat`, whose content view belongs to the AlertDialog. Getting either wrong is what made Reset write the default away invisibly and then have OK overwrite it with the stale box contents. A per-face preference that only one layout reads gets an `isVisible` line in `updatePlayerCapabilityVisibility` (`wear_expressive_seek_mode`, `wear_carousel_card_shape`) — a picker offered beside a face that ignores it reads as broken, not as inapplicable. Album-accent → surface-color math (tonal containers, the legacy blur-radius downscale) lives in `common/.../PaletteTransforms.kt` so `WatchPreviewView` and the wear faces/overlays consume the identical functions instead of copies that can drift (same rationale for `common/.../BitmapBlur.kt`, the shared artwork blur — repeated bilinear down/up sampling rather than `RenderEffect`, which is API 31+ and needs a `RenderNode`, so it works on every supported watch and in the phone preview alike); `WatchPreviewView` still duplicates the parts that can't be shared that way — cookie/ring geometry — since `mobile` cannot depend on `wear`, so keep those in sync by hand when changing the wear faces.

**Settings search** (`view/settings/SettingsSearchActivity.kt`, opened from a toolbar action visible only on the Settings/Watch tabs) makes the ~190 preferences across both tabs findable by name instead of by remembering which of the twelve pages holds one. `SettingsCatalog.kt` is the piece that makes this possible without a second source of truth: it holds the section↔category maps for *both* `settings.xml` and `watch_face_settings.xml` (`SETTINGS_SECTIONS`/`SETTINGS_CATEGORIES`, `WATCH_SECTIONS`/`WATCH_CATEGORIES`), read by three consumers — `MiscSettingsFragment`/`WatchFacePrefsFragment` (to hide the categories the current page doesn't want) and `SettingsSearchIndex` (to know which page a result lives on). `SettingsSearchIndex.build()` derives the searchable rows by parsing the preference XML directly rather than from a hand-maintained list, so a new preference is searchable with no second registration to forget, and titles/summaries come out already localized. Matching (`SettingsSearchIndex.rank`, pinned by `SettingsSearchRankingTest`) is a pure function scored by where a term hits (title > category > summary) after accent/case normalization. Picking a result flows back through `MainActivity`: `SettingsSearchActivity` returns (tab, section, preference key) as an activity result, `MainActivity.openSearchResult` stashes it as `pendingSearchTarget` and drives the bottom nav to the right tab, and the bottom-nav listener's `consumeSearchTarget` hands it to `SettingsHomeFragment.newInstance`/`WatchFaceFragment.newInstance` (section) which forward the key one level down to `MiscSettingsFragment`/`WatchFacePrefsFragment`, which scroll the list to it once laid out. The stash-and-consume indirection exists because switching to a tab that's already selected fires no bottom-nav callback, so the direct fragment-swap path and the tab-switch path both have to end up going through the same consumer.

Watch-tab **appearance preferences are scoped per face**: `common/.../FaceScopedPreferences.kt` stores each appearance key in its `SCOPED_KEYS` set as `"<baseKey>@<face>"` and resolves reads as explicit per-face value → per-face default → legacy global value → definition default (one carve-out: a *non-default* legacy `wear_album_art_style` value beats the per-face default, because `default_config.json` seeds `cover` on every install so key presence alone isn't user intent). The per-face defaults give album-accent faces "tonal" quick-panel/queue/volume and "expressive" seek surfaces, give each face its matching background via `PlayerBackgroundStyle.defaultForFace()` (`common/.../PlayerBackgroundStyle.kt` — the artwork/background treatment enum, selectable independently of the structural face and rendered on the watch by `watch/view/PlayerBackgroundDrawable.kt`), and deliberately *beat* a pre-scoping global value (that value was never chosen for the face). The Watch-tab preference screens write through `mobile/.../view/settings/FaceScopedPreferenceDataStore.kt` (scoping by the resolved `AppearanceContext`, so edits land in `custom_active` while a theme is active and in `key@<face>` otherwise; its `getBoolean` must consult `perFaceDefault` in *both* branches, the same trap `FaceScopedPreferences.getBoolean` has fallen into twice), the flat SharedPreferences phone→watch sync carries the scoped entries unchanged, and the watch resolves through the same common object — so the settings UI, the preview, and the watch can't disagree. A new watch-appearance preference that should be per-face must be added to `SCOPED_KEYS`; behavior prefs and the face selector itself stay global, and `wear_quick_panel_source` is deliberately unscoped (it drives a phone-side binding with no per-face notion). The `Boolean` read overload must walk the *same* four-step order as the `String` one — it used to skip `perFaceDefault` entirely, which went unnoticed only because no boolean had a per-face default yet, and then silently ignored Carousel's "edge ring and edge seek off".

Scoping arrived in 3.0, so an in-place upgrade from 2.x carries one pre-scoping global value that keeps bleeding into whichever per-face defaults it happens to match — `mobile/.../view/watchface/FaceResetMigrationPrompt.kt` (called once from phone `MainActivity.onCreate`) recommends "Reset all faces to default" exactly once per device. It cannot detect the upgrade from its own preference key (new in the same build that reads it, so a fresh install and an upgrade look identical on the run that matters); it compares `PackageInfo.firstInstallTime` vs `lastUpdateTime` instead. Its reset path is `WatchFacePrefsFragment.resetAllFaces(context, prefs)` — shared with the Watch tab's button, so keep them one function.

**Custom watch themes** layer on top of face scoping: `common/.../ThemeAppearance.kt` decides which appearance context is active — `AppearanceContext.BuiltIn` (the per-face resolution above) or `AppearanceContext.Custom`. The phone keeps a library of up to 24 named profiles in `mobile/.../view/watchface/theme/WatchThemeRepository.kt` (managed in `WatchThemesActivity`, opened from the Watch tab), stored as JSON in a *separate* named SharedPreferences file — deliberately, since the default prefs file is mirrored wholesale to the watch. Applying a profile materializes exactly one complete snapshot into the fixed `custom_active` scope (`"<key>@custom_active"`) plus metadata prefs (`wear_active_custom_theme_id` / `_schema` / `_complete` / `_revision`) in a single default-prefs transaction. Both the watch and the preview resolve through `ThemeAppearance.resolve()`; a Custom context reads *only* the snapshot (never legacy globals or `key@<face>` values) and falls back to the built-in base face whenever the snapshot is incomplete or its schema mismatches — so a partially synced theme can never activate. The snapshot's key set derives from `FaceScopedPreferences.SCOPED_DEFINITIONS` (= `EXPORTABLE` ∩ `SCOPED_KEYS`), so a new scoped appearance preference must be in both registries or profile capture/import will silently drop it.

The redesigned phone theme is internally named **Lyra** (resource names like `dialog_bg_lyra`, `lyra_*` selectors). The accent color can be static, user-picked, or dynamically extracted from album art; `view/LyraAccent.kt` is the single source of truth for resolving the currently displayed accent outside `MainActivity` (standalone dialog activities use it to match what's on screen).

### Actions system (mobile)

Button presses/gestures map to `PhoneAction` subtypes (`mobile/.../actions/`), each with a corresponding `ActionHandler<T>` implementation (playback, volume, app-launch, Tasker, open menu/playlist, etc.). New actions typically need: an action class, a handler, a binding in `di/ActionHandlersModule.kt`, and an entry in the relevant action list (`RootActionList`, `PlaybackActionList`, `VolumeActionList`).

The saved streaming-shortcuts library doubles as an action-picker category (`StreamingShortcutActionList`): each saved link becomes an assignable `PlayPlaylistShortcutAction`. **Streaming-shortcut launches are watch-initiated:** modern Android blocks a background phone service from starting activities, so an action can carry an optional `remoteUri` (`actions.proto`, present on both button-config and action-menu entries; format `targetPackage|uri` or a bare URI, produced by `PlayPlaylistShortcutAction.remoteUri`). When the watch resolves such an action it registers the URI with `wear/.../communication/PhoneUriOpener.kt` and round-trips the action so `MusicService.playDeepLink` runs on the phone; the phone answers over `CommPaths.MESSAGE_DEEP_LINK_VERDICT` (`/IdleMessages/DeepLinkVerdict`, empty payload = played, otherwise the `targetPackage|uri` to open) and **only that verdict opens anything**. It used to fire the open *in parallel* with sending the action, which defeated the entire ladder below: the target app was brought to the foreground while the silent routes were still being tried, so a pocketed phone lit up and switched apps even when the MediaBrowser route went on to work — and with SoundCloud, where nothing plays, opening the app was the whole visible outcome. `PhoneUriOpener` is process-scoped because every caller (the menu, a button, the Tile trampoline via `ShortcutLaunchActivity`) closes itself in the same gesture, and it is now the single implementation of the open — `MainActivity` and `ShortcutLaunchActivity` each carried a copy of the scheme-validation plus `RemoteActivityHelper.startRemoteActivity` dance. A verdict arriving with nothing outstanding is ignored, since `playDeepLink` also runs for shortcuts started from the phone's own UI. Its `VERDICT_BACKSTOP_MS` (30 s) is a safety net for a lost message or a phone that died mid-ladder, deliberately far beyond the ladder's ~16 s worst case so it can never race a merely slow verdict; a verdict is sent at **every** terminal path, success included, precisely so that timer is not the normal mechanism.

`playDeepLink` (mobile) is the actual playback engine and tries progressively stronger contracts because merely *opening* a link only navigates, it doesn't play: (1) if the target app already has any active session (found across **all** active sessions via `ActiveMediaSessionProvider.controllerForPackage`, not just the tracked "current" one), issue `playFromUri` — and then **verify it**, sampling `playbackIdentity` before and re-checking after `DEEP_LINK_VERIFY_MS`, because "accepted" is not "playing": SoundCloud takes a track URI happily and silently ignores a collection one, so trusting the advertised `ACTION_PLAY_FROM_URI` bit reported success and skipped every remaining step. The one case that counts as swallowed is the app carrying on with exactly what it had; "same item but now playing" is a legitimate resume. This is the same issue-and-verify rule the queue tap follows, and for the same reason — see `MediaSessionCapabilities`; (2) otherwise ask the app's `MediaBrowserService` to play through `mobile/.../music/MediaBrowserPlayback.kt` (URI first, then the shortcut's saved name as a `playFromSearch` — search is a *fallback* here, not only the artist path, because the visible open it used to defer to is not free: it foregrounds the app, and for a collection it doesn't even start playback) — the Android Auto/Assistant path, the only one that works with the screen off / app not running, since binding the browser wakes the app with no Activity launch (this is why the YT Music Liked-Music shortcut plays even after a force-stop; Spotify usually rejects unknown browser clients, so it falls through); (3) finally the visible deep-link open + a media-session nudge (`MediaBrowserPlayback` retries the play command while the freshly-woken session warms up). **Artists** are special: a `playFromUri` on an artist page only navigates, so `StreamingShortcutLinks.isPlayable` treats `ARTIST` as playable and the shortcut's saved *name* is passed as a `playFromSearch` query (the one command both YT Music and Spotify honor from outside) — for precise entities (track/album/playlist) the URI stays authoritative and search is never substituted. `forPlayback` also canonicalises YouTube share links (`youtu.be`, plain `youtube.com`, `/playlist`) into the `music.youtube.com/watch` form that actually starts playback. Dedicated one-tap actions exist for the account "Liked Songs" of YouTube Music (`PlayLikedSongsAction`, `watch?list=LM`) and Spotify (`PlaySpotifyLikedSongsAction`, `spotify:collection:tracks`). When there is *no* current session at all (the watch's "Nothing playing" idle screen), a play/pause command resumes the last app via `AudioManager.dispatchMediaKeyEvent(KEYCODE_MEDIA_PLAY)`.

**Optional online shortcut thumbnails** (`mobile/.../music/ShortcutArtworkFetcher.kt` + `ShortcutArtworkStore.kt`): strictly opt-in (`streaming_shortcut_artwork` pref, off by default — one of five network paths, with the update check, the queue-cover fetch under *Playback queue* below, and the two under *Lyrics and track metadata*), it fetches each saved shortcut's cover once from the service's public **oEmbed** endpoint (Spotify/YouTube/SoundCloud/Deezer), caches the PNG on disk keyed by link, and surfaces it in the phone list, as the assigned action's icon (`PlayPlaylistShortcutAction.defaultIcon`), and on the watch menu — the latter by attaching the PNG as a per-index DataItem asset in `PlaylistShortcutStorage.createDataRequest` (the watch's `decodeCustomList` already reads `assets[index]`, so no watch change was needed). Editing a saved shortcut propagates to every already-assigned copy via `PlaylistShortcutActionSync` (button configs + action list, matched by old link, re-committed through the normal path); the Actions screen re-reads its config in `onResume` (`ActionListViewModel.refreshFromConfig`) so a rename shows up there too.

### Playback queue (mobile)

`OpenPlaylistAction` builds the watch's queue list. Several failure modes that look identical to a user ("no queue" / "no covers" / "tapping a row does nothing") have entirely different causes, so each has dedicated machinery:

- **Encoding**: queue thumbnails are JPEG (`OpenPlaylistAction.encodeThumbnail`), deliberately *not* `BitmapUtils.serialize`, which is lossless PNG. Cover art is photographic with no alpha, so PNG is several times larger — the reasoning `MusicService.transmitToWear` already records for the single now-playing cover, but multiplied by up to 20 assets in one DataItem. The watch decodes with `BitmapUtils.deserialize` (`BitmapFactory.decodeByteArray`), which is format-agnostic, so only the sender needed changing.
- **Which controller is reported** is decided by the pure `resolveReportedSession()` (tested by `ReportedSessionTest`): the playing session, else the last reported one *while it is still live*. `ActiveMediaSessionProvider.currentController` is null whenever nothing plays, so a pause fallback must read `lastReportedController` instead — reading `currentController` meant the first pass after a pause looked right and every later pass reported null, dropping the watch to the idle screen mid-pause.
- **Acquisition** goes through `MusicService.resolvePlaybackQueue()`, not `currentMediaController.queue` directly. Some players run several `MediaSession`s at once — Retro Music ships a `WearBrowserService` session beside its playback one — and only one carries the queue, while the tracked controller is chosen by which session is *playing*. `ActiveMediaSessionProvider.siblingQueueForPackage` covers that gap before the code falls back to `recentTrackHistory` (`CustomLists.HISTORY`). A player that publishes no queue at all (pre-6.x Retro Music never called `setQueue`) genuinely cannot be helped — history is the honest answer.
- **Selection** (what a tap on a row does) has three independent ways to silently do nothing, and each is guarded separately. First, **which session the command goes to**: `resolveQueueSource()` returns the queue paired with the controller that published it (`MusicService.QueueSource`, via `ActiveMediaSessionProvider.siblingQueueSourceForPackage`), and `onCustomMenuItemPresed` sends `skipToQueueItem` to *that* controller, not to the tracked/playing one. A `queueId` indexes one specific session's queue, so in the multi-session case the acquisition bullet above describes, aiming it at the playing session addresses a queue that session has never heard of — accepted, and nothing happens. Second, **whether the command works at all**: entry ids are encoded rather than bare, `common/.../CustomLists.kt`'s `QueueEntry` writing `"<queueId>|<mediaId>"` — split once on the first `|`, the same shape and reasoning as `LibraryEntry`, since a media id may itself contain `|`. `skipToQueueItem` is then issued **unconditionally** and the result *verified*, rather than predicted from `ACTION_SKIP_TO_QUEUE_ITEM`: gating on that bit is how this regressed in the first place, since plenty of players implement the command without advertising it, and the gate diverted a working call into a fallback that did nothing. An unsupported transport command is a harmless no-op, so always trying costs nothing while guessing wrong costs the whole feature — which is why `MediaSessionCapabilities` deliberately has no `advertisesSkipToQueueItem`. `onQueueEntrySelected` samples `playbackIdentity` (active queue id + metadata media id + title) *before* issuing, waits `QUEUE_SKIP_VERIFY_MS`, and only if nothing moved plays the row's own media id through `MediaBrowserPlayback.playMediaId` — the route library/search selections already use. Retro Music is the known case for that fallback: neither of its sessions implements the command, which is again *not* the same as publishing no queue — its browser session hands out real, playable items, it just never answers that one command. The media id is round-tripped from the app's own queue, never constructed, which keeps it inside the rule `docs/player-integration-notes.md` sets out. Tapping the row that is already playing is excluded from the verify, since "nothing changed" is the correct outcome there rather than a failure. Third, **whether the message is sent at all**: `PhoneConnection.executeCustomMenuAction` (watch) runs `withContext(NonCancellable)`, because every caller closes its screen in the same gesture that selects and the send is a node lookup *then* a message — a cancel landing between the two dropped the selection entirely. `OpenPlaylistAction` encodes `activeEntryId` the same way as the rows, looking the playing item's media id up in the **full** queue rather than in the page just sent, because the watch matches it against each row's `entryId` by plain string equality. `QueueEntry.queueId` decodes malformed/`SPECIAL_ITEM_ERROR`-shaped ids to `QueueItem.UNKNOWN_ID`, which the handler treats as "no usable position" rather than passing on.
- **Paging**: the live queue is sent one page at a time — `common/.../CustomLists.kt`'s `QueuePaging` (`PAGE_SIZE` 20, `MAX_ENTRIES` 200, `nextLimit`, pinned by `QueuePagingTest`) — because every entry carries its own thumbnail asset across Bluetooth. The watch states the size it wants in the `MESSAGE_OPEN_PLAYBACK_QUEUE` payload (a 4-byte int; absent from pre-paging watch builds, which reads back as the default first page), and the phone reports how many entries exist in `customList.proto`'s `totalEntryCount` — the only way the watch can know whether offering "Load more" would get it anything. Requests are **cumulative, not incremental**: each asks for a larger prefix and replaces the whole list, because the queue is one DataItem the phone replaces wholesale. Play Services addresses assets by content hash, so covers already on the watch are not re-sent. The consequence to remember when touching this: any autonomous re-push has to reuse `MusicService.lastRequestedQueueLimit`, since `scheduleQueueRefresh` fires on every track change and a default-sized push would collapse a paged-through queue back to 20 rows under the user.
- **Where the watch's queue opens** is `wear/.../view/queue/QueueScrollPolicy.kt` (pure, JVM-tested, same shape as `QueuePaging`): it scrolls to the playing row rather than the top, and distance picks the method — within `ANIMATE_WITHIN_ROWS` it animates, because the movement shows *which way* the list went in a way a jump cannot; beyond it it jumps, because eighty rows of tracks flying past is several seconds spent arriving somewhere the user could have been shown at once.
- **Artwork** goes through `mobile/.../music/QueueArtworkResolver.kt`, a cheapest-first chain: `iconBitmap` → local `iconUri` → artwork URIs in `description.extras` → MediaStore (`loadThumbnail`, else `ALBUM_ID` → the legacy `albumart` table) → remote http(s), with `MusicService.currentAlbumArt` as a final fallback for the row whose `queueId` matches `activeQueueItemId`. That last step matters more than it looks: Media3's `MediaSessionLegacyStub` attaches a bitmap to a queue item **only** when the app embedded raw `artworkData`, while the current track's *metadata* goes through `loadBitmapFromMetadata`, which downloads `artworkUri`. A streaming client (Echo Music, YouTube Music front-ends) therefore shows art on the player while **every** queue row — including the playing one — carries nothing but a remote URL. Reusing the already-decoded player cover costs no network call and no permission. Two steps are gated:
  - MediaStore needs a media-read grant. `READ_EXTERNAL_STORAGE` stopped being grantable at `targetSdk` 33, so `READ_MEDIA_AUDIO` is declared and requested **in context** from the `queue_media_permission` row in Settings → Apps (`MiscSettingsFragment`), never at startup. Ungranted, the step is skipped silently.
  - Remote covers are the Echo Music / YouTube-Music-client case (Media3's `artworkUri` maps onto the legacy description as an http URL). Gated on `queue_remote_artwork`, which is **on by default** (`QueueArtworkResolver.REMOTE_ARTWORK_DEFAULT`) — the exception to the project's otherwise opt-in network stance, because a streaming queue has *no* other cover source, so off produced permanently blank rows rather than a degraded list; the shortcut-artwork fetch stays opt-in since it degrades to an app icon. Defaults are never persisted (`setDefaultValues` is not called anywhere), so this flips for existing installs that never touched the switch. Results are cached on disk and the requested size is rewritten into the URL first (`sizedArtworkUrl`, tested by `SizedArtworkUrlTest`): those clients publish a list-sized ~60px thumbnail, and since `shrinkPreservingRatio` only ever shrinks, fetching it verbatim left Cover-style pills visibly pixelated with no later step able to recover — reusing `ShortcutArtworkStore`, which is a plain URL-keyed PNG cache with no shortcut-specific notion. The download applies the same hardening `ApkDownloader` documents (follow redirects, explicit `User-Agent`, `Connection: close` against Android's truncate-on-redirect pooling bug). **This is a network path: keep `docs/privacy-policy.md` and the Data Safety draft consistent when touching it.** The toggle is intentionally declared in *both* `settings.xml` (Apps) and `watch_face_settings.xml` (Panels, beside the queue styling) — it is not in `SCOPED_KEYS`, so the face-scoped data store passes it through unscoped and both rows drive the one global key.
  - Whichever step found the cover, the result passes through `common/.../BitmapBorderTrim.kt` once (`resolve` wraps the private `resolveRaw` purely so that pass lives in one place). It crops flat letterbox/pillarbox bars — YouTube Music "art track" thumbnails wrap the real square cover in them, so without it a square crop keeps the bars and the cover lands as a small square inside the circle. It was extracted from `ShortcutArtworkFetcher`, which had the identical problem with the same kind of thumbnail and is still a caller; its one piece of real judgement (`isUniformLine` — what counts as "flat") takes a pixel lambda rather than a `Bitmap`, so it is pinned by a plain JVM test. It lives in `common` because the trim has to happen on **both** sides: a cover can also reach the watch from a source the phone never re-encodes (the reused now-playing bitmap, or an older phone build), so the watch trims again in `PhoneConnection.decodeCustomList`, which is the single point every list cover it draws passes through. Trimming twice is free — an already-trimmed cover has varied edges and comes back unchanged.
  - `OpenPlaylistAction` resolves every entry's cover concurrently (`coroutineScope { ... async { QueueArtworkResolver.resolve(...) } }.awaitAll()`), not one at a time — a 20-entry queue with several slow/failing remote fetches would otherwise serialize into seconds of wall-clock delay even though each fetch is already off the main thread. `QueueArtworkResolver` logs each entry's resolution path at `Timber.v` (candidates found, which step matched, why a step was skipped) for exactly this kind of "some covers just don't show up" report.

### Config backup (mobile)

`mobile/.../config/ConfigBackup.kt` exports/imports both button configs, the action list, the `MiscPreferences.EXPORTABLE` watch-behavior settings, the custom watch-theme library (`watchThemes` — see the Watch tab section; since schema 3), and (since schema 4) the user's personal runtime data — saved playlist shortcuts, search history and track history — under a `userData` block, as one JSON document (exposed in `MiscSettingsFragment`). The button-config/action-list files are copied as opaque base64 `PersistableBundle` blobs, so the backup format doesn't need updating when configs gain fields — but adding a *new* config file or a preference that should survive reinstall means touching `CONFIG_FILES` or `MiscPreferences.EXPORTABLE`. The theme library is validated as one unit before any import write (all-or-nothing), and importing a pre-theme (schema 1/2) backup deactivates any active custom theme so the imported `wear_screen_face` can't silently rewrite a saved profile's base layout. The `userData` block holds the three storages' raw JSON strings (`playlist_shortcuts`, `search_history`, `track_history`) and is restored in the same preference transaction; importing re-syncs the shortcut library to the watch. Older backups (schema ≤ 3) simply omit `userData` and leave whatever is already on the phone.

**Parcel-stability warning:** those blobs (and the on-disk config files themselves, `mobile/.../util/BundleFileSerialization.kt`) are raw `Parcel.marshall()` bytes, whose format is *not stable across Android OS versions* — a blob written on one version can throw `BadParcelableException` on another, and only **lazily** (at the first `bundle.get*()` call, far from the read site; nested bundles defer even further). This crashed the Watch tab on Android 15. Consequently: `readFromFile` force-unparcels inside its own guard, quarantines undecodable files (`<name>.corrupt`) and never throws; every deep bundle walk must still catch `RuntimeException`; `ConfigBackup.import` validates all blobs *before* writing anything (`BundleFileSerialization.isDecodable`) and throws on incompatible backups — which also makes `GlobalActionConfig`'s bundled-default seeding (`R.raw.default_config`, itself such a backup exported on some past device/OS) fall back to auto-detected defaults instead of planting an unreadable config. Writes go through temp-file + atomic rename.

### Update system (sideload self-updates)

Because the app is sideload-only, it ships its own updater. Phone side lives in `mobile/.../update/`: `UpdateChecker` polls the GitHub releases API (throttled to daily; triggered from `MusicService.onCreate` and phone `MainActivity.onCreate`; prefs `update_check_enabled` / `update_include_prereleases` in the Settings tab's Updates category), `UpdateNotifier` posts the notification, and `UpdateActivity` is the single update surface (versions, release page, push-to-watch). Release assets are matched **by exact name** (`mobile-release.apk` / `wear-release.apk`) — keep naming releases that way. `WatchApkPusher` downloads the wear APK and streams it over `CommPaths.CHANNEL_WEAR_APK`; on the watch, `watch/update/ApkReceiverService` (manifest `CHANNEL_EVENT` listener) receives it, validates the package name, and commits a `PackageInstaller` session, with `InstallResultReceiver` turning `STATUS_PENDING_USER_ACTION` into a tap-to-install notification (background services can't launch the confirm dialog) and `MY_PACKAGE_REPLACED` doing post-update cleanup. Needs `REQUEST_INSTALL_PACKAGES` + the user's one-time "install unknown apps" grant on the watch. The "Update watch" button is gated on the *watch's* version, reported via the `appVersionCode`/`appVersionName` fields of `watch.proto`'s `WatchInfo` (absent on pre-2.2 watch builds). Both app modules have `buildConfig true` enabled for `BuildConfig.VERSION_NAME` access.

The **phone updates itself** through the same shape: `ApkDownloader` (shared byte-count-validated download) → `PhoneApkInstaller` → `PhoneInstallResultReceiver`, mirroring the watch's `ApkReceiverService`/`InstallResultReceiver`. Two non-obvious constraints, both learned from an unlocalized system "There was a problem parsing the package" failure with no recovery path: the download is validated as a genuine APK *for this package* (`getPackageArchiveInfo` + package-name check) **before** it ever reaches an installer, since a matching byte count still misses same-length corruption; and it is committed through a `PackageInstaller` session rather than an `ACTION_VIEW` intent at the file — so there is deliberately **no FileProvider** in `mobile/` for APKs (sessions write from a `File` directly; the old `apk_paths.xml` was removed, don't reintroduce it). Missing "install unknown apps" is reported as a `Progress.NeedsPermission` state that opens the settings screen, never as a failure.

### Custom lists (watch menu content)

Several watch-facing features are phone-side SharedPreferences storages (`mobile/.../music/*Storage.kt` — search history, playlist shortcuts, track history) delivered to the watch as **custom lists**; the list types (live queue, recently-played fallback for apps that hide their queue, search results, playlist shortcuts, search history, library page) are defined in `common/.../CustomLists.kt`, and selection/deletion round-trips through `MusicService.onCustomMenuItemPresed` and `CommPaths.MESSAGE_DELETE_CUSTOM_LIST_ITEM`. Watch-initiated search (`SearchAction`) opens voice/keyboard input on the watch; the query returns via `CommPaths.MESSAGE_PLAY_FROM_SEARCH` and is resolved with `MediaBrowserSearch` (MediaBrowserService library search — the Android Auto/Assistant mechanism, far more reliably implemented by music apps than `MediaSession.playFromSearch`).

**Library browsing** (`CustomLists.LIBRARY`) is how the watch starts something that was never saved or searched for: `OpenLibraryAction` → `MusicService.openLibraryOnWatch()` walks the playing app's `MediaBrowserService` tree one page at a time via `mobile/.../music/MediaBrowserLibrary.kt` (a deliberate sibling of `MediaBrowserSearch`, sharing its `findBrowserService`/`connect`, since searching is one stateless query while browsing is a caller-driven walk; every page connects and disconnects rather than holding another app's binding open across a killable service). Row ids are encoded by `CustomLists.kt`'s `LibraryEntry` object (`b|` browsable / `p|` playable / `^up`) — a prefix rather than a new protobuf field, because the watch has to know whether a tap swaps in the next page or closes the menu and plays. `browse()` returning null means "this app exposes no library at all", which is reported as one explanatory row and is distinct from a `Page` with no children.

The governing constraint on all of this, written up in `docs/player-integration-notes.md`: **a media id is only meaningful to the app that produced it** (Retro Music `parseInt`s it, Echo demands an `auto/` prefix, InnerTune splits on `/`), so ids are only ever round-tripped from that app's own browse/search results — never constructed — and a *browsable* id must never reach a play command. Related: `mobile/.../music/MediaSessionCapabilities.kt` decides whether a transport command is worth issuing at all, with three states rather than two — a null `PlaybackState` resolves to **true**, because a session that has published nothing has not declined anything and is usually one freshly woken by a browser binding, which is exactly the wake-then-play path everything depends on. Its limit is worth knowing before reaching for it: the bitmask reliably says what a session *claims*, not what it does, and a missing bit is routinely wrong. Use it only where a false negative is cheap (search, which has a real alternative) — never to withhold a transport command whose failure mode is a silent no-op, which is why the queue tap issues and verifies instead (see *Playback queue*).

### Lyrics and track metadata

Two watch screens are fed by **on-demand request/response**, not by the pushed `MusicState`, and the reasoning is the same for both: a surface nobody has open should cost nothing. A watch on any other face never sends the request, so the phone never makes a network call, never opens a file, and the payload never crosses Bluetooth.

**The phone always does the network call, never the watch.** A Bluetooth-only watch has no internet route of its own, so a watch-side fetch would work on the LTE models and quietly fail on every other one; it also keeps the app's whole network surface on the device `docs/privacy-policy.md` describes. **Both paths are network paths — keep the privacy policy and the Data Safety draft in step when touching them.**

Both protocols echo the requested track's title/artist back in the answer, and the watch discards a response whose track is not the one on screen: the two sides drift by a track whenever a skip is in flight, and an answer for the wrong song is worse than none because nothing about it looks wrong.

- **Lyrics** (`lyrics.proto`, `CommPaths.MESSAGE_REQUEST_LYRICS` → `MESSAGE_LYRICS_RESULT`). Phone side: `mobile/.../music/LyricsFetcher.kt` reads [LRCLIB](https://lrclib.net) — chosen because it matches on *metadata* (track/artist/duration) with no API key, account or per-service track id, which is what lets lyrics work regardless of which app is playing; `LyricsRepository.kt` caches answers **in memory only** (persisting would leave a folder of other people's copyrighted text on disk and a privacy question to answer) and deliberately does not cache failures. Watch side: `wear/.../view/lyrics/` (`LyricsActivity`/`LyricsScreen`/`LyricsViewModel`) plus `LyricsFeed.kt`, which feeds the Verse face and which `MusicViewModel` enables *only* while that face is selected. Raw LRC travels as text and is parsed on the watch by `common/.../LyricsParser.kt` (honours the file's `[offset]`; renders per-word karaoke timing as ordinary lines). Tapping a line seeks to it (`LyricsViewModel.seekToLine`): it anchors `PlaybackClock` locally *before* sending `MESSAGE_SEEK_TO`, the same order the player's own seek uses, since waiting for the Bluetooth round trip would leave the old line lit long enough to look like a missed tap. Two decisions there. It seeks to the line's exact `timeMs` with **no lead-in** — a little earlier would be kinder to a listener catching the run-up, but `LyricsParser.indexAt` would then highlight the *previous* line, so the screen would answer a tap by lighting up a different row. And it is **not** gated on `MusicState.seekable`: that bit is routinely under-reported, an ignored seek is a no-op the clock's next check undoes, and withholding it on a wrong bit loses the whole feature — the rule `MediaSessionCapabilities` records and the queue tap already follows. The rows carry `indication = null` deliberately: the tapped line becoming the current line *is* the confirmation, and a ripple would be a third thing on a screen whose design is that the accent appears in exactly two places. `common/.../LyricsStatus.kt` keeps `NONE` and `FAILED` distinct — one is an answer, the other is a missing answer, and only the second is worth a retry or a "check your connection". `MiscPreferences.LYRICS_ENABLED` is **on** by default, for `QueueArtworkResolver`'s remote-artwork reasoning rather than the shortcut-artwork opt-in stance: there is no second source for a lyric, so off does not degrade the screen, it empties it — and opening the screen is itself the consent, since nothing is fetched until someone does. The action is `ACTION_OPEN_LYRICS` / `OpenLyricsAction`, watch-local in the same sense as the playlist menu: the watch launches `LyricsActivity` directly, and the phone-side handler only runs for paths that always execute on the phone (the actions menu), where it bounces `MESSAGE_OPEN_LYRICS` back.
- **Track metadata** (`metadata.proto`, `CommPaths.MESSAGE_REQUEST_TRACK_METADATA` → `MESSAGE_TRACK_METADATA`), backing the `metadata` face and `wear/.../view/metadata/MetadataFeed.kt`. Deliberately *not* folded into `MusicState`, which is sent on every state change and rides a size-capped payload — twenty mostly-empty strings would be paid for on every pause and volume nudge by every face. `mobile/.../music/TrackMetadataReader.kt` reads two sources in cost order: the playing app's own `MediaMetadata` (free, instant), then the **file** for bitrate/sample rate/channels/size, which are properties of the encoded audio and not `MediaMetadata` fields at all — local tracks only, gated on the media-read grant, and silent when either is missing. `mobile/.../music/MusicBrainzMetadata.kt` is the optional enrichment (ISRC, label, release date, catalogue ids): free, no key, and the only realistic source for those, but the match is *fuzzy* on title+artist alone, which is why `MiscPreferences.METADATA_LOOKUP_ENABLED` is **off** by default — unlike lyrics it only ever *adds* rows to a table that already stands on the player's own tags. The phone answers **twice** for one request when it is on — immediately with what it already knows, then again with `enriched` set — so the table is on the wrist before the first packet leaves, and the watch needs `enriched` to tell a second answer from a newer track.
- Both use the `/Messages` prefix, **not** `/IdleMessages`. That prefix exists to wake a watch whose UI is not running, and both payloads are useless to a watch with no such screen open — routing them there would spin the process up to throw the answer away. `/Messages` has no manifest listener, so they reach only `PhoneConnection`'s runtime listener, alive exactly when the screen is.

The payload also carries **how it is being played**, not only what is playing: the media URI verbatim, the local file's name (queried via `OpenableColumns.DISPLAY_NAME`, since a MediaStore `content://` URI ends in a numeric row id far more often than in a name), the audio output, `MediaController.PlaybackInfo.playbackType`, and the player's download status. Two things about that block. It is a **snapshot** — the answer is asked for once per track, so a value that moves mid-track (the output device, a download completing) is right when drawn and can go stale until the next track; the alternative is a subscription pushing on every change, which is exactly what `MusicState` already refuses to do for the position. And the URI is *sent* but never *opened*: `TrackMetadataReader` filters to `content://`/`file://` before any probing, because handing an `https://` media URI to a `MediaMetadataRetriever` would make this screen perform a network download to fill in a bitrate row. The output is read from `AudioManager.getDevices(GET_DEVICES_OUTPUTS)` in a priority order rather than from a "current route" API, because there is no reliable one at `minSdk` 23 — available is a good proxy for in-use for the three cases a listener distinguishes, and casting is answered first from the session itself since the phone's own route says nothing then. `outputKind` and `downloadStatus` cross as **codes, not labels**: a phone service's `getString` does not reliably follow the in-app language pre-33, so the watch owns the localisation (a Portuguese watch showing an English row would be the visible symptom).

`common/.../TrackMetadataFields.kt` owns both halves of the face's row registry: the `Group` enum (CORE/RELEASE/CREDITS/IDENTIFIERS/TECHNICAL/PLAYBACK — each a face-scoped preference key plus its default, so the renderer and `MiscPreferences.metadataGroupPreference` cannot disagree about what exists; a new group must be added to `EXPORTABLE` and `SCOPED_KEYS` too, which `ScopedAppearanceRegistryTest` pins) and the pure numeric formatters, shared for the same reason `PaletteTransforms` and `WatchTypography` are. Grouped rather than one switch per field, because a row exists only when the player published that tag — per-field switches would mostly control rows that are not there. The face never says "unknown": it draws a row per populated field, and a short table is the honest signal that a player is stingy with metadata. It fits rows by *measuring* rather than scrolling (scrolling would fight the host's configurable up/down swipe pseudo-buttons), which is what makes the group switches load-bearing — turning off the file details is how you make room for the credits. A row declares how many lines it costs (`MetadataEntry.lines`) and the budget is spent per line rather than per row, so the full-URL row — `wide`, three lines, no label column, because no 90dp column holds a signed CDN URL — displaces others instead of overflowing off the bottom.

Two details of the face are worth knowing before touching it. The **elapsed position is drawn to the millisecond and by its own composable** (`LivePositionRow`), not from the row list: the host's position ticker is 500 ms, which would step the last three digits by 500 twice a second, so the digits in between are extrapolated from the watch's own monotonic clock — the same rule `PlaybackPositionEstimate` enforces for the sample's trip across Bluetooth, never a cross-device subtraction. It re-anchors on every sample (so a seek lands rather than being caught up to) and runs only while playing. Keeping it out of `metadataRows` is what stops its ~16 Hz refresh from rebuilding the whole table. And the row-dedup checks compare against the **metadata payload's own** title/artist, never the two lines on screen: those become status text the moment playback stops, so comparing against them made pausing produce an "Album artist" row carrying the very name the check exists to suppress, directly under an artist line reading "Playback Stopped".

### Localization

The app ships translations for 14 locales, and the UI language is a **user preference that syncs to the watch**, not just a device setting: `MiscPreferences.APP_LANGUAGE` (in `EXPORTABLE`) is picked in the phone's Settings and resolved on both sides through `common/.../AppLocales.kt`, so a phone set to Portuguese doesn't leave an English watch. The two apps *apply* it by different means, deliberately — `mobile/.../view/settings/AppLanguage.kt` uses `AppCompatDelegate.setApplicationLocales` (every phone activity is an `AppCompatActivity`, and on Android 13+ this registers with the framework's per-app language setting), while `wear/.../util/WatchLanguage.kt` wraps each activity's base context, because `MenuActivity`/`QueueActivity` are plain `ComponentActivity` and AppCompat's pre-33 backport only recreates `AppCompatActivity`. Unknown/unsupported tags resolve to the system language rather than to themselves, since a value can arrive from an imported backup or a newer build on the other device.

Adding a language means keeping four places in step, all of which must agree or the picker lies about what's translated: a `values-<code>` folder in **each** of `mobile/`, `wear/` and `common/` (each module carries its own strings; `common/` backs shared views), `AppLocales.SUPPORTED` (order = picker order), `mobile/src/main/res/xml/locales_config.xml` (the Android 13+ system picker), and the `app_language_entries`/`app_language_values` arrays.

The folder names are **not** uniformly `values-<code>`: eleven of the thirteen use the plain/region form (`values-de`, `values-pt-rBR`, …) but two use the BCP-47 form — `values-b+id` and `values-b+zh+Hans`. Neither is stylistic. Android's legacy resource code for Indonesian is `in`, not `id`, so a `values-id` folder is silently never selected; and Simplified Chinese needs its script subtag, which the old syntax has no way to express. `AppLocales.SUPPORTED` and `locales_config.xml` still spell these the modern way (`id`, `zh-Hans`) — only the *folders* differ, which is exactly why the mismatch is easy to introduce and invisible until someone runs the app in that language.

**Adding an *entry* to any `<string-array>` picker is the sharper hazard**, and it has bitten repeatedly (3.1-beta2's changelog is largely this bug). `ListPreference` pairs `entries` with `entryValues` **by index**, and the `*_values` arrays live only in `values/` because they aren't translatable — so a translated `entries` array that wasn't extended does *not* degrade to English. An item missing from the end is unreachable (the five colour harmonies shipped in 3.1-beta1 could not be selected in any of the twelve translated locales); an item missing from the middle silently shifts every later label onto the wrong value (picking "Square (sharp corners)" applied Frosted edges). So a new picker option means adding it **at the same index in all thirteen `strings.xml` files**, not just `values/`. `mobile/src/test/.../res/TranslatedArrayAlignmentTest.kt` pins this by comparing item counts per locale.

## Build & test commands

Requires JDK 21 and an Android SDK path in `local.properties` (`sdk.dir=...`, gitignored — Android Studio creates it on first sync). After cloning, run `git submodule update --init` before building (see `wearutils/` above).

**There is no `java` on this machine's `PATH`.** `./gradlew` works only because `.claude/settings.json` sets `JAVA_HOME` to the unpacked JDK (`~/jdks/jdk-21.0.11+10`). Gradle picks that up, but anything invoking a JDK tool *directly* — `keytool` to check signing certs, `javap` to inspect a library class, `java -version` — must use the absolute path under `$JAVA_HOME/bin/`, or it fails with "command not found" rather than anything that names the real cause. `apksigner` likewise lives in the SDK (`~/android-sdk/build-tools/<ver>/`), not on `PATH`.

Standard Gradle/Android workflow (run from repo root):

```
./gradlew assembleDebug              # build phone app debug APK
./gradlew :mobile:assembleDebug      # build only the mobile module
./gradlew :wear:assembleDebug        # build only the wear module
./gradlew test                       # run all JVM unit tests
./gradlew :mobile:testDebugUnitTest --tests "*.StreamIntegerTest"   # single test class
./gradlew :wear:testDebugUnitTest --tests "*.StemButtonsManagerTest"
./gradlew :common:testDebugUnitTest  # common-module tests
./gradlew lint                       # Android lint across modules (see caveat below)
```

`lint` is **not a usable gate right now**: the modules carry a large backlog of unrelated lint errors and the task aborts before reporting, which is why checks lint would otherwise cover (e.g. `InconsistentArrays`) are pinned as plain JVM tests instead. Don't treat a lint failure as a regression from your change without checking it against `master` first.

Unit tests live under `mobile/src/test`, `wear/src/test`, and `common/src/test` (JUnit 4). `wear/build.gradle` uses the `unmock` plugin to run certain Android-framework-dependent tests on the JVM instead of mocking — see the `unMock { ... }` block when adding tests that touch `android.*` classes in `wear`.

There is no instrumented/UI test setup in this repo currently, and no CI — `.github/` holds only `FUNDING.yml`, so nothing runs these tests but you.

The testing convention that makes that workable: whenever a decision is subtle enough to have caused a bug, it gets **extracted into a pure function with no Android dependencies** and pinned by a JVM test, rather than being tested through the Android class that calls it. `resolveServiceHold` / `resolveReportedSession` / `RotaryAction.resolve` / `PausedHoldPolicy.holdMillis` / `IdleScreenAction.forButton` vs `forAutoOpen` / `LibraryEntry` / `MediaSessionCapabilities.advertises` / `sizedArtworkUrl` / `ColorHarmony` / `SettingsSearchIndex.rank` / `QueueEntry` / `QueuePaging.nextLimit` / `BitmapBorderTrim.isUniformLine` / `PlaybackPositionEstimate` / `PlaybackSyncPolicy` / `PredictedTrackAdvance` / `QueueScrollPolicy.resolve` / `FaceRecency` / `LyricsParser` / `MusicGlyphs` / `AccentFloorStyle` / `TrackMetadataFields` are all this shape — note how many of them exist specifically to pin a *fallback* choice, which is where the bugs were. Prefer following it over adding mocks.

A second shape has grown out of that one: **tests that read the resource/registry files directly and enforce a structural invariant no single function owns**, living under `mobile/src/test/.../res/`. `TranslatedArrayAlignmentTest` is the localization one above; `AppearancePreferenceScopingTest` asserts that every key declared in `watch_face_settings.xml` is in `FaceScopedPreferences.SCOPED_KEYS`, because the Watch face screen *is* the appearance surface — an unscoped key there silently changes every face at once (how the mini-button row offset stayed global while its four siblings were scoped). Its `DELIBERATELY_GLOBAL` set is the escape hatch, and adding to it is meant to be the moment you stop and justify it. `SettingsCatalogTest` is the same shape for `SettingsCatalog` (see *Phone app UI*): every category declared in `settings.xml`/`watch_face_settings.xml` must appear in the matching category list or it is never assigned a page visibility and shows on all of them (how `cat_idle` ended up on every Settings page), and every listed category must be reachable from at least one section or its settings become unreachable. `ScopedAppearanceRegistryTest` (in `common`) is the registry-side counterpart to the first of those: every key in `FaceScopedPreferences.SCOPED_KEYS` must also be in `MiscPreferences.EXPORTABLE`, since `WatchPreferenceSyncCoordinator` filters on that registry and `SCOPED_DEFINITIONS` is the intersection — omit it and the phone stores the value, the phone's own preview reads it back and looks completely correct, and the wrist never hears about it while no saved theme can capture it. All of them fail with an explanatory message naming the offending file or key, so read the failure rather than adjusting the expectation.

To sideload builds onto real devices, `serve_apk.py` (repo root) serves the assembled mobile/wear debug and release APKs — plus the release `.aab` bundles — over HTTP on the local network (**port 8760**), build first, then `python3 serve_apk.py` and download from the phone/watch browser.

## Signing

Release signing is pulled from an optional `keystore.properties` file at the repo root (not checked in; keys `storeFile`/`storePassword`/`keyAlias`/`keyPassword`) — see the `afterEvaluate` block in the root `build.gradle`. Note the shape, which is not the usual one: neither module declares a `release` signing config at all. Both `mobile/` and `wear/` point their release build type at `signingConfigs.debug`, and the root `afterEvaluate` **rewrites that debug config's credentials in place** when `keystore.properties` exists. So the file's presence re-signs *every* variant, debug included — which is what lets a locally built `assembleDebug` update an installed release build in place and still talk to it over the Data Layer. Without the file, everything falls back to the real debug key and release APKs are debug-signed. `release.keystore` sits at the repo root too and is gitignored via `*.keystore`; it is the *one* key both APKs must share (see "Package naming gotchas"), so losing it means no user can ever update in place.

## Releases & release docs

- `versionCode` lives in `mobile/build.gradle` and `wear/build.gradle`; the two modules are version-coded independently (`versionName` is kept in sync — currently mobile `59` / wear `159`, both `3.1`). A `-betaN` (or similar) `versionName` suffix is how Crashlytics/Analytics reports are kept out of a future stable release's "3.1" bucket. `UpdateChecker.isNewer` gives that suffix **semver pre-release precedence** — `3.1-beta1` < `3.1-beta2` < `3.1` — rather than discarding it, which it used to do: every beta of one numeric version compared equal, so beta testers were told "you're up to date" while the screen displayed a newer beta as the latest release, and they'd also never have been offered the eventual `3.1` final. Note the bootstrap trap that leaves behind: an install running a build from *before* that fix carries the old comparator, so it can only be reached by a release whose **numeric** part is higher (`3.1.1`/`3.2`, not `3.1`) — or out of band via the announcements FCM topic. The gaps in the versionCode sequence (e.g. wear jumping 135 → 140) are historical: Play Console permanently burns every uploaded versionCode, so bumps had to skip ahead during the abandoned Play Store attempt. That's no longer an active constraint now that the app is sideload-only, but keep bumping monotonically.
- `CHANGELOG.md` (repo root) is the user-facing changelog — update it alongside user-visible changes.
- `docs/player-integration-notes.md` records what specific music apps (Retro Music, Echo, InnerTune) actually implement, read from their source — which browse/search/play callbacks exist, and which sessions honour them. Consult it before guessing at `playDeepLink` / `MediaBrowserPlayback` / `MediaBrowserLibrary` behaviour; it names its sources and read date, and all three are moving targets. `docs/spotify-integration-assessment.md` is a **closed question**: a Spotify Web API / App Remote integration is not blocked technically but by Spotify's quota rules (development mode caps at 5 hand-allowlisted users; extended quota has been organizations-only since 15 May 2025, with a 250k-MAU bar). Screenshots for the README go in `docs/images/`.
- `docs/index.html` is the **GitHub Pages landing page** (the `docs/` folder is the Pages root): a single self-contained HTML file styled after the app's Lyra look, using the fonts in `docs/fonts/` and images shared with the README in `docs/images/`. It's a hand-styled transcription (same Lyra colors/fonts/logo as `docs/index.html`, its own `<style>` block), not something generated from the `.md` at build time, so **the two don't stay in sync automatically**: `docs/privacy-policy.md` remains the maintained source text (including the "Last updated" date), and any edit to it — a new network call, a changed default, a permission add/remove, all the call-outs elsewhere in this file that say "keep `docs/privacy-policy.md` ... consistent" — needs the matching section hand-copied into this page too, with the date bumped in both.
- Publishing a release means: bump both `versionCode`s and the shared `versionName`, close the `Unreleased` CHANGELOG section, `assembleRelease` both modules, and attach `mobile-release.apk` + `wear-release.apk` to a GitHub release tagged with the version (`--prerelease` for a beta). Verify both APKs carry the same signing certificate before publishing — a mismatch silently breaks all phone⟷watch communication. Publishing is what triggers `UpdateChecker`'s notification to existing users, so it is the point of no return.

## Package naming gotchas

The app was renamed from Music Center for Wear (fork of matejdro/WearMusicCenter): all code now lives under `com.svartifoss.snfell` / `com.svartifoss.snfell.common`. Older docs/commits referencing `com.matejdro.wearmusiccenter` mean the same code.

- **The three modules nest differently, and `mobile/` is the odd one.** `common/` is under `com.svartifoss.snfell.common.*` and `wear/` under `com.svartifoss.snfell.watch.*`, but phone code sits at the *bare* root `com.svartifoss.snfell.*` with no module segment — there is no `.mobile` package. So the `mobile/.../music/QueueArtworkResolver.kt` shorthand used throughout this file expands to `mobile/src/main/java/com/svartifoss/snfell/music/QueueArtworkResolver.kt`, and guessing a symmetric `…/snfell/mobile/…` path will miss every time. A few phone classes (`WearMusicCenter`, `WatchListenerService`, `NotificationService`, `WatchPreferenceSyncCoordinator`) sit loose at that root rather than in a subpackage.
- Despite living in `wear/`, the watch-side code is under the package `com.svartifoss.snfell.watch.*` (not `.wear.*`) - that's the Gradle `namespace`, used for generated R/BuildConfig classes only. All watch-side classes (`PhoneConnection`, `WatchMusicService`, `MainActivity`, etc.) are in subdirectories named `watch/communication/`, `watch/view/`, `watch/model/`, `watch/config/`, `watch/util/`.
- The Gradle **`applicationId`** **must be identical** in `mobile/` and `wear/` (both `com.svartifoss.snfell`) and both apps must be signed with the same key. The Wearable Data Layer API (`MessageClient`/`DataClient`) only routes messages/DataItems between a phone app and a watch app that share the same `applicationId` — a mismatch means the two apps never connect and both report "No watch connected". (This regressed once: the wear app was briefly given `com.svartifoss.wrfell` for a separate Play Store listing, which broke all phone⟷watch communication.) Both apps therefore ship as same-key sideloadable APKs — the identical `applicationId` is a Data Layer requirement, not a store one. `MainActivity.openWatchPlayStorePage()` (mobile) still opens `market://details?id=<WEAR_APPLICATION_ID>` (== the phone package), but with the app no longer on the Play Store this path is effectively **vestigial**; regardless, `WEAR_APPLICATION_ID` must still equal `wear/build.gradle`'s `applicationId`.
- `mobile/` still contains one deliberately un-renamed package: `com.matejdro.wearvibrationcenter.notificationprovider`. This isn't just a name to preserve — it backs a **functioning notification-access interop subsystem** (`mobile/.../notifications/NotificationProvider.kt` plus the AIDL contract in `mobile/src/main/aidl/com/matejdro/wearvibrationcenter/notificationprovider/`) that lets the separate Wear Vibration Center app read notifications through Svartifoss. Renaming the package would break that cross-app AIDL binding.
- The `wearutils/` submodule keeps its own `com.matejdro.wearutils.*` packages.

## Modernization roadmap

`docs/wear-modernization-plan.md` contains the full phased modernization strategy: Foundation (targetSdk bump — now at 35 — and deprecated API cleanup) → MediaSession mirror (watch-side `MediaSession` that forwards controls to the phone) → Tiles & Complications → in-UI navigation. Consult this doc before making architectural decisions in `wear/`.

**Current state (merged to `master`):** `WatchMediaSession` is implemented and active (Phase 1), and the Phase 2 Tiles & Complications surfaces exist: two Tiles (`watch/tile/`, built with `androidx.wear.protolayout`/`androidx.wear.tiles` — `MediaTileService.kt` for track info/transport/seek, and `ShortcutsTileService.kt` rendering the synced playlist-shortcut custom list as tappable chips, each dispatched through the invisible trampoline `ShortcutLaunchActivity`, because a Tile `Clickable` can only start an Activity — never send a Data Layer message — so it re-performs the same open-URI-on-phone + `MESSAGE_CUSTOM_LIST_ITEM_SELECTED` pair the watch menu does, see *Actions system*) and a complication data source (`watch/complication/AlbumArtComplicationDataSourceService.kt`, `androidx.wear.watchface` complications). Because these run outside the main app UI lifecycle, they fetch music state directly over the Data Layer via `CommPaths` rather than through `PhoneConnection`; the manifest-registered `MusicStateListenerService` (`watch/communication/`) requests a Tile + complication refresh whenever the phone publishes new music state — `WatchMusicService` does the same while running, but it idle-times out, and without this listener the surfaces froze on stale state. It also revives a dead `WatchMusicService` when the received state says music is playing (the phone only sends `MESSAGE_START_SERVICE` on a playback-*start* edge, so a service that died mid-playback would otherwise stay dead). A sibling `ConfigListenerService` (`watch/communication/`) does the analogous job for the button-config (`/Actions/*`) and action-menu (`/ActionList`) DataItems: those have no other always-on delivery (they arrive only through `PhoneConnection`'s runtime `DataClient` listener, live only while the connection is active), so a config edited on the phone while the watch is idle used to apply only after the user woke/tapped the watch. The manifest listener posts the frozen `DataItem` into `PhoneConnection`'s config `LiveData` — which the `WatchActionConfigProvider`/`WatchActionMenuProvider` observe with `observeForever` — so an open now-playing screen re-decodes and applies the change with no interaction.

Jetpack Compose for Wear OS (`wear.compose.material3`) is enabled in `wear/build.gradle` and used for `QueueActivity`/`QueueScreen` (`watch/view/queue/`) and `MenuActivity`/`MenuScreen` (`watch/view/menu/` — the actions/custom-list menu, which replaced the old `WearableDrawerLayout` bottom drawer; `MenuActivity` is a pure picker that returns the selection for `MainActivity` to execute). Shared Compose chrome (curved clock, scroll indicator, the pulsing `EqualizerBars`) lives in `watch/view/compose/WatchScreenChrome.kt`; those three bars are the app's single "something is happening" animation — the queue's now-playing marker, its "Load more" row, and (as `LoadingBars`, the same drawing at standalone size) every loading state in the watch app. An arc spinner filled the last role and was dropped for being a second vocabulary: a generic platform shape inside a screen that already had a house animation for exactly this, and one that reads as *audio*. The bars carry deliberately non-harmonic periods (480/360/560 ms) so they do not beat in step and read as one block breathing, and all three are drawn in **one** `Canvas` with the animated values read inside the draw lambda — animating each bar's `fillMaxHeight` re-ran layout for the whole row every frame and genuinely did cost the queue its scroll budget; design constants for all three UI stacks live in `watch/theme/WatchTheme.kt` — including the typography catalog: `MiscPreferences.WEAR_FONT` picks the track title/artist typeface via `watchFontFamily()` (system families plus bundled fonts — retro typewriters, Google Sans, Poppins, Montserrat, Marcellus, Bebas Neue, Playfair Display, Space Grotesk, Orbitron, Caveat). The phone's half of that mapping lives in `mobile/.../view/settings/WatchFontCatalog.kt` — extracted out of `WatchPreviewView` so the *picker* can render each option in the font it names — so a new font key means three places in step: `watchFontFamily()`/`watchFontTypeface` on the watch, `WatchFontCatalog`, and the `wear_font_entries`/`wear_font_values` arrays. A bundled font must be dropped into **both** `mobile/src/main/res/font/` and `wear/src/main/res/font/` (the preview and the watch each load their own copy) with its license text added under `licenses/<font>/`, with a keyword easter egg (`lainFont()`) that overrides the chosen font when the track/artist text matches Serial Experiments Lain-adjacent keywords. `WEAR_FONT` styles only the track title and artist unless `MiscPreferences.WEAR_FONT_ALL_SCREENS` is on, which extends it to the menu, the queue and the shared Compose chrome. Song lyrics have their own key, `MiscPreferences.WEAR_LYRICS_FONT` — a `WEAR_FONT` catalog key or `WatchTypography.LYRICS_FONT_FOLLOW` (the default), which keeps whatever each surface was designed with (the UI font on the lyrics screen, Marcellus on Verse); resolved by `WatchTypography.lyricsFontKey` on both sides, and face-scoped like the rest of the appearance keys so a saved theme carries it. Music-note characters inside lyric text are drawn as the Svartifoss mark rather than as text: lyric files are full of `♪`/`🎵` and most of the font catalog has no glyph for them, so they arrived as a fallback face, the wrong weight, or tofu. `common/.../MusicGlyphs.kt` decides what counts as a note and where the boundaries fall in a string (pure, JVM-tested); `watch/view/compose/MusicNoteText.kt` does the rendering, since only Compose can put an image inside a line of text.

New watch UI work should prefer Compose; the legacy View-based `MainActivity` (now-playing screen) remains, but its central rendering is now a swappable **now-playing face** (`watch/view/face/NowPlayingFace.kt` — a state-in/events-out contract, selected by `MiscPreferences.WEAR_SCREEN_FACE`): "classic" is the original View presentation (MainActivity itself is its implementation), "expressive" is a Compose face (`watch/view/face/ExpressiveFace.kt`, mirroring the Material 3 Expressive system media controls: cookie play/pause button, contour-following progress ring, round tonal transport buttons, accent-tinted/vignetted backdrop; queue/volume/menu access is left entirely to the user's configured mini buttons and gestures — there is no fixed default glass trio, so there's never a second, conflicting set of shortcuts), and the remaining keys — "vinyl", "poster", "studio", "halo", "aurora", "eclipse" (true-black AMOLED), "spectrum" (animated per-track bar field), "material" (capsule/tonal-surface treatment), "immersive", "depth" (three parallax layers) — are the **curated player collection** in `watch/view/face/CuratedPlayerFaces.kt`, which replaced the old standalone `VinylFace.kt`/`PosterFace.kt` Beta faces; "carousel" (a full-bleed cover rail, card silhouette from `common/.../CarouselCardShape.kt`) is big enough to live in its own `watch/view/face/CarouselFace.kt`, as is "chat" (`watch/view/face/ChatFace.kt` — the session as a messaging thread: a title and artist bubble per played track, the current one as a wide right-aligned voice-message bubble with the cover as avatar and the waveform doubling as the progress bar). Four things about it are load-bearing. Its thread lives **in the face**, session-scoped, deliberately not from `CustomLists.HISTORY` (a persisted, user-deletable list) nor `queueCards` (what has *not* played yet) — neither answers "what this sitting played, in order", so either would show rows the user never heard; it appends inside a `LaunchedEffect`, not in the composable body, since growing a `mutableStateListOf` that the same composition reads is a write-during-composition. It filters status text out of that thread using `NowPlayingFaceState.titleIsStatus`/`artistIsStatus` (fed from the host's `titleLineIsStatus`), which exist precisely because a face that *accumulates* metadata would otherwise record "ERROR" or "Playback Stopped" as a track that played — and the strings can't be matched on, being localized into 14 languages. Its gestures hang off a large **centre region** rather than a control, because `binding.centerTapZone` is `View.GONE` for every Compose face (`MainActivity` line ~4023) so a face that wires nothing has no working centre at all — and the voice bubble is deliberately *not* clickable, since sitting over that centre and taking taps is exactly what broke play/pause in the first version. Finally it is the one curated face with a fixed action row, and that row is where it **hosts** the mini buttons rather than letting the shared View row float over them: `MiniButtonPlacement.isHostedByFace` (the one registry all three consumers read) makes `MainActivity` suppress the row and hand the face the configured slots through `NowPlayingFaceState.miniButtons`, so Chat draws one circle per configured slot, sized to re-fit for a third, each running that slot's own tap and long press. With nothing configured it falls back to the pair it has always had (queue + skip next) — the thread occupies that band, so it would otherwise ship with no shortcuts at all. The consequence to keep straight is which half of the mini-button settings reaches a hosted row: the *appearance* does (background style through `MiniButtonSurfaces`, group opacity), the *placement* cannot (the composition places them), so `WatchFacePrefsFragment` hides the curve and shape pickers for a hosting face rather than leaving pickers that change nothing — the rule Carousel's card shape already follows. It therefore no longer defaults the row off (only the edge arc), since defaulting it off would hide the buttons from the one face built to show them; `FaceScopedBooleanDefaultTest` pins that. "verse" (`watch/view/face/VerseFace.kt`) puts the song's *words* on the main screen - the line before, the line now and the line next - fed by `watch/view/lyrics/LyricsFeed.kt`, which `MusicViewModel` enables only while this face is selected (the lookup is a phone-side network call per track, so no other face pays for it). Its lyric lines are set in a serif, the one in the collection that is; everything ordinary about it - running head, elapsed time, the per-line progress hairline - goes through the shared text/progress helpers, because a face designs its own *composition*, not its own settings. A track with no synced lyric is the common case, not a failure, so it falls back to a title card rather than an error. "split" (`watch/view/face/SplitFace.kt`) is the notification-card layout: cover in the top band, a solid album-coloured panel below holding artist over title, and the source-app icon as a round badge straddling the seam. It is the only face that **paints its own opaque backdrop**, so the Album background styles have no effect on it by construction — the two-tone composition *is* the treatment, and letting the host's full-screen artwork show through would erase it (it still honours `albumArtHidden`). That is precisely why its panel has a control of its own, `common/.../SplitPanelStyle.kt` (`wear_split_panel`, face-scoped, JVM-tested): without one there is no way to change that half at all. `BLUR` (the default) lays the cover across the **whole screen** and clips the blurred copy to the panel rather than scaling a second copy into it — fitting it to the lower box would crop it differently and the seam would read as two unrelated pictures instead of one going soft. It composites artwork *over* an opaque panel (`PANEL_ART_ALPHA`), not a colour wash over artwork: the same blend either way, but this order keeps the panel's luminance anchored to `panelArgb`, which is the value `AdaptiveTextContrast.prefersDarkText` decides the text colour from. It blurs through the shared `BitmapBlur` rather than Compose's `Modifier.blur`, which is a no-op below Android 12 and would leave older watches a sharp photograph — a different design, not a degraded one. `WatchPreviewView.drawSplitPlayer` mirrors all of it. Its text colour is decided, not assumed: the panel is the album's colour and can land anywhere from near-black to near-white, so both it and the badge glyph run through `AdaptiveTextContrast.prefersDarkText`, whose `relativeLuminance` is hand-rolled free of `android.*` precisely so the phone preview and the watch make the identical call from a JVM-tested function. "note" (`watch/view/face/NoteFace.kt`) is the minimal one: a black backdrop (its `defaultForFace` is `HIDDEN`), a small cover disc and one centred `Artist: Title` sentence built as a single `AnnotatedString` so it wraps as a sentence rather than as a label and a value. It keeps its mini-button row (it leaves the bottom band free, so that row is the only way to reach anything) but still defaults the edge arc off. It also draws its cover disc regardless of `albumArtHidden` — the one departure from the convention that a small cover is decoration a "hide artwork" background may remove, because its own default backdrop *is* that style and honouring the flag would ship the face permanently empty. "metadata" (`watch/view/face/MetadataFace.kt`) inverts the collection's premise: every other face is built around the artwork and treats the tags as a caption, this one shows a small cover and then as much of the record's actual detail as the screen holds — fed by the on-demand path in *Lyrics and track metadata* above, so no other face pays for it. Split and Verse share `FaceScopedPreferences.SELF_COMPOSED_FACES` (mini-button row and edge arc off), with `SPLIT_DEFAULTS`/`NOTE_DEFAULTS`/`VERSE_DEFAULTS`/`CHAT_DEFAULTS` layering each face's own on top (Chat left that set when it began hosting the row — it keeps the edge arc off and nothing else); all of them hang their gestures off the shared `CenterGestureRegion` in `FaceChrome.kt`.

**A per-face default only works if both overloads resolve it.** `FaceScopedPreferences.getString` and `getBoolean` must walk the identical four steps (explicit `key@face` → `perFaceDefault` → legacy global → definition default). The boolean one has now dropped the `perFaceDefault` step **twice**, and the failure is quiet and specific: the phone data store consults it on both, so the settings switch shows the face default while the watch shows the definition default, and the only way a user can reconcile them is to toggle the switch — which writes an explicit `key@face` and hits the one branch that always worked. `FaceScopedBooleanDefaultTest` pins it. Curated faces share one interaction contract: the single visual focus toggles play/pause, double-tap opens quick actions, long-press opens the queue; previous/next/menu/volume are deliberately left to the configurable mini buttons and gestures. Their gradients/progress/accents come from album-art-derived palettes (`watch/theme/AlbumPalette.kt`), and each ships a dedicated ambient variant. All Compose faces render in the single `ComposeView` (`composeFaceKind` picks which) layered between the gesture layers and the overlays, keep the expressive face's bottom pill-trio geometry so the shared mini-buttons/quick-panel fit unchanged, ship their own outline AOD variant (AOD "follow" maps each Compose face to itself), and share small building blocks via `FaceChrome.kt`. A new face key must also be added to `ThemeAppearance.ALLOWED_BASE_FACES` (the canonical registry both sides validate against — also the source the on-watch picker's `WatchFaceCatalog` derives from, so a face registered there cannot go missing from the picker), the phone's `wear_screen_face_entries/values` arrays, `WatchThemeRepository`'s face-name map, `MainActivity`'s `composeFaceKind` list *and* its `when` that constructs the composable, the visual-AOD-face set in `WatchFacePrefsFragment.updateAodDetailVisibility`, and given a miniature in `WatchPreviewView` (which carries several `when` branches keyed by face — grep the key of an existing curated face to find them all). The face *count* is also written out in prose in five user-facing spots that no test pins — `README.md` twice (the screenshot caption and the **Eighteen now-playing faces** feature row, which also *names* the faces) and `docs/index.html` three times (the hero paragraph, the stat tile, and the faces-wall heading) — so update all five with the registry. They were left stale at "eleven" through two releases before being corrected for 3.1; the drift is invisible until someone reads the docs. **A face is an assembly of pieces, not a monolith.** The distinction that matters: a face owns its *composition* - what goes where, at what size, in what shape - and never its *settings*. Concretely, every Compose face must render its backdrop through `PlayerBackgroundTreatment(state)` and `PlayerShadingOverlay(state)` rather than painting its own; must take its title colour from `titleTextColor(state, designed)`, its artist colour from `state.artistColor`, its fonts from `state.titleFont`/`state.artistFont` and its typography from `state.titleTypography`/`state.artistTypography`; and must route any progress element through `state.progressColor`. Painting `.background(Color.Black)` on the root is the specific mistake to watch for - it silently makes every one of the ~20 Album background styles, the blur radius, and the whole shading group render as a black screen on that face. Carousel had exactly that bug and its fix is recorded in its own source; Verse shipped with it and was corrected the same way. The counterpart rule is that a distinctive *treatment* belongs in a shared registry so any face can wear it and a custom theme can save it - `common/.../AccentFloorStyle.kt` (the accent wash pooled along the bottom edge — `MiscPreferences.WEAR_ACCENT_FLOOR`, off everywhere but Verse; drawn by `watch/view/compose/AccentFloorGlow.kt` inside `PlayerBackgroundTreatment` so it lands above the backdrop and below the content, its falloff a function of distance from the *centre* because a flat vertical gradient cuts a chord across a round display and reads as a rectangle behind the bezel) is the worked example: it was extracted out of the lyrics screen and the Verse face precisely because a treatment welded into one composition cannot be put on another. Deliberate exceptions exist and are documented at their sites (Split's opaque two-tone backdrop, Note's cover disc, Expressive's and Material's always-drawn rings, Chat's waveform), but each one costs a user a preference, so adding to that list is a decision, not a shortcut. A face whose defaults fight the standard chrome gets an entry in `FaceScopedPreferences.perFaceDefault` instead of special-casing at the draw site — `SELF_COMPOSED_FACES` (Split, Verse) turns the mini-button row and the edge progress arc off, because those two compose the whole screen edge to edge and the shared chrome lands *on top of* the composition rather than beside it. Hosting the row (Chat, above) is the other answer to the same collision and the better one where a face already has somewhere to put the buttons: the chrome stops being something to hide and becomes part of the composition. (Note these are defaults only: the keys stay face-scoped and switchable, and `perFaceDefault` returns `String?` for every type, so a boolean default is the string `"false"`.) Faces retired for known problems go into `ArchivedFaces.KEYS` (`common/.../ThemeAppearance.kt`; `view/watchface/theme/WatchThemesActivity.kt` keeps a `typealias` so the phone's call sites stay put) rather than being deleted: that one set hides them from both the face picker and the Watch-themes list, which used to keep separate copies and drift, and the developer "Show archived options" switch reveals them. All input handling (quadrants, swipes, stem, rotary, mini buttons, quick panel) is face-agnostic and stays in MainActivity; the hidden classic views keep being updated (ambient mode and the quick panel read from them).

**Colour treatments and typography** both resolve in `common` so the watch, the phone preview and the settings UI cannot disagree. `SurfaceColorTreatment` is the vocabulary (Normal/Desaturated/Expressive plus the harmony cases Complementary/Triadic/Analogous/Monochrome/Duotone); `ColorHarmony` holds the derivation math and `ColorModifier` (`wear_color_modifier`: none/vibrant/pastel/warm/cool) the orthogonal tone filter applied afterwards; `SurfacePaletteResolver.derive()` is the **single entry point** all three callers use — wear `MainActivity.resolveSurfacePalette`/`applyAccentColor`, `WatchPreviewView`, and `ColorTreatmentPreference`'s swatch dialog. Every treatment deliberately anchors its **primary** to the album's own hue and rotates only the companion slots, so switching treatments alone never changes the main accent; `wear_color_hue_shift` (0–359°, applied last inside `derive`) turns all three slots together, which varies that primary while preserving each harmony's internal angles. It is skipped for `NORMAL` — that colour was picked by hand, so rotating it would render something other than what the picker showed. Adding a treatment means a case in the enum + resolver and an entry in both `wear_color_treatment_*` and `wear_component_color_treatment_*` arrays; nothing else. Two rules the harmony math enforces and `ColorHarmonyTest` pins: a hue rotation is meaningless below `CHROMATIC_SATURATION_FLOOR`, so near-greyscale artwork degrades to a tonal ladder instead of yielding three identical greys; and a neutral source is never clamped up into the legible saturation band, which would invent a tint the cover never had. `WatchTypography` does the same job for the per-element title/artist controls (weight — a free 1–1000 value, not stepped — italic, scale, opacity, tracking, plus source-icon scale/opacity), returning primitives so Compose faces, the classic View face and the preview's `Paint` each apply them their own way. **Every default is the exact identity, and identity means "keep what this face designed"** — weight 400 leaves a deliberately-bold face bold rather than flattening it to 400. AOD is deliberately *not* affected: it has its own `WEAR_AOD_*` controls. These controls live in the Watch tab's own **Typography** section (`WatchFacePrefsFragment.SECTION_TYPOGRAPHY`, `cat_wf_typography_*` categories in `watch_face_settings.xml`) rather than under Style/Colors, so the font/title/artist/icon controls aren't buried among layout and colour settings — and the title/artist/clock *colour* controls belong there too, beside the rest of that element's settings, not on the Colors page (Colors keeps the album palette and the non-text surfaces).

Two more text helpers resolve in `common` for the same preview-must-not-lie reason. `AdaptiveTextContrast.kt` keeps album-derived text legible against the artwork actually behind it: a fixed lightness floor (`WatchTheme.accentForText`) can only ever be right for one assumed background, so this measures the luminance of *the band the line occupies* — not the whole cover, which averages away exactly the local contrast that matters — and pushes lightness apart while keeping hue/saturation, so the line still reads as the album's colour rather than as white. It is opt-in per element (`WEAR_ARTIST_ADAPTIVE_CONTRAST` and the clock's equivalent) precisely because a hand-tuned palette shouldn't be silently corrected, and applies only to the album-colour mode (White/custom are explicit choices; Dynamic resolves legibility its own way). `RoundScreenText.kt` holds the geometry for keeping a text block inside a round screen: the usable chord collapses fast towards the top and bottom, so hand-tuned side padding is only ever correct for the line count its author tested — the moment a title wrapped, the second line sat deeper and ran into the bezel. It returns width as a fraction of screen width at a given depth, clamped so a very low band can't collapse into a one-character column. Carousel is its first consumer. `AlbumAccentSelection.kt` decides *which* swatch of the cover becomes the accent in the first place, and exists because the two sides had quietly disagreed for as long as both existed: the watch took Palette's balanced answer and the phone preview took the vibrant one, each with a comment claiming it matched the other. `selectPrimaryAccent(vibrant, swatches, source, minShare)` is now the one function all three consumers call — wear `MainActivity`, `MediaTileService` and `WatchPreviewView` — with the disagreement promoted to a user choice, `MiscPreferences.WEAR_ALBUM_ACCENT_SOURCE` (face-scoped, in `SCOPED_KEYS`): `BALANCED` takes the vibrant swatch only when it covers at least `minShare` of the dominant swatch's pixels and the dominant colour otherwise, so a lens flare on a mostly-blue cover can't turn the UI red while the blurred backdrop behind it stays blue; `VIBRANT` takes it regardless, which is the trade `BALANCED` refuses. Unknown values resolve to `BALANCED` because that is what every existing install already renders. A null return means "no colour information at all" and is reported as *keep the accent already showing*, never as a colour. The watch caches the extracted palette per bitmap, so `lastPaletteAccentSource` has to be part of the cache key — changing the setting otherwise does nothing until the track changes.

One font in the `WEAR_FONT` catalog, **Google Sans Flex** (`WatchTypography.FLEX_FONT_KEY`), is a true OpenType variable font with six axes (`wght`, `wdth`, `opsz`, `slnt`, `GRAD`, `ROND`; bounds pinned to the bundled font's own `fvar` table, not guessed). `wght`/`slnt` reuse the per-element weight/italic controls above (so Flex doesn't add a second, conflicting weight control); the other four — width, optical size, grade, roundness — are deliberately *global*, not per-element, and only shown (`cat_wf_typography_flex`, toggled live by `WatchFacePrefsFragment.initTypographyDependencies`) once Flex is actually selected. `WatchTypography.flexVariationSettings()` builds the one variation string both sides render from: the watch's classic face resolves it via `WatchTheme.flexTypeface` (`Typeface.Builder(File)` — the font resource has no direct-from-resource-id builder constructor, so it's extracted to a cache file once per process), Compose faces via `WatchTheme.flexFontFamily` (`Font(resId, variationSettings = FontVariation.Settings(...))`, gated behind `@OptIn(ExperimentalTextApi::class)`), and the phone preview via its own identical `Typeface.Builder(File)` path — same extract-to-cache trick, since `mobile` cannot depend on `wear`. The bundled `google_sans_flex.ttf` (~4.1MB, in both `mobile/src/main/res/font/` and `wear/src/main/res/font/`, OFL-licensed under `licenses/google-sans-flex/`) is the true variable master, not a static instance — smaller combined than the two static Google Sans weights it sits alongside.

The colour treatments above only *compute* a distinct secondary/tertiary — on the classic face, nothing drew them anywhere visible (progress bar and artist text render only the primary slot, and every album-derived treatment deliberately keeps the primary close to the raw accent), so switching Expressive→Triadic looked like a no-op. `CircularProgressSeekBar`'s `RingStyle.SOLID` (the default ring style) now paints a primary→secondary→tertiary sweep gradient instead of a flat fill, but *only* when `ColorHarmony.hueDistance` between them clears `MIN_DUOTONE_HUE_GAP` — so Normal/Desaturated/Expressive/Monochrome (whose secondary/tertiary sit close in hue) render pixel-identical to before, and only the hue-rotating treatments (Triadic, Complementary, Analogous, Duotone) visibly change. Normal stays in that group *by construction, not by coincidence*: `WEAR_NORMAL_COLOR_MULTI` (default **on**) makes it derive a secondary/tertiary from the picked colour via `PaletteTransforms.sameHueTone` at .42/.68 lightness rather than filling all three slots with it, so its triad is a tonal ladder — same hue, so `hueDistance` stays at zero and the ring never gradients, while any surface that reads the companion slots does get real tones. Turning the switch off restores the flat three-identical-slots triad. The flag is a `derive()` parameter rather than a lookup inside it, so all three callers must pass it (wear `MainActivity`, `WatchPreviewView`, and `ColorTreatmentPreference`, which is fed it by `WatchFacePrefsFragment`) or the swatch dialog and the preview will disagree with the wrist. It is face-scoped alongside `wear_normal_color` — it was briefly not, which made it the one key on the Watch face screen that changed every face at once and left `AppearancePreferenceScopingTest` failing. It has since been generalized from Normal-only to **every** treatment: off, the whole surface paints one colour. The collapse is applied *last* — after the treatment, hue shift and modifier — by the pure `SurfacePaletteResolver.flatten`, which is split out precisely because `derive` goes through androidx ColorUtils and so cannot be JVM-tested, while "collapse to the primary, never to a companion" can (`SurfaceColorTreatmentTest`). Applying it last is what keeps the main colour identical with the palette on or off, so the switch reads as simplifying the theme rather than changing it. The key name stays `wear_normal_color_multi` for lossless migration, the same historical-name pattern as `wear_classic_icons_visible`; only the *picker* (`wear_normal_color`) is still Normal-only in the settings UI. `WatchPreviewView.drawEdgeSeekRing`'s `"solid"` branch mirrors the same conditional gradient so the phone preview doesn't lie about what the watch will show.

Orthogonal to face *structure* is the universal control-style treatment `ScreenTheme` (`common/.../ScreenTheme.kt`, pref `MiscPreferences.WEAR_SCREEN_THEME`: default / minimal / compact / cinema / vivid / contrast / amoled / hidden — "hidden" draws no control icons while keeping touch targets and accessibility actions active). It lives in `common` so the phone preview and the watch decode exactly the same tokens and can't drift apart (the wear-side `watch/view/face/ScreenTheme.kt` is just typealiases into it); `common/.../OverlayBackdrop.kt` does the same for the volume/seek/quick-panel overlay backdrops. Per-element visibility follows the same shared-pref pattern: `WEAR_SHOW_TRACK_TITLE` / `WEAR_SHOW_TRACK_ARTIST` (status/error text stays visible regardless), `WEAR_PLAYER_CONTROLS_VISIBLE` (persisted under its old key `wear_classic_icons_visible` so existing installs and backups migrate losslessly), and separate internal-progress (`WEAR_INTERNAL_PROGRESS_VISIBLE`) vs. edge-progress (`WEAR_EDGE_PROGRESS_VISIBLE`) visibility with independent edge-seek enablement.

**Album-derived colour lands asynchronously**, and anything resolved outside `applyAccentColor` will therefore read the *previous* track's accent. `Palette.generate` is a callback, so on a track change the art path starts extraction and continues immediately; `applyAccentColor` is what finally assigns `currentAccentColor` and it is the single place every dependent value is recomputed (title/artist/progress/shading/AOD tint into face state, plus `styleScreenButtons`, `applyAlbumArtScrim`, `applyPlayerBackground`). The awake clock was the one exception — `resolveClockColor` reads `currentAccentColor` but `applyClockAppearance` was only called from the art path, i.e. before extraction finished — so it stayed one track behind until an unrelated preference change refreshed it. It is now called at the end of `applyAccentColor` too, mirroring the `applyAmbientViewColors` call the ambient branch already made for the same reason. Anything new that derives from the accent belongs inside that function, not beside the call to it.

The always-on display is separately configurable via `MiscPreferences.WEAR_AOD_STYLE` ("follow"/"classic"/"chrono" plus one per Compose face — "expressive", "material", "eclipse", "poster", "studio", "immersive", "carousel", "chat", "split", "note", "verse"; the removed "minimal" is still mapped to "classic" on both sides so a stored value keeps working, and the list must stay in step with `wear_aod_style_values`) plus per-element toggles (`WEAR_AOD_SHOW_ART`/`_CLOCK`/`_TRACK_INFO`/`_TRANSPORT`/`_PROGRESS`/`_PILLS`), an outline color mode (`WEAR_AOD_COLOR_MODE` white/album/custom, lightness-lifted on the watch for legibility on black) and a brightness scale (`WEAR_AOD_INTENSITY`), all configured in the phone's Watch face tab: the classic AOD is the original View presentation, every Compose AOD is that face with `NowPlayingFaceState.ambient` set (outline-only, animation-free, same geometry as the awake face so wake-up taps land on the intended button), and "chrono" is a standalone `ChronoAmbientFace` — a big centred clock on pure black with the title beneath; `MainActivity.applyAmbientPresentation()` is the single place that styles ambient, and every variant keeps the burn-in pixel jiggle. Touch is never delivered to apps in ambient (the system wakes the watch instead) — only stem buttons/rotary work there, so AOD "buttons" are display-only by platform constraint.

`ButtonAction.isCoverArt` is the flag that separates **genuine artwork from an app-launcher icon**, and it is not the same question as `iconTintable`: an app icon is full-colour and so untintable too, which is why an "open app" row grew to album-cover size and got cropped into a circle. The rule is written **twice** — `MenuScreen.leadsWithArtwork` and the inflated quick-panel rows in `MainActivity.renderQuickPanelExtraActions` — and both had it wrong; the quick panel is the easy one to miss, because its *pill background* check already read `isCoverArt` correctly while the leading icon beside it did not, so half the row behaved. Both now derive three sizes from two flags: `isCoverArt` → cover, `!isCoverArt && !iconTintable` → app icon (`APP_ICON_DP`/`APP_ICON_SIZE`, kept in step by name since the two surfaces list the same actions), `iconTintable` → glyph. Only `PlayPlaylistShortcutAction` sets it, and only when the *fetched* thumbnail exists — the destination app's launcher icon is a real image but stretching it across a pill reads as a smeared logo. Three sizes result, not two: cover art fills the pill, an app icon keeps its own colours at glyph size, a monochrome template glyph stays a glyph.

Surface-level visual styling (volume overlay, quick panel, queue screen) is independently user-selectable per surface via `MiscPreferences` string prefs (e.g. `WEAR_VOLUME_STYLE`), each decoded to a local `*Style` enum (see `CircularVolumeBar.VolumeStyle`) with a `fromPref()` mapper — new styles are additive enum cases plus a `when` branch in that surface's paint/draw logic, not a new preference.

**Player shading** (the darkening overlay for legibility, `common/.../PlayerShading.kt` / `PlayerShadingDrawable.kt` on the watch, mirrored in `WatchPreviewView`) has three user controls, all face-scoped: a **style** (`wear_player_shading_style`), a **numeric intensity** (`album_art_dim_strength`, a 0–150 % value read as `percent/100f`; the old named `wear_player_shading_intensity` soft/balanced/strong pref is retained only to migrate legacy values — `PlayerShadingIntensity.percentFor`), and a **colour** (`wear_shading_color_mode`: black / album accent / desaturated / custom `wear_shading_custom_color`, resolved to a dark chromatic tone via `PaletteTransforms.shadingTone`). The clamp ceiling is the shared `SHADING_MAX_MULTIPLIER` const, not a hardcoded 1.0. Note the hard boundary this draws: `PlayerShadingDrawable` renders *over* the artwork and never receives the bitmap, so every treatment it can offer only darkens — a real edge blur is impossible there. That's why frosting is an **artwork** style instead (`common/.../FrostedEdges.kt`, an `ALBUM_ART_STYLE` value composed once where the bitmap is known, blurring through the shared `BitmapBlur` for the same API-31/`RenderNode` reason, and consumed by the classic face, every Compose face and the phone preview alike). Anything new that has to *see* the cover belongs on that side of the line. Authored *background* styles (Expressive, Poster, …) render their designed look independent of the "Dim album art" toggle — that toggle governs only the separate legibility scrim over plain artwork; the shared "apply this look to all faces" action in the Watch tab (`WatchFacePrefsFragment.applyCurrentAppearanceToAllFaces`) copies the current scope's explicit `SCOPED_KEYS` values onto every face.

Two watch-lifetime behaviours: the classic idle "Nothing playing" screen taps through to configured stopped-config gestures, but a play/pause command with no session resumes the last app (`AudioManager` PLAY key, see *Actions system*); and `MiscPreferences.WEAR_KEEP_SCREEN_ON` (applied by `wear/.../util/KeepScreenOn.kt`, which re-applies rather than sets once — the preference is phone-owned and can flip, or the face under it change, while a screen is open — and clears the flag as well as setting it) holds the player awake against the system's inactivity timeout, and is **face-scoped** rather than global: whether a screen should be held is a property of the composition in front of you, so a face you read wants it while the one you glance at should not pay its battery cost. It defeats the *timeout* only - lowering the wrist is a system gesture no window flag overrides, which is why the screens that must survive it (the lyrics screen) carry an ambient variant instead. The queue and menu deliberately do not consult it: they belong to no face. `MiscPreferences.WEAR_CLOSE_ON_IDLE` (default on, `MusicViewModel`) auto-closes the app ~60 s after reaching the truly-idle state, distinct from the user-configurable `CLOSE_TIMEOUT` which covers the paused case and stays off unless set.

The idle screen is otherwise driven by `common/.../IdleScreenAction.kt` (resume / shortcuts / menu / search / queue / none): `WEAR_IDLE_BUTTON_ACTION` picks its main button and `WEAR_IDLE_AUTO_OPEN` optionally jumps straight to one of those screens when the app opens with no session. The two decode through *different* fallbacks on purpose — an unrecognised button value resolves to `RESUME` (the user should still be left a way to start playback), an unrecognised auto-open value to `NONE`, and `RESUME` is excluded from `AUTO_OPEN_CHOICES` entirely, because starting playback merely because the app was opened is a surprise rather than a shortcut. The idle screen also shows the **stopped**-config mini buttons, which is exactly where the "start something" shortcuts live.
